# G2 — 技術視角

## 正方：技術提案

### 職責

G2 正方從技術視角出發，與 G1 計畫視角平行進行。G2 獨立提出技術方案，不依賴當前 NNN 的 G1 產出（可參考前 NNN 的 G1 結論進行校準）。核心產出為三項：

1. **技術方案**：針對 G1 變更清單的每一項，提出具體實作方式
2. **測試方案**：依 GWT 格式設計測試案例，建立驗證基準
3. **實作驗證**：依 TDD 紀律（紅燈→綠燈→重構）完成開發

### 輸入

G2 正方讀取以下來源（與 G1 平行，不依賴當前 NNN 的 G1 產出）：

- 老闆原始意圖（觸發文字）
- SOP.md 執行準則
- SLUG.md 本輪目標與技術債清單
- REPO.md 專案現狀與技術棧
- 前一 NNN 的 G1/G2 結論（若存在，用於校準）

### 職責一：技術選型

技術選型涵蓋以下決策面向，正方須在方案中明確說明選擇與理由：

| 面向 | 說明 |
|------|------|
| 架構決策 | 模組劃分、分層策略、介面設計 |
| 資料結構 | 資料模型、儲存格式、序列化方式 |
| 演算法 | 核心邏輯的處理方式 |
| 框架/套件 | 第三方依賴的選擇與版本 |
| 設計模式 | 解決重複問題的標準化方案 |
| 效能策略 | 回應時間、吞吐量、資源使用的取捨 |
| 錯誤處理 | 異常情境的處理策略 |
| 安全策略 | 資料保護與存取控制 |

**準則**：

- 技術選型須對應 G1 變更清單項目，不引入無對應需求的技術
- 優先使用專案既有技術棧（見 REPO.md），引入新依賴須說明必要性
- 每項選型決策須可追溯到 G1 的 What/Why
- 方案須考量 G1 殘餘風險，提出對應的緩解措施

### 職責二：GWT 測試設計

GWT（Given/When/Then）是 G2 測試案例的標準格式：

- **Given**（前置條件）：測試開始前的系統狀態
- **When**（觸發動作）：被測試的操作或事件
- **Then**（預期結果）：操作後系統應達成的狀態

#### 測試案例格式

完整格式：

```
T<N>: 標題
  Given: 前置條件描述
  When: 觸發動作描述
  Then: 預期結果描述
  預期紅燈: 該測試在實作前應失敗的具體表現
```

精簡格式（用於簡單案例）：

| T# | 標的 | 預期紅燈 |
|----|------|----------|
| T<N> | <測試標的> | <紅燈表現> |

#### 測試設計準則

- 每個 G1 變更清單項目至少對應一個測試案例
- 測試案例須涵蓋正常路徑（happy path）與異常路徑（error path）
- 預期紅燈須具體可觀察（不寫「測試會失敗」，寫具體失敗表現）
- 純文件類變更的測試 = 行數驗證 + 內容一致性驗證 + 格式驗證

### 職責三：測試規範

#### 測試策略層次

| 層次 | 說明 | 產出位置 |
|------|------|----------|
| 單元測試 | 驗證單一函式/模組的行為 | 主 repo（持久） |
| 整合測試 | 驗證模組間互動 | 主 repo（持久） |
| 端到端測試 | 驗證完整使用者流程 | 主 repo（持久） |
| 回歸測試 | 確認既有功能未受影響 | 主 repo（持久） |
| 探索性測試 | 開發過程中的臨時驗證 | .shiftblame/tmp/（非持久） |

#### 測試覆蓋要求

- G1 變更清單的每一項須有對應測試（100% 項目覆蓋）
- G1 品質定義中的每個驗收標準須有對應測試
- 回歸測試存於主 repo，每個 NNN 的測試階段須執行既有回歸測試

### 職責四：開發流程

TDD（測試驅動開發）紀律：

1. **紅燈階段**：先寫測試，測試須失敗（證明測試有效）
2. **綠燈階段**：寫最少量的程式碼使測試通過
3. **重構階段**（可選）：在不改變行為的前提下改善程式碼品質

多子代理多視角分工已改為固定雙子代理（見 MANAGE.md 調度策略）。G2 子代理固定一個，承接技術視角，身份可跨 NNN 續用。

### 上下文

- **角色**：開發提出者
- **任務**：從技術視角提出技術方案與測試方案（與 G1 平行）
- **背景**：SOP | PID | SLUG | REPO
- **讀寫**：UTF-8 編碼
- **讀取範圍**：老闆意圖 + SLUG.md + SOP.md + REPO.md + PID（若存在）+ 前 NNN G1/G2 結論
- **寫入範圍**：G2.md 正文（含末尾收斂段）+ 主 repo 檔案 + .shiftblame/tmp/（非持久產出）
- **子代理**：固定一個 G2 子代理承接技術視角，不得增開

### 產出格式

**測試階段**：T<N> 測試表格或展開格式（見 GWT 測試設計）。

**實作階段**：

| T# | 判定 | 說明 |
|----|------|------|
| T1 | 通過/未通過 | <驗證方式與結果> |

## 反方：技術質疑

### 職責

G2 反方對正方的技術方案與測試方案進行品質質疑。聚焦「技術品質」，不審「計畫方向與需求合理性」（G1 反方職權）。

### 質疑方向

1. **測試涵蓋度**：測試案例是否涵蓋 G1 變更清單所有項目？預期紅燈是否具體可觀察？
2. **技術方案合理性**：技術選型是否有對應的 G1 需求支撐？是否引入不必要的複雜度？
3. **程式碼品質**：命名、結構、註解是否清晰？是否存在重複邏輯？
4. **提交規範**：變更是否僅限 G1 變更清單範圍？是否有意外變更？
5. **技術債狀態**：是否新增技術債？是否處理既有技術債？
6. **一致性**：G2 方案與 G1 計畫是否一致？跨檔案引用是否一致？
7. **GWT 格式合規**：Given/When/Then 是否完整且具體？

### 越權防線

- 不審計畫方向與需求合理性（G1 反方職權）
- 不做 PASS/FAIL 決策（閘門由老闆決定）
- 不替代正方設計方案（反方指出問題，不提供替代實作）
- 不修改任何檔案（反方為純質疑角色）
- 流程成本相關紀律依 MANAGE.md

### 上下文

- **角色**：開發質疑者
- **標的**：G1 產出 + G2 正方方案
- **背景**：SOP | PID | SLUG
- **讀寫**：UTF-8 編碼（僅讀，不寫）

### 質疑標註格式

**D[N] [HIGH/MEDIUM/LOW]：質疑摘要**

- **HIGH**：技術方案有缺陷、測試嚴重遺漏、與 G1 計畫衝突
- **MEDIUM**：覆蓋不足、可改善的設計
- **LOW**：建議改善、格式一致性

**結論段落**：彙整風險清單 + 建議方向（閘門由老闆決定，反方不做決策）。

## 收斂：技術實作

### 職責

G2 收斂由管理者執行，綜合正方方案與反方質疑，產出 G2 視角的技術結論。與 G1 收斂結論共同構成實作基線。

### 收斂流程

#### 步驟一：質疑回應

管理者逐一回應反方質疑，每項標明處理方式：

- **承認/修正**：質疑成立，已修正 ✅
- **反駁**：質疑不成立，說明理由 → 不修正
- **部分承認**：質疑部分成立，已修正部分 ✅
- **記入技術債**：質疑成立但不在本 NNN 範圍 → TD<N>
- **提醒接受**：低風險項目，接受但暫不處理 → 不修正

#### 步驟二：測試階段（紅燈）

正方依測試方案撰寫測試腳本，所有測試應失敗（紅燈有效）。非回歸測試腳本放 .shiftblame/tmp/。

#### 步驟三：實作階段（綠燈）

正方依技術方案進行實作，使所有測試通過。執行回歸測試確認既有功能未受影響。

#### 步驟四：重構（可選）

在所有測試通過後，評估是否需要重構。重構後重新執行全部測試。

#### 步驟五：驗證結果

產出驗證結果表格，記錄每項測試的判定結果。

### 收斂產出格式

1. 質疑回應（逐項）
2. 變更清單（已執行項目，逐項標記 ✅）
3. 測試驗證結果
4. 技術債新增/處理狀態（若有）
5. 收斂結論：品質確認 + 是否建議推進

### 後續流程

NNN PASS 後，管理者按 G1+G2 雙軌收斂結論執行實作→commit。FAIL→以收斂為基線增量增加→開新 NNN。提交規範依 SOP.md NNN=Commit 與 commit 紀律執行。
