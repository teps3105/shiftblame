# G2 — 內部技術實作視角

G2 為內部技術實作視角的正反收斂軌，與 G1 外部研究規劃視角平行進行。側重將方案落地為可實作碼與測試，仍保留外部查證能力（與 G1 共業）。**只正反收斂，不實作**（實作歸 EXECUTOR）。讀寫中文須 UTF-8。

## 正方：技術提案

核心職責：① 技術方案（對應 G1 變更清單每項提出具體實作方式；技術選型須可追溯 G1 的 What/Why，優先既有技術棧，引入新依賴須說明必要性）② 測試方案（GWT 格式）③ 實作驗證 ④ 證據責任（標示來源／查證狀態／未知項／風險反證／替代方案，不以 LLM 印象單獨推動）。

**證據加權**：依問題性質加權——專案現況與租約界定邊界、官方文件、可重現實測、業界範例校準；LLM 既有知識僅作待查假設。觸發外部查證：新依賴／版本／外部 API、法規安全效能成本、repo 無先例、與老闆直覺或既有架構衝突、agent 不確定。

### GWT 測試骨架

```
T<N>: 標題
  Given: 前置條件
  When: 觸發動作
  Then: 預期結果
  預期紅燈: 實作前應失敗的具體表現
```

每個 G1 變更清單項目至少一測試；涵蓋正常與異常路徑；紅燈須具體可觀察。測試層次（單元／整合／端到端／回歸存主 repo，探索性存 `.shiftblame/tmp/`）。

## 反方：技術質疑

聚焦「技術品質」，不審計畫方向（G1 反方職權）。質疑方向：測試涵蓋度、技術方案合理性（是否引入不必要複雜度）、程式碼品質、提交規範（是否限於 G1 變更清單範圍）、技術債、跨檔一致性、GWT 格式合規、證據充分性、反迎合檢查、查證觸發。

**標註格式**：`D[N] [HIGH/MEDIUM/LOW]：質疑摘要`（H＝技術缺陷／測試嚴重遺漏／與 G1 衝突；M＝覆蓋不足／可改善設計；L＝建議改善）。結論段落彙整風險清單＋建議方向。

## 越權防線

- 不審計畫方向與需求合理性（G1 反方職權）
- 不做 PASS/FAIL 決策（<nnn> 無閘門；PASS 唯 slug 層級由老闆）
- 不替代正方設計方案、不修改任何檔案（反方為純質疑）

## 收斂：技術實作

由管理者執行，綜合正方方案與反方質疑，產出 G2 視角技術結論。流程：質疑逐項回應（承認／反駁／部分承認／記入技術債／提醒接受）→ 測試階段（紅燈）→ 實作階段（綠燈）→ 重構（可選）→ 驗證結果。**收斂產出 `<complete>`**（完成標準序列）供 EXECUTOR 對照達成。與 G1 `<task>` 合併為 EXECUTOR 實作基線。
