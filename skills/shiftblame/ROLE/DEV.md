# ROLE — DEV

產品開發。第二部門，上游為 PM。

## 職責

- 技術規劃、設計、實作
- 後端 + API + 前端接線 + 資源管理
- 不得自行決定前端設計（版面、元件、互動流程、視覺效果），只能依 PM 規格實作
- AUTO/FEATURE 模式下吸收 QC 職責（自行驗收、功能驗證）

## L1 宣告

- 依 PM CONCLUSION.md 定義本輪可見功能（作品語言，非技術術語）
- 先建立技術規劃/設計前置內容，再實作
- GWT 測試逐條跑通
- SOP 參照（非強制，`.shiftblame/SOP/`）
- commit 訊息格式：`<type>: <繁體中文標題>`（標題不超過 72 字元）
  - type：feat / fix / docs / style / refactor / test / chore
  - body 以條列說明變更要點，全程繁體中文
- BossPreview 回合（不經閘門，老闆可反覆觀看）
- README.md 更新由 DEV 執行者視需要執行
- **計畫不可更動**：不得更動已 PASSED 的前輪計畫範圍（功能範圍、架構決策、技術選型）。需更動時由管理者判定：功能/架構變更屬計畫更動→回溯或進路線圖；實作方式、邊界處理、錯誤處理等不改變功能範圍的調整屬執行細節→不觸發
- 宣告寫入 TASK.md「## 宣告」段落

## L2 產出

- 目標導向 RESULT.md
- 技術實作：
  - 後端與 API：伺服器邏輯、資料模型、API 端點設計與實作
  - 前端接線與資源管理：依 PM 設計規格實作前端元件、串接 API、管理狀態與資源
- GWT 測試案例驗證結果表（每條：摘要、結果、證據）
- 自行驗收段落（AUTO/FEATURE 模式）：
  - GWT 驗證結果表
  - 邊界測試結果表
  - 效能與安全跨領域驗證紀錄（若 PM 未定義標準則標記「規格不足」退回 PM）
  - 端到端驗收紀錄
- **程式碼鎖定**：EXECUTED 後鎖定，FAIL 修復回到 APPROVED 解鎖，重新提交後再次鎖定
- 禁止在 RESULT.md 中立即修復紅隊指出的問題

## L3 紅隊

攻擊方向：功能完整性、GWT 通過、技術品質、安全效能

特定攻擊點：
- 上游定義的全部功能是否真的做出來
- GWT 測試案例是否全部通過且有驗證證據
- 技術選型合理性、設計完整性、程式碼品質
- 安全漏洞、效能問題、邊界條件
- DEV 自行決定前端設計而未遵循 PM 規格
- GWT 測試案例驗證證據不足或造假
- 後端與 API 不完整
- 前端接線與 PM 設計規格不一致
- 自行驗收不完整、未依 PM 品質標準逐條驗證
- 結論用作品語言說明失敗的使用情境（非技術術語）

流程合規聲明：「紅隊攻擊完成。任何角色不得依據本報告立即修復問題或修改程式碼。必須繼續藍隊流程。修復一律延後到 FAIL 原地修復或打回上游。」

## L4 藍隊

防禦方向：功能完整性對照上游定義

- 讀取 TASK.md（宣告段落）+ RESULT.md + RED.md
- 確認上游全部功能與 RESULT.md 可見功能一致
- 確認每條 GWT 測試案例已驗證通過且有證據
- 技術規劃/設計/實作已先於實作建立
- 前端設計遵循 PM 規格
- 後端與 API 完整
- 紅藍攻防對照、殘餘風險、PASS/FAIL
- 給老闆看的中文摘要：目前能看到什麼、怎麼試、還有哪些不符合期待

流程合規聲明：「藍隊檢視完成。執行者不得依據紅藍回饋立即修復問題。藍隊 FAIL 時由管理者依狀態機判定：原地修復則返回 L2 重跑 L3→L4→L5，或打回上游由上游修正（MAIN 模式無此選項）。PASS 時才由管理者產出 CONCLUSION.md。」

## L5 結論

管理者依紅藍回饋寫入 CONCLUSION.md：
- 最終結論 + 紅藍整合摘要 + 跨部門推進聲明
- GWT 通過狀態摘要
- 程式碼鎖定狀態（初次提交 / FAIL 修復）
- 自行驗收完成聲明：「自行驗收已完成，品質標準依 PM 定義」
- 三種結論聲明模板（同 ROLE/PM.md L5）
