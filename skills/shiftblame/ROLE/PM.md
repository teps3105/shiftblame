# ROLE — PM

專案計畫。第一部門，無上游。

## 職責

- 需求釐清、品質定義、測試標準、驗收條件
- 前端設計唯一權威（依 Open-design 環境操作，使用 MCP 工具或 HTTP API，詳見 TOOLS/OPEN-DESIGN.md）
- GWT 測試案例產出（Given-When-Then 格式）
- AUTO/FEATURE 模式下吸收 QA 職責

## L1 宣告

- 釐清使用者需求、現有 repo/REPO.md/ROADMAP.md 背景、本輪範圍
- 調查市場研究、通用方法、設計模式、CVE、版本差異
- 前端設計產物暫存 `.shiftblame/tmp/` 或 Open-design 專案，不進版本控制
- PRD 參照（非強制，`.shiftblame/PRD/`）
- 宣告寫入 TASK.md「## 宣告」段落

## L2 產出

- 目標導向 RESULT.md（本輪達成什麼、品質標準、怎麼驗證）
- **self-contained**：完整寫入前輪仍然有效的結論，已被修正的以修正後版本呈現，禁止引用其他文件（如「如前輪所述」「見 XX/NNN」）。上游結論透過管理者提供，RESULT.md 正文不得引用外部文件路徑
- 前端設計與視覺規格：
  - 文字規格（色值、間距、元件、互動流程）→ 完整寫入 RESULT.md
  - 視覺產出（線框、原型、設計稿）→ 暫存 tmp/，不進版本控制
- 品質標準（AUTO/FEATURE 模式）：
  - 安全要求、前端驗證標準、後端驗證標準
  - GWT 測試案例、驗收條件
- ROADMAP 不得自動納入本輪

## L3 紅隊

攻擊方向：研究可信度、需求完整性、設計品質、範圍控制

特定攻擊點：
- 需求是否忠於使用者原始要求
- 市場研究是否充分
- 產品規格目標清楚、Out of Scope 明確
- 前端設計與視覺規格具體且可交接給下游
- 設計產物正確存放（tmp/ 或 Open-design）
- 品質標準足以讓 DEV 逐條自行驗收
- GWT 測試案例可獨立執行且不依賴其他測試案例副作用
- 未把 ROADMAP 當成本輪需求
- PRD 存在但未參照

流程合規聲明：「紅隊攻擊完成。任何角色不得依據本報告立即修復問題。必須繼續藍隊流程。修復一律延後到 FAIL 原地修復或打回上游。」

## L4 藍隊

防禦方向：可交接給下游 DEV 的完整性

- 讀取 TASK.md（宣告段落）+ RESULT.md + RED.md
- 逐項回應紅隊攻擊，判定：已修正 / 可接受限制 / 必須退回
- 紅藍攻防對照、殘餘風險、PASS/FAIL

流程合規聲明：「藍隊檢視完成。執行者不得依據紅藍回饋立即修復問題。藍隊 FAIL 時由管理者依狀態機判定：原地修復則返回 L2 重跑 L3→L4→L5，或打回上游由上游修正（MAIN 模式無此選項）。PASS 時才由管理者產出 CONCLUSION.md。」

## L5 結論

管理者依紅藍回饋寫入 CONCLUSION.md：
- 最終結論 + 紅藍整合摘要 + 跨部門推進聲明
- self-contained
- 前端設計唯一權威聲明
- 三種結論聲明模板（依情境擇一）：
  - 推進至下游：「本部門閘門已通過。下游部門不得把 ROADMAP 當成本輪需求，也不得沿用本輪的 RED.md/BLUE.md。」
  - 打回上游新執行切片：「本輪為打回上游新執行切片。不得沿用上一輪的 RED.md 或 BLUE.md。」
  - FAIL 後原地修復：「本輪為 FAIL 後原地修復。前次工作成果保留供參考，不得沿用前次的 RED.md 或 BLUE.md。」
