# DEPT.md — 部門主管協調機制

> 所有路徑基於專案根目錄解析，執行時由 task.md 提供絕對路徑。

## 1. 角色定位

部門主管（主管）是 CLI 員工與老闆之間的協調者，透過 `terminal()` 呼叫 CLI 員工（claude / codex / gemini）。

- 主管 = 部門代表，負責協調該部門的 CLI 員工
- 主管不是分析者，技術分析由 CLI 員工執行
- 主管負責：派工、追蹤、彙整共識、回報老闆

## 2. 部門分類與執行模型

### 部門分類

| 部門類型 | 部門 | execution_model | 職責 |
|---|---|---|---|
| 研究部門 | SEC / QA / PRD | equal_consensus | 三方各自分析寫 proposal.md，主管彙整 conclusion.md |
| 執行部門 | DEV / QC / EXP | lead_executor | 主執行者獨佔 worktree，輔助者檢視 |

### 執行模型差異

研究部門與執行部門的共識流程詳見 SKILL.md「部門執行模型」區段。

## 4. 研究 vs 執行部門流程差異

| 差異 | 研究部門 | 執行部門 |
|---|---|---|
| execution_model | equal_consensus | lead_executor |
| worktree | 無（唯讀分析） | 主執行者獨佔 worktree |
| 派工方式 | 三方同時派工 | 階段 0（共識）→ 階段 1（執行） |
| 產出 | proposal.md（主管寫 conclusion.md） | proposal.md + result.md（主管寫 consensus.md） |
| 共識 | 部門主管彙整三方意見 | 階段 0 達成四項準則共識 |

## 5. CLI 員工共識機制

### 共識流程（執行部門）

執行部門（DEV/QC/EXP）的共識流程：

```
辯論收斂（直接論點比較）→ 寫入 consensus.md → 各自執行 → 寫入 result.md
```

研究部門（SEC/QA/PRD）的共識流程詳見 SKILL.md「部門執行模型」區段（三方各自寫 proposal.md → 主管彙整 conclusion.md）。

consensus.md 必須包含：
```markdown
# <DEPT> 共識
## 分工
- claude：<工作項目>
- codex：<工作項目>
- gemini：<工作項目>
## 做法
<三方同意的執行方案>
## 產出結構
<三方同意的最終產出格式>
```

### 分歧處理原則

技術分歧（實作方式、架構選選、分工爭議）由 CLI 員工內部解決：
- 辯論收斂：最多 2 輪，異議必須附替代方案
- 互助修正：提前完成的 CLI 員工審查同事作業，發現錯誤直接修正
- 吸收降級：單點失效時由其他 CLI 員工吸收份額

需求不明（不清楚老闆要什麼、規格有歧義）才透過主管協調與老闆溝通，重新派工。
主管不參與技術裁決。

### 合作式失敗處理機制

同一部門的三個 CLI 員工是命運共同體，一榮則榮一損則損。

**失敗通知（failure-notice.md）：**

主管偵測到 CLI 員工失敗後，由主管在通訊目錄根層建立 failure-notice.md。

**單點失效補救：**

| 情境 | 處理 |
|---|---|
| 單一 CLI 員工失敗 | 其他 CLI 員工讀取 failure-notice.md，吸收其份額 |
| 單一 CLI 員工達到限額 | 主管寫入 failure-notice.md + 記錄詳情 |
| 二個 CLI 員工失敗 | 剩餘獨立完成，共識降級為單體，主管記錄降級原因 |
| 全部失敗 | 回報主管暫停 |
| 共識含技術分歧 | CLI 員工互助修正或重新辯論；仍無法收斂時採多數決，在 consensus.md 記錄少數意見 |

**權限錯誤處理：**

若 CLI 員工失敗原因是權限錯誤（非限額問題），主管必須排查並修改呼叫指令參數，直到權限正確為止。**不得因為權限問題就實施降級**。權限問題屬於派工設定失誤，不是 CLI 能力不足。

**部分完成失敗（proposal 已寫入但 consensus/result 因超時未寫入）：**

| 情境 | 處理 |
|---|---|
| 重試一次仍失敗（連續兩次超時） | 停止重試，改用單體彙整模式（見下方） |
| 全部失敗（連 proposal 都沒寫） | 回報主管暫停 |

**單體彙整模式（主管觸發）：**

當研究部門連續超時但三方 proposal 均已完整寫入時，主管派工**單一 CLI 員工**進行彙整：

- 單一 CLI 員工讀取三份 proposal.md + 上游報告 + DEPT 定義
- 研究部門：寫入 conclusion.md（含三方分析紀錄）
- 執行部門：寫入 consensus.md（含三方分工紀錄）和各 CLI 員工的 result.md
- meta.md 記錄降級事件：「共識收斂階段連續超時，降級為單體彙整」
- 這不是「全部失敗」，因為分析產出已完整，僅共識匯聚步驟需要代勞

### CLI 員工互助互監督機制

- CLI 員工應互相監督，發現同事的執行錯誤時直接修正，不等主管發現
- 提前完成作業的 CLI 員工不是發呆，而是監督同事的作業是否正確
- 各 CLI 員工的工具與指令定義是明文寫在 DEPT/*.md 與 CLI.md 中的，同事可以閱讀並驗證

### 執行期限額偵測

CLI 員工執行後，若偵測到 HTTP 429/503/529 等限額錯誤，在 proposal.md 中記錄詳情（研究部門）或 result.md 中記錄詳情（執行部門）。

## 6. 執行部門四項開工準則

### 執行部門共識流程

1. **階段 0（共識）：** 三方各自分析任務，寫入自己子目錄的 proposal.md，提出四項開工準則
2. **部門主管彙整：** 主管讀取三方 proposal.md，彙整三方意見寫入 consensus.md
3. **階段 1（執行）：** 主管指定一名主執行者，其餘為輔助者

### 四項開工準則

見 SKILL.md「執行部門四項開工準則」。

### CLI 失敗吸收策略

當某個 CLI 員工遇到失敗（限額、不可用、超時等）：

1. **重試**：CLI 內建 retry 机制（重試 1-2 次）
2. **吸收**：其餘兩個 CLI 員工接手失敗者的份額
3. **退回**：若全部失敗，則回報主管，由主管判斷是否退回上游

**新版失敗處理鏈：** 重試（內建）→ 吸收（其餘 CLI 接手）→ 退回上游部門


## 7. 退回機制

### 退回觸發條件

- 三個 CLI 員工皆失敗
- 四項準則無法共識
- 需求不明
- 工具不足

### 退回層級

| 退回層級 | 觸發條件 | 處理 |
|---|---|---|
| 同部門 | 單一部門內問題 | 退回該部門補強 |
| 上游部門 | 需要上游重新研究 | 退回上游部門 |

### 退回增量記錄

- L3/L4 模式中，退回任意部門時，其部門文件應增量填寫（不替換），確保退回有紀錄
- 退回後重新派工時，主執行者採公平序列輪替重新選定
- 退回紀錄格式：
  ```
  ## 退回紀錄
  - 退回來源：<部門名稱>
  - 退回原因：<簡述原因>
  - 退回時間：<ISO 8601 timestamp>
  - 退回輪次：Round N
  ```
- 退回修正紀錄格式（「退回修正」為輕微問題的針對性修正，不重新走完整派工流程）：
  ```
  ## 退回修正紀錄
  - 退回來源：閘門檢查點 2（輔助者檢閱）
  - 修正內容：<簡述修正項目>
  - 修正時間：<ISO 8601 timestamp>
  - 退回修正次數：N / 2
  ```
- 「退回」與「退回修正」的區別：「退回」= 完整重做，需重新走完整派工流程；「退回修正」= 輕微修正，不重新派工輔助者。兩者紀錄格式不同，不可混用。
- 退回修正次數限制：同一部門最多 2 次退回修正，超過自動升級為「退回」（完整重做）。

## 8. 主管嗅探責任

主管在派工後必須定期 poll，檢查 CLI 員工的 proposal.md 是否有內容：

- **頻率**：每 30 秒 poll 一次
- **檢查**：各 CLI 子目錄的 proposal.md 是否已有內容（研究部門）或 proposal.md / result.md 是否已有內容（執行部門階段1）
- **超時處理**：若 process 結束但檔案仍為空，判定為失敗，啟動失敗處理流程
- **空輸出處理**：若長時間（>10 分鐘）無新輸出，主管應主動介入診斷

### 向上請求工具支援

當 CLI 員工偵測到能力不足時：
1. 在 proposal.md（研究部門）或 result.md（執行部門）中記錄具體的限制和嘗試過的解決方案
2. 嘗試替代方案：使用其他工具（`terminal()` shell 指令、`write_file()`、`patch()`）完成工作
3. 若替代方案不足，在 proposal.md（研究部門）或 result.md（執行部門）中寫入：
   ```
   [TOOL_SUPPORT_REQUEST: <需要的工具/能力>]
   - **限制**：<具體描述>
   - **嘗試方案**：<已嘗試的解決方式>
   - **需要支援**：<具體需要什麼工具或權限>
   - **影響範圍**：<哪些任務項目受影響>
   ```
4. 主管偵測到 `[TOOL_SUPPORT_REQUEST]` 標記後，透過 `clarify()` 向老闆報告並請求指示
5. 禁止靜默降級：不可不記錄就直接跳過任務

## 9. 資料存取限制

各部門僅能讀取自身及上游部門的產出，嚴格禁止讀取下游部門的檔案。

## 10. 版本號制度（Semantic Versioning）

- 格式：major.minor.build
- 預設每次升級 build（第三段）
- 不主動升級 minor 或 major，除非老闆明確指示
- 同一 slug 內版本號僅在首次實作輪升 build，後續退回修正/增量輪次不重複升版
- 版本號最終由主管在 squash merge 前確認

## 11. 執行部門桌面驗證

所有執行部門（DEV/QC/EXP）完成任務後，必須實際執行業務流程驗證。

**驗證原則：**
- 驗證方式：用 `terminal()` 實際啟動/執行，產出執行輸出作為證據
- 「實際跑通」= `terminal()` 有實際輸出證明流程可運行，不是 ping 通就當通
- 文字描述「已啟動」不算證據，必須有 `terminal()` 輸出

**驗證標準（按部門）：**

| 部門 | 驗證標準 | 最低證據 |
|------|---------|---------|
| DEV | 應用/服務成功啟動，核心功能可操作 | `terminal()` 啟動日誌 + health check 回應 |
| QC | 至少一個 Happy Path 和一個邊緣案例實際跑通 | 完整測試執行輸出 + 操作步驟紀錄 |
| EXP | 完整用戶旅程端到端走通 | 端到端操作日誌 + 操作步驟可重現 |

**閘門檢查：**
主管在執行部門閘門中，讀取部門報告確認含「實際跑通」證據（`terminal()` 輸出、服務啟動日誌等）。若證據不足或缺少 → 退回該部門補齊。

**禁止行為：**
- 禁止以文字描述替代實際執行證據
- 禁止跳過驗證步驟
