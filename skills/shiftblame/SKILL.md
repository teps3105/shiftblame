# Shiftblame

把已授權的需求完成，以可核對的結果交付。工作目標由使用者決定，完成以實際成果為準。

## 授權與續行

使用者的新輸入先理解其目標與範圍；必要時用一句白話揭露差異。直接承接明確的行動要求及既有授權。只在缺少會實質改變結果的資訊，或需要新增授權、改變產品範圍、破壞性目標及正式發布政策時詢問；等待時先完成不依賴答案的工作。

使用者決定目標、授權、版本與正式出口。一般技術選型、修復、測試與工作分解由代理負責。新產品機制超出原授權時顯性說明並取得同意；已授權結果的正常實作由代理自主完成。使用者的明確指示優先於技能方法建議。

延續活動 slug；已指定 main 或 slug 就照辦。沒有活動流程的小型、可回復工作，沿目前已授權的分支直接實作。需要建立分支／slug 且使用者尚未決定時，先準備具體範圍再確認路由。純問答直接回覆。意圖理解詳見 [think](../think/SKILL.md)。

## 工作模式與兩個審查時點

直接實作：理解範圍 → 修改與適當驗證 → 檢閱結果 → 提交與交付。保護使用者既有變更，文件依維護與交付需要建立。

main 模式是在已授權分支直接作業，不要求分支一定名為 main，也不必建立 slug。需要跨回合或交接時，依 [save](../save/SKILL.md) 保存具名工作，再由 [resume](../resume/SKILL.md) 核對接續；交接不改變工作模式或授權。

slug 以 intent → requirement → research → plan → test → build → verify 記錄目前責任，使用 sb next 切段。G1 定義需求，G2 記技術決策，G3 記實作與驗收安排；內容依需求複雜度縮放。

- 時點 1：G1 完成後，獨立檢閱需求是否忠於意圖；修正必修項，再由使用者判定，requirement → research 帶 --adversarial 與 --boss-ok。
- 時點 2：verify 已取得必填需求的行為證據後，獨立檢閱驗收結果；修正必修項，再由使用者終審，開下一里程碑或結束時帶同一組旗標。
- 旗標只記錄已取得的真實授權。G1 定義區於時點 1 封存；契約變更重新核准。未變且仍在原授權內的契約可沿用。
- 先行研究：送出獨立審查後到使用者判定前，可非同步做唯讀查證、外部查證、<repo>/.shiftblame/tmp/ 筆記及隔離原型；不推進、不改 G1 或受驗來源、不提交。審查結果與待判定內容照常即時交給使用者，不因研究延後。筆記記下 sb state 印出的比對基準（時點 1 為 G1 定義區 hash，時點 2 為受驗 HEAD），判定後核對並只重查受影響部分；影響需求的發現告知使用者，判定前的研究結果不提供給審查者。
- 中鏈工作由代理自主推進。技術證據推翻方案時，回責任階段修正受影響成果，再驗證續行。只有實質改變需求或授權才重走 intent；續行、進度詢問與技術補充沿用目前需求。

審查時依 [AUDIT](references/AUDIT.md) 分開核對需求符合度與工程品質。審查意見由主代理核對並負責，追加獨立意見依未解爭議或證據缺口決定。

## 分工、進度與完成

主代理維持目標、授權與整合責任。當獨立工作可縮短時間或提高品質時，可分派有明確邊界的子代理。審計者對受審來源唯讀；實作者只能在已授權的隔離工作區產出，每份檔案由單一實作者修改，主代理檢閱後整合。

持續完成整體已授權工作，插入問題回答後接續原任務。進度更新說明有意義的結果與下一步，篇幅依內容選擇，估時須有依據。缺少必要授權、資訊或環境時揭露阻塞；完成整體交付後結束。

相同工具呼叫可能在觀察變化中的外部狀態。依新證據、結果與進展判斷是否重試；無進展時改變假設或方法；寫入範圍保持與任務相關。

## 驗證

選擇能證明需求的最小足夠證據：可自動化的行為使用測試，視覺、互動與外部應用依需要實際操作或渲染。行為保持也是有效契約；重構及遷移可以要求既有結果不變。

Given／When／Then 是驗收描述工具。測試通過、檔案存在或工具回傳成功，只證明其涵蓋的範圍；未執行標為未驗。保存實際操作、輸入、結果與必要來源，避免以代理指標冒充使用者結果。

變更後只重驗受影響或已失效的證據。新增測試依真實回歸風險決定，完成必要的回歸與整合檢查。外部查證及獨立意見依未知事實、風險與證據缺口觸發，沿用仍新鮮且適用的既有證據。

## 文件與提交

正式文件保持當下自洽，改動影響到描述時與實作同批更新。依 repo 慣例安排 README、模組文件、API、操作指南及設計理由；同一事實指定權威來源並引用。文件品質以正確性、可理解性與操作用途判定。

G1 的正式契約與執行證據分區；更新對應 AC／技術項，不堆疊互相衝突的版本。SOP／ROADMAP 依受影響範圍更新，重大治理變更才完整重審。整理方法見 [rewrite](../rewrite/SKILL.md)。

工作過程、診斷、審計報告及交接放在 <repo>/.shiftblame/tmp/；.shiftblame/ 不入庫。對話授權由平台保存；工作帳本只在跨回合或交接確有需要時維護。保存／恢復見 [save](../save/SKILL.md)、[resume](../resume/SKILL.md)，丟棄見 [dice](../dice/SKILL.md)。

提交聚焦一個可檢閱的變更，包含相關測試與文件；使用 sb commitmsg 驗證訊息與 staged 邊界，再提交。訊息清楚描述變更並遵循 repo 慣例。保護無關檔案及使用者修改。

## 需要時再讀

啟動先確認目標 repo、分支、工作樹與 sb state；存在活動流程時載入其 SLUG 與當前需要的 G 檔。SOP／ROADMAP 及過往決策依任務相關性讀取。恢復時用檔案和 git 核對關鍵狀態，摘要用於定位，正式來源用於核對；依相關性及變更範圍選擇讀取內容。

- 翻譯需求、釐清範圍或定義可觀察結果：[REQUIREMENT](references/REQUIREMENT.md)；治理詞義有歧義時查 [GLOSSARY](references/GLOSSARY.md)。
- 選型、待決問題或需用原型取證：[RESEARCH](references/RESEARCH.md)。
- 安排片段、依賴與驗收：[PLAN](references/PLAN.md)；建立 slug 文件時使用 [SLUG](assets/SLUG.md)。
- 選擇測試介面及斷言：[TEST](references/TEST.md)；整合與提交：[BUILD](references/BUILD.md)；核對交付結果：[VERIFY](references/VERIFY.md)。
- 難定位、反覆修補或原症狀未消失：[DEBUG](references/DEBUG.md)。
- CLI 操作及保護邊界：[MECHANISMS](references/MECHANISMS.md)；main 保存或恢復：[HANDOFF](references/HANDOFF.md)。
- 模組邊界、介面選擇或跨模組重構：[STRUCTURE](references/STRUCTURE.md)。
- 編修方法、術語或長期決策文件：[DOCS](assets/DOCS.md)；建立專案操作或方向文件：[SOP](assets/SOP.md)、[ROADMAP](assets/ROADMAP.md)。
