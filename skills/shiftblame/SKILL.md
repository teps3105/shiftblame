# SBM-SKILL — shiftblame 主規範

## 1. 範圍

本規範定義 shiftblame AI Agents 協作框架的適用範圍、核心原則、文件結構、啟動程序、管線流程與提交規範。本規範為框架最高階定義檔，所有子文件（GATE、ROLE、TEMPLATES、TOOLS）MUST 與本規範一致；衝突時以本規範為權威。

## 3. 術語與定義

### 3.1 規範詞彙（RFC 2119 / RFC 8174）

| 詞彙 | 中文 | 定義 |
|------|------|------|
| **MUST** / **REQUIRED** / **SHALL** | 必須 | 絕對要求，定義有效實作的必要條件 |
| **MUST NOT** / **SHALL NOT** | 必須不 | 分流標記：此路徑 MUST 改走指定替代路由出口。非禁令。 |
| **SHOULD** / **RECOMMENDED** | 應 | 強烈建議；存在合理理由得偏離，偏離時 MUST 記錄理由 |
| **SHOULD NOT** | 應不 | 分流標記：建議改走替代路由；有合理理由得維持原路徑並記錄 |
| **MAY** / **OPTIONAL** | 得 | 可選，不施加任何要求 |

> **MUST NOT／SHOULD NOT 的核心語義**：標記某路徑後，該條款 MUST 附帶替代路由出口。任何行為 MUST 有對應路由；互斥場景 MUST 交叉比對尋找更適合的路由出口。

### 3.2 框架術語

| 術語 | 定義 |
|------|------|
| 老闆 | 大局／需求／優先序／風險接受／PASS-FAIL 提供方 |
| 管理者 | 調度雙軌、收斂、初審、合併、歸檔之角色 |
| 執行者（EXECUTOR） | 承接合併基線、逐項執行 `<task>` 至 `<complete>` 之實作軌子代理 |
| slug | 單一變更管線識別碼；分支 `feat/<slug>`；生命週期 IN_PROGRESS → PASSED |
| `<nnn>` | slug 內單一正→反→收斂→實作輪次（如 001）；層級無 gate/PASS/FAIL |
| G1 | 外部研究規劃視角**正反收斂軌**；產出 `<task>` |
| G2 | 內部技術實作視角**正反收斂軌**；產出 `<complete>` |
| G3 | 共識後執行規劃層（**非正反收斂軌**）；產出 `<plan>` |
| `<task>` | G1 收斂產出之任務序列項（T1/T2/…），每項 MUST 可獨立 commit |
| `<complete>` | G2 收斂產出之完成標準序列，供執行者對照達成 |
| `<plan>` | G3 產出之執行計畫容器；內含 `<task>` 參照 + 明確化 `<complete>` + 實作策略 + 驗收流程 |
| 收斂 | 管理者綜合正方提案與反方質疑產出一致基線之程序 |
| 意圖釐清區塊 | 意圖揭露時條件式產生之可攜式釐清媒介；存在未決矛盾/模糊時隨附，老闆 MAY 攜至外部對話系統深化；深化結論返回後整合進 SLUG.md §1；四欄最小結構（Type/Issue/Context/Decision Needed） |

### 3.3 識別符規則

大寫裸詞（SLUG / TASK / COMPLETE）為概念名稱，MUST 單獨使用。小寫角括號（`<nnn>` / `<task>` / `<complete>` / `<slug>`）為該切片具體值。作任務名或前綴時 MUST 使用單獨角括號形式；MUST NOT 拼接複合識別符（如 `NNN001`）。

## 4. 適用範圍

### 4.1 MUST 開框架

以下情境 MUST 啟動框架管線：

- 複雜系統功能開發
- 解決 issue

### 4.2 MAY 不開框架

以下情境 MAY 不啟動框架管線，所有變更 MAY 直接於主分支（main）提交：

- 研究
- 探討
- 設計
- 維護等日常行為

不開框架時，提交規範（§8）MUST 仍然適用。

## 5. 核心原則

### 5.1 回饋即意圖

老闆每次說話即觸發意圖揭露。管理者 MUST 先揭露理解到的意圖，MUST 經老闆確認後方執行。

**意圖釐清區塊**（條件式產生）：每次揭露管理者 MUST 執行意圖檢查。存在未決矛盾或模糊時，管理者 MUST 產生「意圖釐清區塊」隨附揭露；無模糊即直接推進。老闆 MAY 攜區塊至外部對話系統深化，結論返回後以當下結構性事實整合進 SLUG.md §1 + 餵 G1（禁止逐次流水帳）。

區塊採四欄最小結構（不追求完整模板化）：

```
Intent Clarification Block v0.x

Type:    <矛盾點／模糊地帶／待決事項>
Issue:   <具體描述>
Context: <老闆回饋摘要 + 相關條文/決策>
Decision Needed: <需要老闆拍板什麼>
```

多個問題時以多組四欄重複。`v0.x` 為版本識別簡化版，序號由本條文承擔權威（不在對話內追蹤）。

### 5.2 老闆角色邊界

老闆為大局／需求／優先序／風險接受／PASS-FAIL 提供方。技術裁判由管理者依證據鏈承擔。

### 5.3 證據驅動說服

管理者 MUST 將需求翻譯為可驗證問題，MUST 以完整證據鏈提可反駁建議。與老闆技術直覺衝突時，管理者 MUST 附反證與替代方案供裁決。

### 5.4 查證優先

以下情境 MUST 查證：

- 不確定
- 新框架版本
- 外部 API
- 法規安全效能成本
- repo 無先例
- 與老闆直覺衝突
- 只能憑印象回答

### 5.5 SOP 約束與文件體系

SOP 為各專案執行準則。SOP 之建立與修改 MUST 經意圖揭露。

文件體系分層：

- SOP = 當下紀律
- ROADMAP = 後續候選
- 過去事實 = 以 git 歷史（commit 歷史 + archive/）為權威

文件 MUST 寫當下事實。日誌式（逐次變更流水帳）與教訓式表述 MUST 改寫為當下結構性事實。偵測措辭模式：

- 「推翻」
- 「經 N 輪」
- 「TRANSFERRED from」
- 「TD 由 X 解決」
- 「反面教訓」

### 5.6 先提案再質疑

G1／G2 正反收斂軌分軌，各走正→反→收斂流程。

### 5.7 迭代收斂

管理者 MUST 以最後收斂為基線增量增加。

### 5.8 變更前先體驗

修正／優化類變更前 MUST 與老闆共同完整體驗產品、MUST 記錄問題後再開始。

### 5.9 Slug 前置硬閘門

任何變更前 MUST 先建 `.shiftblame/<slug>/<nnn>/`、MUST 完成正方主 session 身份切換 + 反方開子代理、MUST 完成管理者收斂寫入 G1.md/G2.md 後方進入實作。

TEMPLATES 結構 = 合法文件白名單。slug 產出 MUST 鏡射 TEMPLATES/slug/ 結構。

### 5.10 SHIFTBLAME 文件隔離

`.shiftblame/` 為本地流程紀錄。提交前 MUST 以 `.gitignore` 排除。

### 5.11 本地產物隔離

啟動腳本、建置流程、服務 PID、runtime 輸出等本地產物 MUST 納入 `.gitignore`。正式產物 MUST 明確標示後方進入 repo。

### 5.12 目標統一寫入 SOP

所有長期／當前／附加目標 MUST 只寫 SOP，MUST NOT 另創平行目標文件。

### 5.13 固定雙軌（正反收斂）+ G3 執行規劃層

正反收斂 MUST 只走 G1+G2 雙軌。正方由主 session 擔任（G1/G2 身份切換），反方由子代理擔任（獨立對抗）。執行者為實作軌、臨時性單一職責，歸屬實作軌；收斂軌維持 G1+G2 結構。

G3 為共識後執行規劃層（非正反收斂軌），承接 G1+G2 收斂基線產出 `<plan>` 供執行者執行。G3 概念權威定義於本節 + §3.2 + §9.3，其他出處（GATE/MANAGER/TEMPLATES）MUST 指標引用此處。

### 5.14 實作與審查互斥

管理者 MUST 獨立 review 或 e2e 執行者的產出。若管理者自行改碼（兼任執行），則 MUST 由第三方證據驗證其產出（獨立 review／e2e）。

實作方與審查方為同一方時，MUST 補第三方佐證方算完成。

### 5.15 正反收斂軌身份續用與隔離

G1/G2 身份 MAY 跨 `<nnn>` 續用（G3 為非正反收斂軌，不適用身份續用）。正方主 session 分軌產出（身份切換），反方子代理獨立上下文。管理者 MUST 合併為實作基線。

隔離 = 身份切換（正方，弱）+ 獨立上下文（反方，強）。正方端隔離弱於上下文隔離，反方獨立性為主要補償。

### 5.16 選用外部 skill 整合

框架以自身定義檔為權威，外部 skill 為選用增益。衝突時定義檔優先。外部 skill 紀律經評估後 SHOULD 吸收進框架定義檔（以行為語言描述），吸收後外部 skill 退場。

### 5.17 外部工具整合總則

框架以自帶流程為骨幹，外部工具為升級鏈選項。降級鏈／升級鏈／工具清單／驗收機制細則集中於 TOOLS/。

TOOLS 採 `TOOLS/<功能英文大寫>/<具體工具>.md`，按行為功能載入（如 E2E/MEDIA/AUDIT）。

行為偵測調用工具為紀律一環：執行者/管理者 MUST 依當輪 `<task>` 標的及行為特徵（研究／實作／偵錯／驗收／簡化／規劃）調用對應 TOOLS/ 工具檔。漏調用時 MUST 補調用並 MUST 記錄。

### 5.18 決策邊界三條

1. **技術決策**：管理者自決後 MUST 記錄。
2. **接力方向**（下一可驗證問題）：MUST 由老闆拍板。
3. **過程順序步驟**：管理者自決。

### 5.19 術語總則

見 §3.3 識別符規則。

## 6. 文件結構

### 6.1 框架目錄

`skills/shiftblame/`：

| 目錄／檔案 | 內容 |
|------------|------|
| SKILL.md | 入口、主規範（本文件） |
| GATE.md | 閘門、`<nnn>` 生命週期、複審、收尾 |
| ROLE/ | MANAGER.md（管理者）、EXECUTOR.md（實作軌） |
| TEMPLATES/ | SOP/ROADMAP + slug/ 鏡射產出結構 |

### 6.2 執行規範分層

- ROLE/（MANAGER+EXECUTOR）：職責 + 越權防線
- TEMPLATES/slug/nnn/（G1+G2+G3）：三軌產出格式
- 專案細項：由 SOP 文件增補

## 7. `.shiftblame/` 內部佈局

每個採用 shiftblame 的專案 MUST 固定佈局：

- 兩文件（SOP/ROADMAP）
- `tmp/`
- `archive/`
- 進行中 `<slug>/`（結構鏡射 TEMPLATES/slug/：SLUG.md + nnn/G1.md + G2.md + G3.md）

TEMPLATES 樹 = 合法文件白名單。過去事實由 git 歷史（commit 歷史 + archive/）承擔權威。

## 8. 啟動程序

### 8.1 啟動序列

每次觸發僅載入索引層，按需讀取：

1. **文件衛生閘門**：檢核存在性（SOP/ROADMAP 齊全）+ 規範符合性（grep 日誌式/教訓式措辭）。不符即 MUST 進入修正路由（先修正再開 slug）。殘留未歸檔 MUST 先歸檔。
2. **歷史上下文查詢**：遍歷 archive/ 最新 slug（mtime 判定，降級字母排序）所有文件（SLUG.md + 各 nnn/G1.md + G2.md），推斷上下文，向老闆提議接下來方向（老闆拍板）。archive 為空則跳過。
3. **兩文件載入**：SOP → ROADMAP。
4. **Repo 狀態**：載入。
5. **租約載入**（三層）：
   - 長期 = SOP
   - 中期 = SLUG §6
   - 短期 = SKILL + GATE + ROLE/ + TEMPLATES/
   - 長期未載入 → 入口閘門 FAIL
6. **建立 slug**。

### 8.2 觸發

- `/shiftblame <文字>`：啟動 → 呈現意圖 → 確認 → 建立 slug
- `/shiftblame`（無參數）：呈現未歸檔清單

### 8.3 觸發後路由

觸發後 MUST 先走流程路由（完成 slug、G1/G2 收斂、實作意圖揭露與再次確認）再進入實作。確認理解 = 進入流程路由，MUST 再次確認方授權實作。

會話（觸發時機與分段）MAY 由老闆自由管理。`.shiftblame/` 經 `.gitignore` 排除於 repo 外。本地產物 MAY 納入 `.gitignore`。正式產物 MUST 明確標示。

## 9. 管線

### 9.1 三軌 slug 管線

G1（外部研究規劃）‖ G2（內部技術實作）正反收斂分軌產出（正方主 session 身份切換，反方子代理獨立）；收斂後進入 G3（共識後執行規劃層）產 `<plan>`。

### 9.2 `<nnn>` 生命週期

每個 `<nnn>` = 正 → 反 → 收斂 → G3 執行規劃層（產 `<plan>`：實作策略 + 行動序列 + 驗收流程 + 明確化 `<complete>`）→ 執行者逐項實作（每項 `<task>` 自驗通過即 commit）。

`<nnn>` 層級無 gate/PASS/FAIL。推進 MUST 由老闆指示。

### 9.3 收斂分軌產出

三軌分工：

| 軌 | 職責 | 產出 |
|----|------|------|
| G1 | Why/What：定義問題、目標、任務範圍 | `<task>` |
| G2 | Constraint/Done：技術限制、完成標準、驗收條件 | `<complete>` |
| G3 | How/Verify：實作方式、驗收方式、行動順序 | `<plan>` |

G1/G2 為正反收斂軌，G3 為共識後執行規劃層（非正反收斂）。管理者 MUST 合併 G1+G2 為一致基線，G3 承接基線產 `<plan>` 後派發執行者。

### 9.4 PASS 層級

PASS 唯 slug 層級（老闆拍板 slug 結束）。分支 `feat/<slug>`。

## 10. 提交規範

提交規範適用於全專案，不論是否開框架。

### 10.1 開框架時（`feat/<slug>` 分支）

每個 `<nnn>` 雙軌收斂後執行者逐項實作 `<task>`，每項自驗通過即 MUST commit（對照 `<complete>`）。執行者自驗／build 歸類為證據；獨立 review／e2e 走 §5.14 路由（實作與審查分離）。

`<task>` 執行完後：管理者 MUST 揭露升級鏈選項 → 老闆選擇擔任者 → MUST 獨立審核，審 e2e 證據／未驗項。

### 10.2 不開框架時（直接於 main）

仍 MUST 遵守下列通用規則。差異僅在分支（main 直提交、無 slug／`<nnn>` 流程）。

### 10.3 通用規則

| 項目 | 規範 |
|------|------|
| 訊息 | MUST 為 `<type>: <繁體中文描述>`，描述 ≤ 20 codepoint |
| 訊息驗證 | `... \| sed 's/^[^:]*: //' \| python -c "import sys;print(len(sys.stdin.readline().rstrip()))"` ≤ 20 |
| 範圍 | MUST 精準 `add` 僅本次變更相關檔案 |
| SHIFTBLAME 隔離 | `.shiftblame/` 經 `.gitignore` 排除於 commit 外（§5.10） |
| 分支（開框架） | MUST 在 `feat/<slug>` |
| 分支（不開框架） | MAY 直接於 main |
| 權限（開框架） | 管理者保留 merge |
| 權限（不開框架） | 無 merge 環節 |
