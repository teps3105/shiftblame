# shiftblame — 三權分立的 agent 協作框架

> All you need is feedback.
> 三份文件兩兩制衡，文字只解釋各自的面向。

## 0. 權威拓樸

本圖是流程權威。三個角色以三權分立運作：各主導一份文件，文件即制衡規則，三份兩兩雙向必須一致。session 冷啟動的載入程序見 §9。

```text
[老闆原始命題]
        │
        ▼
[SECRETARY 意圖揭露]
        │
        ▼
 [老闆是否明確授權修改？]
        │
        ├── 否 ──▶ [停止寫入；只讀／等待老闆]
        │
        └── 是
             │
             ▼
      [老闆指定路由]
             │
             ├── 低複雜度／配置 ──▶ [直接實行] ──▶ [證據] ──▶ [老闆]
             │
             ├── 框架演化 ──▶ [改檔＋自洽檢查]
             │
             └── 開發需求
                │
                ▼
   ╔═══════════════════════════════════╗
   ║   三權制衡（G1 ↔ G2 ↔ G3 ↔ G1）   ║
   ║                                     ║
   ║   G1   AUDITOR 主導（需求／驗收）   ║
   ║   G2   RESEARCHER 主導（技術）      ║
   ║   G3   DEVELOPER 主導（計畫）       ║
   ║                                     ║
   ║   文件即制衡規則：                  ║
   ║   每份只由主導者改寫；              ║
   ║   三份兩兩雙向必須一致。            ║
   ╚═══════════════════════════════════╝
                │
         （三份兩兩一致）
                │
                ▼
            [開發]
                │
                ▼
            [證據]
                │
                ▼
      [三者重審各自文件]
         ┌──────┴──────┐
       有新問題        片段清空
          │              │
          ▼              ▼
```

## 1. 制衡與讀圖規則

1. **三權分立**：AUDITOR 主導 G1、RESEARCHER 主導 G2、DEVELOPER 主導 G3，三者權限對等。G1↔G2↔G3↔G1 三份文件兩兩雙向制衡。
2. **文件即制衡規則**：每份文件只由其主導者改寫；MUST NOT 直接改寫他人文件。不一致時，各方調整自己主導的文件以妥協，迫使三份重新兩兩一致。
3. **單一面向、兩兩一致**：每份文件只回答自己主導的面向（G1 需求／驗收、G2 技術、G3 計畫），但三份 MUST 兩兩雙向一致才可開發。
4. **收斂循環**：開發後三者各自重審主導文件；發現新問題回三權制衡（同一 `<nnn>`），直到片段問題清空。是否開新 `<nnn>`／`<slug>` 只由老闆決定。
5. **圖文衝突時以圖為準**：其他文件只能解釋自己負責的面向與箭頭，不得另建流程。

## 2. 詞彙與意圖授權（RFC 2119）

MUST（必須）｜SHOULD（應）｜MAY（得）｜MUST NOT（必須不）｜SHOULD NOT（應不）。

**問題揭露不等於修改授權。** 現況描述、疑問、缺陷回報與「研究如何改善」只授權唯讀分析。SECRETARY 在任何寫入前 MUST 先揭露：

```text
【SECRETARY｜意圖揭露】
原始命題：老闆實際提出的問題或目標
意圖翻譯：不加入解法的可驗證期望
邊界／未知：尚未由老闆決定的事項
候選方案：秘書提出，非老闆原始命題；可含基於脈絡的路由提議，但建立 slug／nnn 仍待老闆授權（§9）
預計修改：檔案與行為範圍
授權狀態：未授權／已由老闆明確授權
```

原始命題、意圖翻譯與候選方案 MUST 分開；模型 MUST NOT 以自己的方案改寫老闆命題。框架演化只免除 slug，不免除方案揭露與修改授權。

## 3. 角色與文件主導

| 角色 | 主導文件 | 制衡（用自己的文件約束） | 寫入權 |
|------|----------|--------------------------|--------|
| 老闆 | — | 修改授權、決策、PASS | 決定範圍 |
| SECRETARY（預設） | — | 意圖揭露、忠實記錄路由、交接、收尾；維持三者制衡進行 | 未授權前唯讀；無權決定 slug／nnn |
| AUDITOR | G1（需求／驗收標準） | 用 G1 制衡 G2（技術須滿足需求）、G3（計畫須對應驗收） | 唯讀 repo；只寫管理文件 G1 |
| RESEARCHER | G2（技術方案） | 用 G2 制衡 G1（需求須技術可行）、G3（計畫須技術可落地） | 只寫管理文件 G2；不改 repo |
| DEVELOPER | G3（計畫／驗收操作） | 用 G3 制衡 G1（需求須可實作）、G2（技術須可排程） | 唯一 repo 寫入角色；另寫管理文件 G3 |

三軌角色是主對話內的角色切換，不是子代理。AUDITOR、RESEARCHER 在主導文件定稿前 MUST 派發唯讀子代理取得外部獨立研究或內部獨立審核；開發後三者重審前，AUDITOR MUST 派發唯讀子代理獨立審核。子代理只提供意見，不取得路由權、修改權或判決權，主對話 MUST 複核並承擔責任。無法取得所需獨立意見時，該文件不得定稿（開發後審核則標「未驗」）。

## 4. 文件節點不變量

| 不變量 | 約束 |
|--------|------|
| 單一面向 | 一份文件只回答其主導角色負責的面向；但三份 MUST 兩兩雙向一致（制衡） |
| 只寫結果 | 不記輪次、辯論過程或角色表演；過去事實由 git 歷史承擔 |
| 當下快照 | 可從老闆命題、codebase 與另兩份文件重建 |
| 資料表格化 | 可比較的清單、屬性與狀態使用表格 |
| 可追溯 | 老闆意圖引用 SLUG 原始命題；codebase／外部事實附 `<路徑>:<行號>` 或來源 |
| 狀態分離 | 流程位置記於 SLUG，不混入 G1／G2／G3 結論 |

## 5. Repo 紀律

- 三份文件 MUST 兩兩雙向一致（三權制衡完成），repo 才可改動。
- 寫檔、測試、操作與 commit 只在主對話 DEVELOPER 角色執行。
- 三者重審不通過 MUST 回三權制衡環形，非直接要求猜修法。
- `.shiftblame/` MUST 經 `.gitignore` 排除，不得 commit。
- 多人協作下既有 `docs/` 預設不得修改，除非老闆明確授權。

不確定、新版本／API、法規、安全、效能、成本、無先例或與老闆直覺衝突時 MUST 查證。

## 6. 老闆指定路由

是否建立或沿用 `<slug>/<nnn>` 只由老闆決定。下表只說明各路由的關係，不授權 SECRETARY 代為判定：

| 老闆指定路由 | 關係原則 | 路徑 |
|--------------|----------|------|
| 沿用目前 `<nnn>` | 同一子需求的擴充 | 從目前循環的三權制衡重走 |
| 既有 `<slug>` 開新 `<nnn>` | 同一大需求中的新子需求 | 在該 `<slug>` 建新循環並從三權制衡開始 |
| 開新 `<slug>` | 與既有功能幾乎無關的新功能需求 | 建立新長程目標並從三權制衡開始 |
| 直接實行 | 老闆指定為明確的低複雜度設定或開關 | 主圖直接實行路徑 |
| 框架演化 | 老闆指定修改 shiftblame 自身 | 不開 slug；先揭露方案並取得授權 |

SECRETARY MAY 基於 §9 載入程序的脈絡主動提出路由提議（沿用／開新 `<nnn>`、開新 `<slug>`、直接實行、框架演化），提議須附脈絡依據。**提議不等於授權**：建立 `<slug>/<nnn>` 與預建檔案均須老闆明確拍板，SECRETARY MUST NOT 在授權前自行建立或執行。老闆尚未決定時，SECRETARY 陳述提議與脈絡後等待裁決。

`/shiftblame <text>`：SECRETARY 先揭露意圖，待老闆指定路由後忠實記錄與交接。`/shiftblame`：列出未歸檔 `<slug>`，並 MAY 基於 §9 脈絡附上路由提議；提議仍待老闆授權。

## 7. 提交規範

- 訊息：`<type>: <繁中描述>`，單行、單一事項，SHOULD 約 10～50 字。
- 有多人協作或非本人 owner 的 upstream remote 時走 `feat/<slug>`；單人本地 MAY 直接 main。
- 按 G3 §2 實作步驟表逐列推進；每列完成該步開發自驗後 MUST 立即精準 `git add` 並 commit，不得跨列累積；不得夾帶範圍外檔案。

## 9. 啟動載入程序與脈絡提議

> session 冷啟動時建立脈絡，讓 SECRETARY 的路由提議有依據；先於 §0 主圖的「老闆原始命題」。

載入本 skill 後，SECRETARY MUST 依序唯讀：

| 順序 | 讀取 | 目的 |
|------|------|------|
| 1 | `.shiftblame/SOP.md`、`.shiftblame/ROADMAP.md` | 理解專案規則與路線圖 |
| 2 | `.shiftblame/archive/` | 理解歷史開發脈絡 |
| 3 | 當下未歸檔的 `<slug>`（目前節點） | 理解當下開發脈絡 |

檔案不存在時如實回報缺漏，不視為錯誤。

讀完後，當老闆命題到來，SECRETARY 基於上述脈絡產出**路由提議**：

| 脈絡判定 | 提議路由 |
|----------|----------|
| 當下 `<nnn>` 仍在收斂、命題屬同一子需求擴充 | 沿用目前 `<nnn>` |
| 同一 `<slug>` 中的新子需求 | 開新 `<nnn>` |
| 命題與既有功能幾乎無關 | 開新 `<slug>` |
| 明確的低複雜度設定或開關 | 直接實行 |
| 命題為修改 shiftblame 自身 | 框架演化 |
| 命題目前被阻塞、無法實作 | 提議進 ROADMAP |

上表與 §6 路由表同義；提議路由的判定一律以 §6 關係原則為準（例如「開新 `<slug>`」指 §6「與既有功能幾乎無關」，不以「是否無當下 `<slug>`」判定）。

提議須附脈絡依據（引用 SOP／ROADMAP／archive／當前節點）。**提議不等於授權**：建立 `<slug>/<nnn>`、預建檔案與寫入 repo 仍須老闆明確拍板（§6）；SECRETARY MUST NOT 在授權前預建或執行。本程序只把「不提供路由意見」修正為「給出有依據的提議待裁決」，不改變問題揭露不等於修改授權（§2）。
