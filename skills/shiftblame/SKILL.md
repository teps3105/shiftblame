# shiftblame — 回饋驅動的 agent 協作框架

> All you need is feedback.
> 文件越乾淨,注意力越自由。

> **shiftblame = 轉移責任以保持注意力。** 注意力是有限資源;框架的每個機制都在把責任轉移到別處,讓當下的注意力保持乾淨聚焦。

```
老闆 ──揭露意圖──▶ 迭代(讀 G1/G2 + codebase → 改寫快照,到穩定)
                       │ 穩定(重讀結論不再變)
                       ▼
                  G3 cross-attend ──▶ 執行(causal) ──▶ 證據
                       ▲                                    │
                       └──────── 未 PASS 退回迭代 ──────────┘
老闆 ──PASS──▶ 收尾歸檔
```

## 0. 命題:轉移責任以保持注意力

注意力是有限資源(context、聚焦、工作記憶)。框架每個機制都是把責任轉移到別處,讓當下的注意力保持乾淨聚焦:

| 機制 | 轉移責任到 | 保持的注意力 |
|------|-----------|--------------|
| 三角分工(管理者↔執行者↔審查者) | 不同 agent | 各自只注意自己的 scope |
| 文件快照(G1/G2/G3) | artifact | 狀態落盤,釋放工作記憶;要時再 re-attend |
| `<slug>` / `<nnn>` | 兩個注意力弧 | `<slug>` 釘住跨迭代穩定的目標;`<nnn>` 承載當輪結論 |
| 兩 checkpoint | 老闆在對的弧上拍板 | 其餘轉移給自由迭代 |

### 兩層模型(機制的核心形狀)

| 層 | 角色 | 形狀 |
|----|------|------|
| **文件層** | 責任落點(blame sink):承載「現在的結論」 | 乾淨、線性、單一職責、結果式快照 |
| **協定層** | 注意力運算:agent 如何讀寫文件 | 多視角注意力、迭代、emergent 收斂 |

注意力是 agent 對文件的**讀法**,不是文件的形狀。乾淨的線性文件正是 transformer 讀得最好的輸入——讓文件乾淨,與讓 agent 用注意力,是同一件事。

## 1. 詞彙(RFC 2119)

MUST(必須)|SHOULD(應)|MAY(得)|MUST NOT(必須不)|SHOULD NOT(應不)。

## 2. 角色

老闆是三角外的主角(principal);三角分工三者互斥,保獨立:

```
             老闆(意圖/PASS)
                   │
       ┌───────────┼───────────┐
       ▼           ▼           ▼
   管理者       執行者       審查者
   (規劃)      (實作)       (驗證)
```

- **老闆**:需求/優先序/風險/PASS。握有兩個真 checkpoint:揭露意圖、PASS。
- **管理者**(規劃):多視角讀 G1/G2+codebase,迭代到穩定,cross-attend 產 G3,派發執行者,收尾。不實作、不審查。
- **執行者**(實作):逐項 `<task>` 實作至 `<complete>`,自驗通過即 commit。
- **審查者**(AUDITOR,驗證):`<complete>` 後獨立審 e2e 證據/未驗項/可查核引用。不實作、不規劃。

## 3. 三文件(皆為當下結論快照)

| 文件 | 職責 | 產出 |
|------|------|------|
| G1 需求研究 | What/Why/邊界/可行性/品質定義/變更清單 | `<task>` 候選 |
| G2 技術分析 | How/選型/測試骨架/證據/完成標準 | `<complete>` |
| G3 實作計畫 | 綜合 G1+G2 → 行動序列+驗收 | `<plan>` |

G1/G2 是兩個研究視角對同一份 codebase+意圖的結論(cross-attend),不是先後階段。G3 由 cross-attention 產生:計畫項逐一引用研究結論,非重抄。

## 4. 文件層五不變量(同時保證乾淨 + 不鎖迭代)

1. **單一職責**:一份文件只承擔一個角色;內容與流程狀態不分混。
2. **只寫結果,不寫過程**:文件是「現在是什麼」。第幾輪、誰質疑誰、收斂記錄一律不入文件。過去事實以 git 歷史為權威。
3. **冪等可重寫**:任何時刻能從 codebase + 老闆意圖重生成而不丟資訊。文件不當唯一記憶體。
4. **狀態與內容分離**:流程狀態用極簡欄位承載,不滲進內容結構。改內容不破壞狀態語義,推進不卡住內容迭代。
5. **注意力在讀不在寫**:文件結構絕不表達「誰注意誰」。引用只是引用,不是注意力網。

## 5. 協定層:注意力迭代(不鎖迭代的引擎)

- **讀 = self-attention**:每輪把 G1/G2/G3+codebase+SOP 當 token 集合,可同時掛多視角(需求一致性/技術可行性/風險/成本/合規)。視角是讀的姿態,不是額外文件。
- **寫 = 落盤當下結論**:把該改的那份覆寫成新快照。增量,不改形狀。
- **收斂 = emergent**:重讀後結論不再變 = 穩定,即終止條件。由「結論還在變嗎」決定,不由「走完幾個閘門」決定。

## 6. 紀律:不變量 + 兩 checkpoint,不靠狀態機

- **文件不變量**(每份文件隨時 MUST 滿足):證據優先、寫當下事實、可查核引用。隨時可審,不綁順序。
- **真 checkpoint 只有兩個**:老闆**揭露意圖**(進入迭代)、老闆 **PASS**(結束)。中間全是自由迭代。
- **三角互斥**:規劃/實作/驗證分屬管理者/執行者/審查者;實作與審查 MUST 不同人(見 SBM-GATE §6)。
- **可查核引用**:每條事實陳述 MUST 附 `<檔案路徑>:<行號>`;引用對象變更時同步查核,失效引用等同錯誤。
- **文件先於 repo 改動**:涉及 repo 的改動 MUST 先由 slug 文件承載(G3 `<plan>` 指明該變更);MUST NOT 先改碼再回頭補文件。迭代發生在文件層(讀 G1/G2、改寫快照),repo 改動是穩定計畫後的執行——順序不可倒置。

證據查證觸發:不確定、新版本/依賴/API、法規/安全/效能/成本、無先例、與老闆直覺衝突——MUST 查證。

## 7. 觸發

- `/shiftblame <text>`:揭露意圖 → 老闆確認 → 建 `<slug>` → 迭代 → 穩定後再確認 → 實作。
- `/shiftblame`:列未歸檔 `<slug>`。

## 8. 提交規範

- 訊息 `<type>: <繁中描述>`,簡潔一行可掃過(防膨脹,不硬限字數;MUST NOT 為算字數耗 token)。
- 分支依外部證據:SOP 記載多人協作、或具非本人 owner 的 upstream remote 等 → 走 `feat/<slug>`,管理者收尾 merge;單人本地無上述證據 → MAY 直接 main。

## 9. 框架檔

```
skills/shiftblame/
├── SKILL.md      # 主規範(本檔)= SBM-SKILL
├── GATE.md       # checkpoint、<nnn>、收尾 = SBM-GATE
├── ROLE/
│   ├── MANAGER.md   = SBM-MANAGER
│   ├── EXECUTOR.md  = SBM-EXECUTOR
│   └── AUDITOR.md   = SBM-AUDITOR
└── TEMPLATES/    # 範本 = 合法文件白名單
    ├── SOP.md       = SBM-SOP
    ├── ROADMAP.md   = SBM-ROADMAP
    └── slug/        # 鏡射 .shiftblame/<slug>/
        ├── SLUG.md  = SBM-SLUG
        └── nnn/
            ├── G1.md = SBM-G1
            ├── G2.md = SBM-G2
            └── G3.md = SBM-G3
```

## 10. 專案工作區 `.shiftblame/`

每個採用 shiftblame 的專案自成本目錄,MUST 經 `.gitignore` 排除於 repo 外。

```
.shiftblame/
├── SOP.md         # 專案執行準則(長期租約,當下事實)
├── ROADMAP.md     # 待開發業務需求(老闆提,現無法實作)
├── <slug>/        # 鏡射 TEMPLATES/slug/
├── tmp/           # 非持久產出(探索性研究/草稿)
└── archive/       # 已歸檔任務(過去事實由 git 歷史承擔權威)
```
