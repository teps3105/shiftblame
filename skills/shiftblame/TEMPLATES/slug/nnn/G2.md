# G2 — 內部技術實作視角

> 與 G1 分軌進行。正方主 session（身份切換）、反方子代理獨立。

## 1. 正方：技術提案

對應 G1 變更清單每項 MUST 提具體實作方式。技術選型 MUST 可追溯 G1 What/Why，SHOULD 優先既有技術棧，新依賴 MUST 說明必要性。

**最短決策階梯**（依序採用，前階可用即止）：YAGNI 跳過 → 復用既有 → 標準庫 → 平台原生 → 已裝依賴 → 一行勝五十行 → 刪除優先於新增 → 投機抽象改直接實作。

**證據加權**：專案現況界定邊界 > 官方文件 > 可重現實測 > 業界範例。LLM 印象歸待查假設。**觸發外部查證**：新依賴/版本/API、法規安全效能成本、無先例、與老闆/架構衝突、不確定。

**GWT 測試骨架**：`T<N>: 標題 / Given: 前置 / When: 觸發 / Then: 預期 / 預期紅燈: 實作前失敗表現`。每個 G1 變更清單項 MUST 至少一測試。測試先行（紅燈→綠燈）。涵蓋正常與異常路徑。層次：單元/整合/e2e/回歸 → 主 repo；探索性 → `.shiftblame/tmp/`。

遇缺陷 MUST 建假設→驗證鏈，逐環驗證後再下結論。根因修復 SHOULD 優先症狀修補。

## 2. 反方：技術質疑

聚焦技術品質：測試涵蓋度、方案合理性、過度工程、程式碼品質、提交規範（範圍限 G1 變更清單）、技術債、跨檔一致性、GWT 合規、證據充分性、反迎合、查證觸發。計畫方向審查歸 G1 反方。

**標註**：`D[N] [HIGH/MEDIUM/LOW]：摘`（HIGH=技術缺陷/測試嚴重遺漏/與 G1 衝突；MEDIUM=覆蓋不足/可改善設計；LOW=建議）。結論 MUST 彙整風險清單+建議。

## 3. 越權防線

計畫方向/需求合理性歸 G1 反方。PASS/FAIL 歸 slug 由老闆。反方產出回管理者，寫檔限白名單 G1.md+G2.md。方案設計歸正方。

## 4. 收斂：技術實作

管理者執行：質疑逐項回應 → 紅燈 → 綠燈 → 重構（可選）→ 驗證。產出 `<complete>`（完成標準序列）與 G1 `<task>` 合併為執行者基線。

**明確化 `<complete>`**（於 G3 產出具體清單，**格式權威在本節**）：`T[N]`（同 G1 `<task>` 軌）下掛 `- [ ] V[N][.M] 驗證類型：判準`。驗證類型限四類：grep/行數/字串/檔案。不可機械驗證項 MUST 標 `S[N]`「需管理者初審」。抽象段為權威。
