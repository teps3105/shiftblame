# G2 — 內部技術實作視角

G2 為內部技術實作視角的正反收斂軌，與 G1 外部研究規劃視角分軌進行。**正方由主 session 擔任**（身份切換），反方由子代理獨立對抗。側重將方案落地為可實作碼與測試，仍保留外部查證能力（與 G1 共業）。**只正反收斂，不實作**（實作歸 EXECUTOR）。讀寫中文須 UTF-8。

## 正方：技術提案

核心職責：① 技術方案（對應 G1 變更清單每項提出具體實作方式；技術選型須可追溯 G1 的 What/Why，優先既有技術棧，引入新依賴須說明必要性；**遵循最短解決策階梯**：需求存疑先跳過（YAGNI）→ 復用既有 → 標準庫 → 平台原生 → 已裝依賴 → 一行勝五十行 → 禁投機抽象（單一實作的介面/工廠/設定）、刪除優先於新增）② 測試方案（GWT 格式）③ 實作驗證（**遇缺陷須建立假設→驗證鏈，禁跳結論；根因修復非症狀修補**）④ 證據責任（標示來源／查證狀態／未知項／風險反證／替代方案，不以 LLM 印象單獨推動）。

**證據加權**：依問題性質加權——專案現況與租約界定邊界、官方文件、可重現實測、業界範例校準；LLM 既有知識僅作待查假設。觸發外部查證：新依賴／版本／外部 API、法規安全效能成本、repo 無先例、與老闆直覺或既有架構衝突、agent 不確定。

### GWT 測試骨架

```
T<N>: 標題
  Given: 前置條件
  When: 觸發動作
  Then: 預期結果
  預期紅燈: 實作前應失敗的具體表現
```

每個 G1 變更清單項目至少一測試；**測試先行（紅燈→綠燈）：實作前先寫測試，測試結構按專案特性建立正確結構**（框架不預設測試形態，依專案技術棧與可驗證性質選擇）；涵蓋正常與異常路徑；紅燈須具體可觀察。測試層次（單元／整合／端到端／回歸存主 repo，探索性存 `.shiftblame/tmp/`）。

## 反方：技術質疑

聚焦「技術品質」，不審計畫方向（G1 反方職權）。質疑方向：測試涵蓋度、技術方案合理性（是否引入不必要複雜度）、**過度工程審查（可否刪減、有無投機抽象、是否重複標準庫/平台能力）**、程式碼品質、提交規範（是否限於 G1 變更清單範圍）、技術債、跨檔一致性、GWT 格式合規、證據充分性、反迎合檢查、查證觸發。

**標註格式**：`D[N] [HIGH/MEDIUM/LOW]：質疑摘要`（H＝技術缺陷／測試嚴重遺漏／與 G1 衝突；M＝覆蓋不足／可改善設計；L＝建議改善）。結論段落彙整風險清單＋建議方向。

## 越權防線

- 不審計畫方向與需求合理性（G1 反方職權）
- 不做 PASS/FAIL 決策（<nnn> 無閘門；PASS 唯 slug 層級由老闆）
- 不替代正方設計方案、不修改任何檔案、不自行寫檔（反方為純質疑，產出回傳管理者；白名單僅 G1.md+G2.md）

## 收斂：技術實作

由管理者執行，綜合正方方案與反方質疑，產出 G2 視角技術結論。流程：質疑逐項回應（承認／反駁／部分承認／記入技術債／提醒接受）→ 測試階段（紅燈）→ 實作階段（綠燈）→ 重構（可選）→ 驗證結果。**收斂產出 `<complete>`**（完成標準序列）供 EXECUTOR 對照達成。與 G1 `<task>` 合併為 EXECUTOR 實作基線。

**明確化 `<complete>`**（實作前規劃階段產出，附於當輪 G2.md 末尾）：將抽象 `<complete>` 細化為機械驗證清單，格式：`T[N]`（與 G1 `<task>` 同軌）下掛 `- [ ] V[N][.M] 驗證類型：判準`，驗證類型限四類（grep／行數／字串／檔案，源自 EXECUTOR 自驗手段）。不可機械驗證項（語義／行為）標 `S[N]`「需管理者初審」，不混入 V#。明確化段為抽象 `<complete>` 的細化（抽象段仍為權威）。
