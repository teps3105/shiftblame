# G2 — 技術分析

> 當下結論快照。與 G1 cross-attend 同一份 codebase+意圖。只寫結果,不寫過程(見 SBM-SKILL §4)。

## 1. 技術方案

對應 G1 變更清單每項 MUST 提具體實作方式。技術選型 MUST 可追溯 G1 What/Why,SHOULD 優先既有技術棧,新依賴 MUST 說明必要性。

### 1.1 最短決策階梯(依序採用,前階可用即止)

1. YAGNI 跳過
2. 復用既有
3. 標準庫
4. 平台原生
5. 已裝依賴
6. 一行勝五十行
7. 刪除優先於新增
8. 投機抽象(單一實作的介面/工廠/設定)→ 改直接實作

### 1.2 證據加權

依問題性質加權:專案現況界定邊界 > 官方文件 > 可重現實測 > 業界範例。LLM 印象歸待查假設。

觸發外部查證:新依賴/版本/API、法規安全效能成本、無先例、與老闆/架構衝突、不確定。

### 1.3 缺陷處理

遇缺陷 MUST 建假設→驗證鏈,逐環驗證後再下結論。根因修復 SHOULD 優先症狀修補。

## 2. GWT 測試骨架

```
T<N>: 標題
  Given: 前置條件
  When: 觸發動作
  Then: 預期結果
  預期紅燈: 實作前應失敗的具體表現
```

- 每個 G1 變更清單項 MUST 至少一測試。測試先行(紅燈→綠燈),涵蓋正常與異常路徑。
- 層次:單元/整合/e2e/回歸 → 主 repo;探索性 → `.shiftblame/tmp/`。

## 3. 明確化 `<complete>`(格式權威定義處)

於 G3 產出具體清單,**格式權威在本節**。將抽象 `<complete>` 細化為機械驗證清單。

**格式**:`T[N]`(同 G1 `<task>` 軌)下掛 `- [ ] V[N][.M] 驗證類型:判準`。

**驗證類型限四類**(源自執行者自驗手段):grep / 行數 / 字串 / 檔案。

**不可機械驗證項**(語義/行為)MUST 標 `S[N]`「需審查者」。

明確化段為抽象 `<complete>` 的細化;抽象段仍為權威。

## 邊界

計畫方向/需求合理性歸 G1。PASS/FAIL 歸 `<slug>` 由老闆。每條事實陳述 MUST 附 `<檔案路徑>:<行號>`。
