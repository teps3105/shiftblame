# 文件品質

文件為讀者要完成的工作而寫。遵循專案的語言、位置、命名與維護慣例。以內容正確、容易理解及能支持操作判斷品質。

## 內容與來源

每個事實有明確權威來源，其他文件回指。描述實際行為、適用條件與必要操作；命令、路徑、簽章或範例在有助理解時提供。區分現況、目標、假設與尚未批准的提案。

同一機制避免互相矛盾的描述。內容服務同一讀者任務時可合併；責任與用途不同時可拆分。README、操作指南、API 參照、設計理由及路線文件依專案需要存在，不指定唯一布局。

## 維護與可讀性

先說用途與入口，再展開細節。段落承載說明，清單與表格承載比較及步驟。術語在需要時定義或回指。長度依內容與讀者任務決定，避免以固定行數代替品質判斷。

同批更新受行為變更影響的文件。重整可依 [rewrite](../../rewrite/SKILL.md) 保存原稿。一般修正可直接編輯，既有標題仍適用時保留。文件檢查依專案設定執行。

必要的設計理由記錄背景、選擇、取捨及證據。被取代時更新有效來源，歷史交版本管理。機密及本機私有配置放適當的受保護位置。

## 可選範本

- [INTERVIEW](INTERVIEW.md)：記錄需求對齊與未決事項。
- [AGENTS](AGENTS.md)：記錄持續適用的操作方法。
- [ROADMAP](ROADMAP.md)：記錄已採用方向及待完成計畫。

範本欄位可依專案修改。代理指引與路線文件依 [框架布局](../references/MECHANISMS.md#本機工作區布局) 管理。其他正式文件遵循專案慣例。

## 核對

以讀者任務檢查文件：能否找到入口、完成操作、理解結果及處理失敗。格式檢查只證明涵蓋的形式條件，正確性仍須核對來源與實際行為。揭露未執行的操作或無法核實的內容。
