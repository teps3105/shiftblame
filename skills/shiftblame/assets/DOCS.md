# 文件品質

文件為讀者要完成的工作而寫。repo 根 README 是入口；模組 README、API 指南、操作說明與設計理由依專案慣例存在。每個事實有唯一權威位置，其他文件回指；說明實際行為、適用條件、必要命令及可核對來源，設計理由有決策或證據支持時保留，主觀假設標明假設。程式碼、路徑、簽章與行號在有助理解或操作時引用必要片段。

## 文件分型

每種文件一種職能，位置與規範隨職能而定——一個職能一份文件，不混寫：

| 型別 | 位置 | 性質與規範核心 |
| --- | --- | --- |
| 治理文件 | `.shiftblame/<slug>/` | 契約型：G 檔與 SLUG，定義區、封存與回指承載可追溯性，寫法僅限流程文件。 |
| 歸檔治理文件 | `.shiftblame/archive/<slug>/` | 契約型歸檔：收尾後凍結的 G 檔與 SLUG，供對照。 |
| 規範文件 SOP | `.shiftblame/SOP.md` | 參照型：持續適用的環境、入口與操作方法，欄位制，每項掛命令、路徑或可觀察結果。 |
| 路線文件 ROADMAP | `.shiftblame/ROADMAP.md` | 參照型：已採用方向、限制與未完成計畫，建議與已批准分開。 |
| 專案文件 | `docs/` | 參照型：編號文件集，索引為入口，每份一種讀者任務。 |
| 形象文件 README | 根目錄，全專案唯一（子專案的 README 不在根目錄） | 參照型：專案是什麼、給誰用、怎麼開始。 |

治理文件的累積式寫法不得套用到參照型文件——治理語彙（時點、G 檔、sb 命令、`.shiftblame/` 路徑）入參照型文件即違例，確需引用以 frontmatter `jargon-allow` 聲明。SOP 與 ROADMAP 不是治理文件：治理語意不擴張到它們，住 `.shiftblame/` 是位置約定，不是身分改變。參照型文件當下自洽、以整檔重寫維護、重點前置；編修一律走 [rewrite](../../rewrite/SKILL.md) 的機械流程，主要承載在每次提交前（提交閘），不在收尾才查。

README 的形象職能是入口：讓讀者很快知道專案是什麼、給誰用、怎麼開始。它不是規範文件（操作規範歸 SOP）、不是治理文件（流程與授權歸 G 檔與 SLUG）、也不是專案文件（細節歸 docs/）——越界內容以回指交給權威位置，README 只留形象與入口。根目錄或 docs/ 出現 SOP.md／ROADMAP.md 是位置違例：正確位置的檔案才有資格被檢查。

## 撰寫規範

1. **同構合併**：多份檔案呈現相同結構或主題時合併為單一文件，以大節區分；不為排版偏好拆檔。
2. **當下自洽**：寫當下有效內容，歷史與過程交 git 與 tmp。產品文件不混入歷史敘事與治理暗語——治理詞彙的定義見 [GLOSSARY](../references/GLOSSARY.md)，產品術語在專案正式文件首次出現即定義或給回指；讀者離開當前對話也要能理解。佔位符殘留（「（填…）」、TODO、待補）視為文件未完成。
3. **單一描述**：同一機制只有一個權威描述位置，其他位置回指；不以多種角度複述同一機制造成多種解釋。
4. **人可讀**：段落承載敘事，清單與表格承載枚舉；不以巢狀結構、粗體與標題層層轟炸替代說明，一段說完一件事。每句指出主體與可觀察動作或事實——寫不出主體、動作或觀察方式的句子是空話，刪或改。
5. **重點前置**：每份參照型文件 H1 之後、第一個標題之前，以一段當下摘要開頭（現況、用途、入口）。
6. **docs/ 編號**：採用 docs/ 文件集時，除 `索引.md` 外全部編號——頂層大節為 `N-名稱/`，節內文件為 `N.M-名稱.md`；編號最多兩層，不得出現 `N.M.K`；非 md 檔不入 docs/。每份文件的 H1 為可讀標題，若帶編號須與檔名一致。
7. **全域重排**：插入或移除大節、文件後重新編號並保持連續——重構是全域重排，不是局部補丁；索引與回指同批更新。
8. **長度預算**：單檔超過 300 可見行須以 frontmatter `length-allow: true` 聲明權威長參照；否則同構合併或拆分。
9. **型別分離**：每份文件或大節只服務一種讀者任務（學習、操作、查閱、理解）。操作與查閱節不摻論述；抽象論述集中於標明的「理由」節，且該節須含背景、選擇、原因、來源四要素，一段即可。
10. **證據配額**：操作與驗證性內容必須掛得住具體值——命令、路徑、數值或預期輸出。連續多句純散文且零具體內容的段落是黑話的宿主：追問這段的命令、觸發條件與預期結果，填不出的內容刪除或移 tmp。腔調問題在結構上解決，不以換詞解決。

反覆混淆的領域詞彙在既有正式文件設唯一詞彙區，記簡短定義及容易混淆的概念，確有需要才獨立成檔；用具體情境與程式碼交叉核對，已知現況和期望結果分開。

當決策同時難以逆轉、缺少背景會令人困惑、且存在真實取捨時，保存當下有效的決策理由：背景、選擇、原因及必要來源，一段即可。長期理由依 repo 慣例留設計文件或 ADR，當次 G1 回指；尚未採用的提案保留提案身分。被取代時更新有效權威與引用，歷史交給 git 或既有治理紀錄。

同批更新受本次行為變更影響的文件；實質內容變更（功能、行為、方向）提交前先整檔重寫，錯字與路徑等小幅修正可直接編輯。機密、本機私有配置及內部拓撲保留在適當的受保護位置；工作過程與診斷放 .shiftblame/tmp/，正式文件寫當下有效內容。

## 驗證

`sb rewrite` 機械檢查：位置違例（根目錄／docs/ 的 SOP.md 與 ROADMAP.md、根目錄 README 大小寫變體並存）、docs/ 結構（編號、層級、索引對帳、結構零變化）與可讀性信號（重點前置、長度預算、治理暗語、純散文段、佔位符殘留）——涵蓋 README、docs/ 與 `.shiftblame/SOP.md`、`.shiftblame/ROADMAP.md`；豁免以 frontmatter 聲明（`lead-allow`／`length-allow`／`jargon-allow`）。提交閘（`sb commitmsg` 於 staged 動到參照型文件時；staged 的 SOP／ROADMAP 任一位置皆擋）與收尾閘（`sb end` 於 slug 期間動過文件時）執行同一判準——未過檔先重寫。

機械檢查只證明結構形式：可理解性、單一描述、描述與實況一致，由 rewrite 回讀與時點審查以「離開當前對話的讀者」身分核對。方法大幅調整時，以代表任務檢查應觸發與不應觸發的情境；刪改規則依實際問題及執行結果，避免把單次成功宣稱為普遍效益。
