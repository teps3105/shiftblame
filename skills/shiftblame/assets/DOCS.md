# 文件品質

文件為讀者要完成的工作而寫。repo 根 README 是入口；模組 README、API 指南、操作說明與設計理由依專案慣例存在。每個事實有唯一權威位置，其他文件回指；說明實際行為、適用條件、必要命令及可核對來源，設計理由有決策或證據支持時保留，主觀假設標明假設。程式碼、路徑、簽章與行號在有助理解或操作時引用必要片段。

## 撰寫規範

1. **同構合併**：多份檔案呈現相同結構或主題時合併為單一文件，以大節區分；不為排版偏好拆檔。
2. **當下自洽**：寫當下有效內容，歷史與過程交 git 與 tmp。產品文件不混入歷史敘事與治理暗語——治理詞彙的定義見 [GLOSSARY](../references/GLOSSARY.md)，產品術語在專案正式文件首次出現即定義或給回指；讀者離開當前對話也要能理解。
3. **單一描述**：同一機制只有一個權威描述位置，其他位置回指；不以多種角度複述同一機制造成多種解釋。
4. **人可讀**：段落承載敘事，清單與表格承載枚舉；不以巢狀結構、粗體與標題層層轟炸替代說明，一段說完一件事。
5. **docs/ 編號**：採用 docs/ 文件集時，除 `索引.md` 外全部編號——頂層大節為 `N-名稱/`，節內文件為 `N.M-名稱.md`；編號最多兩層，不得出現 `N.M.K`；非 md 檔不入 docs/。每份文件的 H1 為可讀標題，若帶編號須與檔名一致。結構以 `sb docs` 機械檢查。
6. **全域重排**：插入或移除大節、文件後重新編號並保持連續——重構是全域重排，不是局部補丁；索引與回指同批更新。
7. **Obsidian 顯示**：`sb vault` 以 repo 根為 vault，顯示規定集＝docs/＋README.md，配置後讀回自驗，爾後以 `sb vault verify` 複查；機制細節見 [MECHANISMS](../references/MECHANISMS.md)。

反覆混淆的領域詞彙在既有正式文件設唯一詞彙區，記簡短定義及容易混淆的概念，確有需要才獨立成檔；用具體情境與程式碼交叉核對，已知現況和期望結果分開。

當決策同時難以逆轉、缺少背景會令人困惑、且存在真實取捨時，保存當下有效的決策理由：背景、選擇、原因及必要來源，一段即可。長期理由依 repo 慣例留設計文件或 ADR，當次 G1 回指；尚未採用的提案保留提案身分。被取代時更新有效權威與引用，歷史交給 git 或既有治理紀錄。

同批更新受本次行為變更影響的文件。機密、本機私有配置及內部拓撲保留在適當的受保護位置；工作過程與診斷放 .shiftblame/tmp/，正式文件寫當下有效內容。

## 驗證

驗證讀者能否依文件完成目標、引用是否有效、描述與實況是否一致；方法大幅調整時，以代表任務檢查應觸發與不應觸發的情境。`sb docs` 只證明結構形式——可理解性、單一描述與暗語排除由 rewrite 的回讀與時點審查以「離開當前對話的讀者」身分核對；機械格式檢查不能證明代理行為。刪改規則依實際問題及執行結果，避免把單次成功宣稱為普遍效益。
