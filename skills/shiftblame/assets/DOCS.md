# DOCS — 專案系統文件的寫法判準

> 本檔規範專案 `docs/` 系統文件的**寫法品質**，不改變流程與寫入授權（流程看 SKILL §0 主圖，授權看 SKILL §2、§5、§6）。判準提煉自 `dnd-prototype` `system-documentation-audit` 002 的三輪修正（rev1 code 導覽作廢、rev2 揣測意圖作廢、rev3 純實作陳述 PASS）。

## 0. 適用範圍（硬性釘死）

| 範圍 | 判定 |
|------|------|
| **適用** | 專案 `docs/` 目錄下的系統文件（描述 codebase 各系統實際運作的文件） |
| **MUST NOT 套用** | `.shiftblame/` 管理文件（G1／G2／G3／SOP／ROADMAP／SLUG）——寫 Why、技術理由、需求動機是這些文件的法定職責（SKILL §4、SKILL §10、references/*.md）。把本規範的反向詞清單套到管理文件會誤殺其核心內容。 |
| **MUST NOT 套用** | 專案 `.shiftblame/SOP.md`——SOP 依其模板（`assets/SOP.md` §1.3）保留真實檔案路徑、行號、命令、URL、埠號、版本與 `path:line` 是其法定職責，與本檔 §2 R3 的「無 code 導覽特徵」**有意為之地分工**：SOP 寫「怎麼跑／配置在哪／入口是什麼」，docs/ 寫「系統實際怎麼運作」。 |

本檔的 grep 反向詞清單（§2）只在 `docs/` 執行；MUST NOT 對 `.shiftblame/` 或 SOP 執行。

## 1. 角色落點

| 項目 | 說明 |
|------|------|
| 本檔性質 | 文件**寫法品質**的通用判準（中央尺），類似 `assets/` 的中央模板 |
| 與 G1 的關係 | 單次文件化工作的**驗收仍由 AUDITOR 主導的 G1 承載**（references/AUDITOR.md）；本規範 MAY 被 G1 引用為驗收依據，MUST NOT 取代 G1。G1 仍只由 AUDITOR 改寫。 |
| 與 SKILL §5 的關係 | 本規範規範「**怎麼寫才正確**」（品質）；§5「既有 `docs/` 預設不得修改，除非老闆明確授權」規範「**誰能改、何時能改**」（寫入權）。兩者正交。本規範**不授予寫入權**——改 `docs/` 仍須走 §5 的老闆授權，且實際寫入由主對話 SECRETARY 執行（唯一 repo 開發執行者）。 |
| 本檔修改路由 | 本檔是框架檔，修改走「框架演化」路由（SKILL §0、§6），不開 slug、先揭露方案取得授權。 |

## 2. 寫法判準（MUST／MUST NOT）

### R1 只描述真實實作

| | 內容 |
|---|------|
| MUST | 陳述系統**現在實際**怎麼運作：操作→行為、條件→結果。與 codebase 一致。 |
| MUST NOT | 寫成 code 的複製品或劣化導覽（見 R3）。 |
| 正例 | `玩家與輸入.md`「點擊可通行且有互動物的格：該物有開關屬性（門）→ 走至其四鄰任一可達格；否則（如樓梯）→ 直接走進該格。」 |

### R2 不揣測意圖

| | 內容 |
|---|------|
| MUST | 只描述「系統做什麼」；不寫「為什麼這樣設計」「玩家會感知什麼」。意圖、感受、動機是虛構且無法驗證，會誤導讀者。 |
| MUST NOT | 出現動機／感受／理由詞，或設計意圖段落。 |
| 反向詞（grep） | `為了`、`讓玩家`、`避免`、`調和`、`用以`、`旨在`、`以便`、`希望`、`確保`、`保證`、`會感覺`、`爽快`、`挫敗`、`玩家感知`、`流暢`（作主觀評價時）、`為什麼設計`、`為什麼這樣設計`、`設計理由`、`設計意圖` |
| 反例 | rev2（作廢）含「玩家感知／為什麼這樣設計」段落、「調和」「避免挫敗」「爽快」等詞；活體殘留反例見 `戰鬥/戰鬥機制.md`「此契約**調和**『視覺流暢』與『回合制邏輯』」。 |

### R3 無 code 導覽特徵

| | 內容 |
|---|------|
| MUST NOT | 把文件寫成 code 的劣化複製品——code 一改文件即過時，且不比直接讀 code 多任何價值。 |
| MUST NOT（grep 特徵） | 行號引用 `:[0-9]`／`行 [0-9]`／`:line`；簽章與內部名 `func `／`enum `／`signal `／`var `／`const `／`await `／`_` 開頭私有成員；常數賦值列舉 `= [0-9]`／`= true`／`= false`／`（固定）`；檔案路徑作敘事主軸 `.gd`／`src/...`／以檔名命名章節。 |
| 界線 | 偶爾為查證而引用檔名「MAY」，但拿檔名當章節骨架或敘事主軸 MUST NOT。 |
| 反例 | rev1（作廢）的 `### Facing（\`src/entities/facing.gd\`）`、`**數值刷新（\`:169-201\`）**`、表格欄「false→**true**」、`show_message`／`refresh PlayerStatsPanelUI` 當主語。 |
| 與 SOP 分工 | R3 的「無 code 導覽」僅規範 `docs/` 敘事體；SOP 依其模板保留真實路徑／命令／行號是法定職責，不在本判準拘束範圍（見 §0）。 |

### R4 各領域覆蓋

| | 內容 |
|---|------|
| MUST | codebase 每個系統有對應文件；有入口總覽檔，用「各系統一句話實際行為 + 文件清單」串接，無 API 表、無設計願景。 |
| MUST NOT | 缺領域；入口檔寫成 API 表或設計願景。 |
| 正例 | `系統架構.md`「各系統實際行為」表 + 「文件清單」表。 |

## 3. 隱性判準（六份範本一致做到、與 R1-R4 同源）

| 判準 | MUST | MUST NOT |
|------|------|----------|
| **數字保留** | 描述行為所需的數字 MUST 保留（如「25×18」「三層」「6×4 網格」「48px」「正交步成本 1.0、對角步成本 √2」「≤34% 紅」）——這些是實作事實。 | MUST NOT 變成常數定義列舉（如 `MAP_W = 25`、`const GRID = 6`），那屬 R3 code 導覽。界線：「描述行為的量」保留，「程式常數定義」禁止。 |
| **表格化** | 可比較的狀態／屬性／分類用表格（如互動物行為表、敵人五狀態表、系統總覽表）。 | 操作流程用條列（如點擊分類、移動規則）；不得為套表格而把流程壓成無操作價值的概括句。 |
| **跨文件引用** | 同一規則只在一處定義，他處用相對路徑指標（如「戰鬥規則見 `戰鬥/戰鬥機制.md`」）。 | MUST NOT 在多處重複定義同一規則造成雙重真相。 |
| **章節標題** | 用行為／規則／領域名命名（如「察覺條件」「點擊分類（操作→結果）」「五狀態與各自行為」）。 | MUST NOT 用檔名／類別名／函式名命名章節（如 `### Facing（\`src/entities/facing.gd\`）`）。 |
| **測試／配置歸屬** | `docs/` 描述「測試驗證了哪些行為」「覆蓋哪些規則」（如「21 個戰鬥 smoke 驗察覺／進戰／先攻」）。 | 具體命令（`npx playwright test`）、配置檔路徑（`export_presets.cfg`）、版本值屬 SOP 職責（見 §0 與 SOP §1.1／§1.3），不重複寫入 docs/。 |

## 4. 可驗證方法（grep）

| 判準 | grep 指令（於 `docs/` 執行） | 通過條件 |
|------|------------------------------|----------|
| R2 不揣測意圖 | `grep -rnE "為了\|讓玩家\|避免\|調和\|用以\|旨在\|以便\|希望\|確保\|保證\|會感覺\|爽快\|挫敗\|玩家感知\|為什麼(這樣)?設計\|設計(理由\|意圖)" docs/` | 0 命中 |
| R3 無 code 導覽 | `grep -rnE ":[0-9]+\|func \|enum \|signal \|await \|\.gd" docs/` | 0 命中（必要時補 `= (true\|false\|[0-9])` 排除常數列舉） |
| R4 各領域覆蓋 | `ls docs/` 對照入口總覽檔的文件清單 | 齊全且一致 |

grep 命中即判違規；例外須在文件內註明理由（如引用外部規格的固定名稱）。AUDITOR 複核時 MAY 直接以本表查核。

## 5. 邊界案例（灰色地帶判定）

| 情境 | 可以 | 不可以 | 判準 |
|------|------|--------|------|
| 維度數字 | 「地圖 25×18」「三層迷霧」 | `MAP_W = 25`、`const LAYERS = 3` | 數字保留原則（§3） |
| 檔名引用 | 「屍體互動發放掉落物（見 `實體與介面.md`）」 | `### Corpse（\`corpse.gd\`）`：首互動發 loot | 章節標題用行為名（§3） |
| 測試描述 | 「39 個 headless smoke 驗戰鬥／移動／AI 規則」 | `npx playwright test`、`scripts/ci/run_smoke.sh`（屬 SOP） | 測試／配置歸屬（§3） |
| 動機偽裝 | 「裝備寫回戰鬥數值」（陳述事實） | 「為了確保戰鬥一致性，裝備寫回數值」 | R2 不揣測意圖 |

## 6. 與其他文件的關係

- **SKILL §5**：規範 `docs/` 的**寫入權**（預設不得改，須授權）；本檔規範**寫法品質**。正交，不衝突。
- **SKILL §8**：框架檔結構含本檔（`skills/shiftblame/assets/DOCS.md`）。
- **SKILL §3**：開發後 AUDITOR 對照 G1 驗收；文件化工作裡 AUDITOR MAY 引用本檔作為 docs/ 驗收尺。
- **assets/SOP.md §1.3**：SOP 保留真實路徑／命令／行號是其職責，與本檔 R3 分工（見 §0）。
- **references/AUDITOR.md**：本檔不取代 AUDITOR 主導的 G1 驗收。
