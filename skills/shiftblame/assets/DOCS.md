# 文件品質

依讀者要完成的工作組織文件。repo 根 README 提供入口；模組 README、API 指南、操作說明與設計理由可依專案慣例存在。每個事實有明確權威位置，其他文件引用，避免矛盾的複製。

說明實際行為、適用條件、必要命令及可核對來源。設計理由有決策或證據支持時保留；主觀假設標明假設。程式碼、路徑、簽章與行號在有助理解或操作時引用必要片段。

方法文件的入口說清楚何種情境要讀，正文區分操作與按需參考，每個步驟用可觀察條件說明何時足夠。所有情境都需要的內容留入口，特定分支才用的細節放有明確觸發的參考；先改善入口措辭，再依實際漏用或篇幅決定是否拆檔。能從設定、程式或命令直接取得的事實，優先引用來源；定義、限制與例子放在同一主題附近。

反覆混淆的領域詞彙在既有正式文件設唯一詞彙區，記簡短定義及容易混淆的概念，確有需要才獨立成檔。用具體情境與程式碼交叉核對，已知現況和期望結果分開；治理詞彙沿用 [GLOSSARY](../references/GLOSSARY.md)。

當決策同時難以逆轉、缺少背景會令人困惑、且存在真實取捨時，保存當下有效的決策理由：背景、選擇、原因及必要來源，一段即可。長期理由依 repo 慣例留設計文件或 ADR，當次 G2 回指；尚未採用的提案保留提案身分。被取代時更新有效權威與引用，歷史交給 git 或既有治理紀錄。

同批更新受本次行為變更影響的文件。機密、本機私有配置及內部拓撲保留在適當的受保護位置。工作過程與診斷放 .shiftblame/tmp/，正式文件寫當下有效內容。

驗證讀者能否依文件完成目標、引用是否有效、描述與實況是否一致。方法大幅調整時，以代表任務檢查應觸發與不應觸發的情境、完整交付、錯誤及不必要停等；機械格式檢查不能證明代理行為。刪改規則依實際問題及執行結果，避免把單次成功宣稱為普遍效益。
