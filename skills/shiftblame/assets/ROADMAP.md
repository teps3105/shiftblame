# ROADMAP — 需求索引

> 用白話記錄產品想成為什麼、不能偏到哪裡，以及接下來想做什麼。它不是技術設計、排程表、驗收報告或工作日誌；需求不必先被阻塞才能列入。

## 1. 產品目標與固定邊界

只寫老闆已採用的產品方向、長期邊界與不能偏離的產品結果；句子要像老闆在說產品，不要改寫成 Agent 的術語或方案。

- **（目標／邊界 1）** — 說明：（填）
- **（目標／邊界 2）** — 說明：（填）

## 2. 待開發計畫索引

每個計畫只代表一個老闆想做、尚未完成的產品計畫；忠實反映老闆原意，不寫技術解法。**排列位置即優先度**——越上面的計畫優先度越高；排序文字（序號、「優先級：高／中／低」「先做」「順序」等明示排序語意）保持零出現，優先度只靠排列傳達。調整排列由秘書依老闆指示直接重排。

- **（計畫名）** — 要做什麼：（填）
- **（計畫名）** — 要做什麼：（填）

## 3. 准入與清理

- **寫入者**：秘書（唯一）——ROADMAP 的修改權僅屬秘書。
- **新增／修改產品意圖**：MUST 有老闆明確授權。秘書 忠實記錄，白話，不改寫成 Agent 術語。路由提議只在對話回報；ROADMAP 內容僅承載老闆授權的產品意圖。
- **隨碼更新（same-commit）**：完成項移除與剩餘方向修正隨造成該結果的程式碼變更同批（同 commit）完成——已完成→移除；部分完成→改寫成剩餘方向；已失效→移除。**不需另行授權**（忠實對照屬維護既有文件，兩層文件模型 SKILL §1.7）。
- **內容歸屬**：G1 需求／驗收、G2 技術、G3 步驟、commit、測試輸出、檔案清單、排程、優先級、估算、負責人、進度、討論、嘗試紀錄、Agent 行為、SKILL／references 流程規範副本一律留在各自載體。**排列位置不在此限**：§2 計畫索引的排列順序表達優先度（越上面越高）——排序語意以排列為唯一載體（序號、`優先級`、`先做`、`順序`等文字形式保持零出現）。

**規則要點**：

- 新增或修改產品意圖 MUST 有老闆明確授權；秘書 的記錄僅限忠實轉寫老闆意圖，自身建議只在對話回報。隨碼更新的完成項移除與剩餘方向修正屬事實對照，歸類為維護既有文件。
- 產品目標、固定邊界與待開發計畫可以在目前可實作或被阻塞時列入；ROADMAP 不要求填阻塞證據、解阻塞計畫或進度狀態。
- 正文 MUST 使用白話；專有名詞僅在老闆原意本來就需要時使用——需求表述保持老闆語言（`Given／When／Then`、API、模組、驗收碼或工作拆解屬 G1／G2 載體）。
- 新增產品目標、改變產品邊界、取消尚未完成的需求或把剩餘方向擴張成新需求，仍須老闆明確授權；完成項的移除與剩餘方向的忠實修正隨程式碼變更同批完成，保持維護既有文件的授權位階。
- 路由提議只在對話回報；`<slug>`／`<ms>` 由老闆決定。
- ROADMAP 的寫入權僅屬秘書。收尾歸檔只移動當下層工作文件（SKILL §1.7.2）——永續層更新已隨程式碼同批完成，收尾本身零文件改寫、零新增產品意圖授權。
