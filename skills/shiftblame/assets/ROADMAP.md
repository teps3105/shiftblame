# ROADMAP — 需求索引

> 用白話記錄產品想成為什麼、不能偏到哪裡，以及接下來想做什麼。它不是技術設計、排程表、驗收報告或工作日誌；需求不必先被阻塞才能列入。

## 1. 產品目標與固定邊界

只寫老闆已採用的產品方向、長期邊界與不能偏離的產品結果；句子要像老闆在說產品，不要改寫成 Agent 的術語或方案。

- **（目標／邊界 1）** — 說明：（填）
- **（目標／邊界 2）** — 說明：（填）

## 2. 待開發計畫索引

每個計畫只代表一個老闆想做、尚未完成的產品計畫；忠實反映老闆原意，不寫技術解法。**排列位置即優先度**——越上面的計畫優先度越高；但**禁止任何序號、順序語意**（不得編號、不得寫「優先級：高／中／低」「先做」「順序」等明示排序文字），優先度只靠排列傳達。調整排列用 `sb-roadmap`。

- **（計畫名）** — 要做什麼：（填）
- **（計畫名）** — 要做什麼：（填）

## 3. 准入與清理

- **寫入者**：秘書（唯一）。其他角色 MUST NOT 修改 ROADMAP。
- **新增／修改產品意圖**：MUST 有老闆明確授權。秘書 忠實記錄，白話，不改寫成 Agent 術語。路由提議只能在對話回報，不得寫入 ROADMAP。
- **收尾保鮮**（slug 結束時）：秘書 重讀 codebase＋slug 文件＋證據。已完成→移除（不留 `DONE`／`IN PROGRESS`）；部分完成→改寫成剩餘方向；已不存在→移除；仍有效→保留。**不需另行授權**（忠實改寫不屬新增產品意圖）。
- **MUST NOT 寫入**：G1 需求／驗收、G2 技術、G3 步驟、commit、測試輸出、檔案清單、排程、優先級、估算、負責人、進度、討論、嘗試紀錄、Agent 行為、SKILL／references 流程規範副本。**排列位置不在此限**：§2 計畫索引的排列順序表達優先度（越上面越高），但優先度不得以任何文字（序號、`優先級`、`先做`、`順序`）記錄——排列是唯一排序載體。

**規則要點**：

- 新增或修改產品意圖 MUST 有老闆明確授權；秘書 只能忠實記錄，不能把自己的建議寫成老闆意圖。收尾保鮮造成的完成項移除與剩餘方向改寫不屬於新增產品意圖。
- 產品目標、固定邊界與待開發計畫可以在目前可實作或被阻塞時列入；ROADMAP 不要求填阻塞證據、解阻塞計畫或進度狀態。
- 正文 MUST 使用白話；專有名詞只在老闆原意本來就需要時使用，不能把需求改寫成 `Given／When／Then`、API、模組、驗收碼或工作拆解。
- 新增產品目標、改變產品邊界、取消尚未完成的需求或把剩餘方向擴張成新需求，仍須老闆明確授權；完成項的移除與剩餘方向的忠實改寫是收尾保鮮，不需另行授權。
- 路由提議只能在對話回報，不得寫入 ROADMAP；`<slug>`／`<ms>` 仍只由老闆決定。
- ROADMAP 只能由 秘書 寫入；其他角色 MUST NOT 修改 ROADMAP。PASS、收尾與歸檔會觸發既定的文件保鮮動作，但不會自動授權新增產品意圖。
