# 實作階段 — 依 G2 寫實作碼＝G2 的落地（執行層 · 主對話承載）

> **G2 落地邊（執行層工作段）**。主對話把 G2 技術方案落地為 repo 實作碼並做必要實機驗證。該功能實作完成後由秘書 commit 存檔（先於驗收，建立待驗對象），驗收後再判決通過／返工。

- **產出**：依 G2（research 段）技術方案寫 repo 實作碼＋實機驗證
- **對應**：research 段（G2）——同面向的定義（G2 技術）↔ 落地（實作碼）
- **時序制約**：寫出的實作要能通過測試階段定義的測試（由驗收階段跑）
- **不做**：不寫測試碼（測試階段職責）、不跑驗收（驗收階段職責）、不判決通過/返工（判決在驗收後，讀驗收產出）

> 實作階段（執行層）高亮。寫的實作要能過測試階段的測試（由驗收階段跑）；同面向對應research 段（G2 技術）。二者皆由主對話承載。

### build 段的工作邊界

build 段讀完整呼叫路徑、重用既有能力並修正共用根因；需要時反覆做實機驗證。**回指 G2（落地邊義務）**：實作對照 G2 技術方案——CONFORMS 的技術細節直接落地；偏離 G2 處（實作期發現更適解）收斸寫入 G2 回指區（全形｜行格式，過程落 tmp）（單調細化語義，SKILL §1.4），G2 的改寫權在 research 段。主對話保留 G1／G2／G3 與已定稿測試脈絡；若根因、API、架構或證據解讀仍無法可靠裁定，依 SKILL §3 必須立即取得一次外部子代理唯讀技術意見，複核後自行承擔技術方案裁定。

### 實作碼的產出與紀律

秘書在實作階段寫 repo 實作碼，依 G2 技術方案落地。執行產出結構化整理後存 `<repo>/.shiftblame/tmp/`（自由傾倒區：變更摘要、實機驗證方式與結果——文件層義務，閘門不讀）；G2 定義區不寫（research 段決策結論）；回指區由 build 段收斸偏離記錄。

**與測試／驗收階段的時序制約**（SKILL §3）：實作階段寫的實作碼是被測對象——要能通過測試階段定義的「過」（由驗收階段對秘書存檔的 commit 跑出來）。實作階段不自己定義測試、不自己跑驗收，避免「自己寫自己驗」。**測試先行**：測試階段先寫測試（此時紅燈），實作階段才寫實作碼讓測試轉綠——實作依測試階段已定義的「過」為目標實作，不是先寫碼再補測試。

**文件先行（永續層義務）**：build 段的行為變更，永續層文件（docs/、SOP、ROADMAP、README）先行改到目標狀態，實作碼依文件撰寫——same-commit 承載批，順序固定：文件在前、碼隨後（與測試先行同族；G 檔與測試碼不在本原則客體內）。執行中發現不一致按歸屬處置（限 build 段）：永續層描述層過時／錯誤→same-commit 修正文件再繼續；G2／G3 與實作現實不符→偏離記 G2 回指區或回 intent 細化；需求／驗收語義出入→SKILL §1.4.1 修約——永續層承載的語義一律經修約。

**commit 時點＝實作完成即存檔**：實作階段完成該功能實作碼後，由秘書**立即 commit 存檔**（獨佔；commit＝存檔——建立不可變的待驗對象，先於驗收，不是驗收通過的完成印記），驗收階段對該存檔跑 CI。實作 commit 於功能完成時存檔；返工修復後疊加新存檔再驗。存檔走 `sb commitmsg` 流程（精準 add，功能＝commit 單位——每次 commit 即該功能的完整檔案集）。

**回頭自由重修**：一切變更走八段（test→build→verify），無繞過路徑；已 commit 的返工疊加新 commit。
