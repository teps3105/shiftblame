# 開發階段 — 寫實作碼，對應研究階段（執行層 · 主對話承載）

> **執行層工作階段**。**同面向對應研究階段（G2 技術方案）**：把 G2 定義的技術方案落地為 repo 實作碼。**承載：主對話**（非子代理）——開發階段反覆實機驗證行為，涉及對外視窗控制，控制權不可外流（SKILL §3 承載歸屬原則）。可寫 repo 實作碼，但**不可 commit**；commit 與合格/返工判決由秘書獨佔。秘書在開發階段親自執行。

- **產出**：依 G2（研究階段）技術方案寫 repo 實作碼＋實機驗證
- **對應**：研究階段（G2）——同面向的定義層（G2 技術）↔ 執行層（實作碼）
- **時序制約**：寫出的實作要能通過測試階段定義的測試（由驗收階段跑）
- **不做**：不寫測試碼（測試階段職責）、不跑驗收（驗收階段職責）、不 commit、不判決合格/返工

> 開發階段（執行層）高亮。寫的實作要能過測試階段的測試（由驗收階段跑）；同面向對應研究階段（G2 技術）。二者皆由主對話承載。

### 承載歸屬：為何開發階段是主對話

開發階段高頻需要**反覆實機驗證行為**——改一行、跑一次、看行為、再改。這涉及對外視窗控制（有副作用、難重現、session 敏感），依 SKILL §3 承載歸屬原則，控制權必須在主對話。因此整個開發階段由秘書親自執行，不派子代理。

**認知探索外包**：開發階段的海量無副作用認知工作（讀既有 codebase 理解結構、grep 找模式、查 API 用法）由秘書派發**唯讀探索子代理**外包——子代理產出結論存 `tmp/`，秘書讀取後決策。**判準：子代理能獨立完成且無副作用 → 外包；需要對外視窗控制 → 留主對話。**

### 實作碼的產出與紀律

秘書在開發階段寫 repo 實作碼，依 G2 技術方案落地。執行產出**結構化整理後存 `.shiftblame/tmp/`**（變更摘要：改了哪些檔、做了什麼、實際用了什麼技術、與 G2 分析的出入、codebase 事實），**不寫入 G2**——G2 保持乾淨只放研究階段的決策結論。

**與測試／驗收階段的時序制約**（SKILL §3）：開發階段寫的實作碼是被測對象——要能通過測試階段定義的「過」（由驗收階段跑出來）。開發階段不自己定義測試、不自己跑驗收，避免「自己寫自己驗」。**測試先行**：測試階段先寫測試（此時紅燈），開發階段才寫實作碼讓測試轉綠——開發依測試階段已定義的「過」為目標實作，不是先寫碼再補測試。

**不可 commit**：開發階段完成實作後，變更留在工作區，由秘書讀過測試階段測試報告與驗收階段驗收報告後**判決合格**，才由秘書 commit（獨佔）。MUST NOT 自行 `git add`／`git commit`。

**預設直接修正**：功能未觸發 §1.4 重流程條件時秘書直接寫不派發——實作碼不是每功能必走完整執行層時序，只有行為／介面／多檔／跨層改變或老闆指定才走。對實作的正確性回報如實，不掩飾問題；遇到技術層問題無法突破時如實回報，由秘書判斷是否以研究階段性質派發瓶頸顧問（SKILL §1.4）。
