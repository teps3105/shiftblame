# test 段 — 回指 G3 驗收排程寫測試定義「過」＝G3 的落地邊（實作層）

> **G3 落地邊（實作層工作段）**。 **段靈魂——把故事翻譯成可機械判的證據**：怎麼綠＝驗什麼可觀察行為，為什麼綠＝證明哪個故事；自畫像判準——把實作換掉，測試還守得住故事嗎？守不住即假測試。主對話把 G3 驗收排程可執行化為測試碼（AC-ID 映射回指 G1 驗收項），定義「什麼叫過」。此狀態可寫 repo 測試碼；測試碼隨功能實作同 commit 定稿（git 承擔不可變性），commit 與判決仍由秘書執行。

- **產出**：依 G3 驗收排程（AC-ID 映射至 G1 驗收項）寫 repo 測試碼，定義「過」的條件
- **對應**：plan 段（G3）——G3 閉環的定義（驗收排程）↔ 落地（測試碼＝驗收排程的可執行化）
- **時序制約**：實作層一依 G3 定義當前功能的單點／整合案例及預期結果，由 build 執行；實作層二（收斂期）撰寫本 ms 所需 E2E，由 build 調整環境並執行至綠燈收斂（build 的功能是讓測試綠）
- **邊界**：本段定義與撰寫測試，實作留給 build、AC 判定留給 verify；測試碼隨功能實作同 commit（提交閘承載）

> 測試階段（G3 落地邊）高亮。回指 G3 分層排程定義並撰寫測試；功能測試隨該功能實作同 commit 定稿，E2E 於收斂期撰寫。

測試碼定稿＝隨功能實作同 commit（單功能單提交，由 `sb commitmsg` 格式閘承載——格式驗證＋印章，hooks 於 git commit 驗章焚章——提交僅機械格式面，審核承載於兩時點）。test→build 邊無機械閘（假測試由文件層判準把關——測試真實性屬工作紀律：須有實斷言，git 歷史可稽；抽樣性攻擊由時點 2 對抗承擔）。測試碼保持與開發流程正交（名稱表達被驗行為，檔名、註釋與識別字由專案正式定義即可辨識；框架本身的正式詞彙依 SKILL §5 使用）——測試碼＝G3 驗收排程的可執行化，AC-ID 與測試的映射由 G3 驗收排程承載、回指 G1 驗收項（SKILL §4 驗收鏈、§5）。**註釋紀律**：測試碼註釋只描述被驗行為與測試意圖——輪次、時點、對抗與修復過程屬流程座標，落 `.shiftblame/tmp/` 與 G 檔，與提交訊息同源同判（SKILL §5、§7；`sb commitmsg` 於 staged 新增行掃座標結構樣式兜底）。

主對話在 test 段寫 repo 測試碼；測試清單與 pass 條件的過程紀錄可整理到 `<repo>/.shiftblame/tmp/`（自由傾倒區）；AC→測試檔：映射收斂寫入 G3 回指區（定義區唯 plan 邊寫）。

**測試規模與穩定度成正比**：被測功能的公開契約或行為語義仍在變動（原型期）時，自動化測試只做跟得上迭代節奏的最小驗證——改動後能立即重跑、失敗能快速定位；不為還會重寫或刪除的功能建大型測試套件（過早的設計固化成維護負擔）。契約與語義穩定後，測試投資才擴大到與風險相稱的規模。**架構性風險的探測不隨原型期縮減**：性能、穩定性這類晚期難以返工的問題，早期就用輕量形式驗（本機 profiling、單點量測、即時回饋），系統穩定後才升級為系統化測試；探測面向依實際架構風險認定，探測同樣留執行證據（工具、輸入、觀察到的數據）。**測試與被測行為同生命週期**：功能刪除或語義改變時，對應測試在同一變更中刪除或改寫；重複、失效或已無對應行為的測試發現即移除——測試數量不是資產指標。

**分層撰寫與執行**（SKILL §4、§3）：test 回指 G3 撰寫當前功能必要的單點、整合案例，先寫測試再實作（定義「過」先於實作——測試先行）；重用既有案例，不強制每功能各寫三套。build 執行單點／整合測試，到達接合點時可補寫整合測試；verify 判讀對應證據。收斂期（實作層二）test 撰寫本 ms 所需 E2E、build 調整環境與接線並執行至綠燈收斂——E2E 全綠＋working tree 乾淨是 build→verify 機械推進資格；verify 段執行的是 GWT 驗收劇本。測試碼寫入權屬 `test`＋`build` 段；隨功能同 commit 後內容與通過判準由 git 鎖定。

**測試定義錯誤＝段內修復環**（SKILL §5）：測試碼隨功能同 commit 定稿後由 git 承擔不可變性。測試定義有誤或 G1 修約後需重寫時，附紅燈證據與定義錯誤理由，旗標切段回 test 段重新撰寫（段內不停等、不計返工輪——對抗出口三分類②；老闆新輸入驅動的定義級變更則重走 intent 開新輪（計返工輪））。實作問題只回 build 段重修，測試不動。

**寫了就要是真的（假測試判返工）**——測試是行為契約，寫真實斷言。**消融對照義務**：G3 圈定的關鍵驗收項，其測試含消融對照——移除／停用該功能後紅燈或行為退化；「刪掉也不影響任何驗收」即假測試（既有判準的正面義務化，MECHANISMS §9）。**假測試判準**（命中任一即假）：
- **無斷言**：測試碼沒有真實斷言（assert 等於沒寫、斷言永遠為真、只印 log 不求值）。
- **測實作細節非行為**：斷言綁死實作內部（呼叫次數、私有狀態、實現順序），行為變了測試照過、行為錯了三不知。
- **mock 過度**：mock 掉整個被測對象，測的是 mock 自己不是真實行為。
- **形式化湊數**：為滿足「每功能必測」而寫、與 G1 驗收項無對應、刪掉也不影響任何驗收。
- **證據越級**：把單點／整合綠燈宣稱為完整使用者流程通過。單點可驗證元件輸入輸出，整合可驗證介面及 schema 契約；此類斷言須真實求值且對應其行為邊界，ms E2E 仍需實際入口、操作與結果。
- **規模溢出**：測試或防護手段的精確度超出其宣稱防護目標所需——只防少數可指名風險卻對全部函式做型別推論、副作用或資料內容相關性分析（規模由防護目標推導，SKILL §4）。
- **紅燈放水**：先看實作再寫測試讓它必過，測試失去先行意義。

秘書判決時**檢查測試真實性**：測試對應哪個 G1 AC-ID、斷言是否真實求值。判假即返工（段內修復環回 test 重寫）。若現有證據不足以可靠判斷測試真實性，依 SKILL §5 必須取得一次外部子代理唯讀技術意見，主對話複核後自行承擔測試設計判決。

**與開發／驗收階段的時序制約**（SKILL §5）：test 先寫測試定義實作前預期失敗，build 依判準實作並執行相關單點／整合測試，verify 核對有效證據；收斂期 test 寫 E2E、build 調整環境並執行至綠燈，verify 以 GWT 驗收劇本核對真實行為。尚未執行的案例記為待驗，預期紅燈與實際執行結果分開記錄。

**測試碼 commit 由格式閘承載**：測試碼隨功能實作同 commit（測試碼＋實作碼同 commit——單功能單提交），經 `sb commitmsg`（格式驗證＋印章）→hooks 於 git commit 驗章焚章，由秘書執行。

**段內修復環**：撰寫測試時若發現 G3 的操作、前提或判準無法成立，`sb next plan` 回計畫修正；不能靠弱化斷言或虛構 fixture 讓計畫看似可測。測試自己的定義錯誤在 test 修正，實作問題回 build。技術修正保留 G1 契約、不計返工輪；需求或授權變更依 SKILL §4 走修約。
