# 測試狀態 — 依 G1 寫測試定義「過」＝G1 的落地（執行層）

> **執行層工作狀態**。主對話把 G1 驗收標準可執行化為測試碼，定義「什麼叫過」。此狀態可寫 repo 測試碼但不可 commit；離開時由 `sb lock` 鎖定，commit 與合格／返工判決仍由秘書執行。

- **產出**：依 G1（審計階段）驗收標準寫 repo 測試碼，定義「過」的條件
- **對應**：審計階段（G1）——同面向的定義（G1 驗收標準）↔ 落地（測試碼）
- **時序制約**：定義的「過」要對齊驗收階段依 G1 要驗收的項；不能「自己寫自己跑放水」——跑測試是驗收階段的職責
- **不做**：不寫實作碼（實作階段職責）、不跑測試（驗收階段職責）、不 commit、不判決合格/返工

> 測試階段（執行層）高亮。依 G1 寫測試定義「過」但不跑（跑是驗收階段）；是 G1 面向的落地。

測試定稿時 MUST 跑 `sb lock <測試碼路徑...>`（SKILL §1.8）：測試碼須寫入承接的 G1 `AC-ID`；腳本同時檢查斷言、AC-ID 是否存在於封存 G1，並記錄 G1 hash、ms、AC-ID 與測試碼 sha256。只有斷言而沒有 AC-ID，不得進實作。

主對話在測試狀態寫 repo 測試碼並把測試清單、pass 條件及對應 AC-ID 整理到 `<repo>/.shiftblame/tmp/`；此記錄同時是判決時的鎖定核對基準，不寫入 G3。

**寫測試 vs 跑測試分離**（SKILL §3 的核心制約）：測試階段只**寫**測試、定義「過」，不**跑**測試——跑測試與驗收是驗收階段的職責。這道分離確保測試階段不能「自己寫自己跑放水」：測試階段定義的「過」要被驗收階段實際跑出來，且要對齊驗收階段依 G1 驗收的項。

**測試鎖定——改測試必須回測試狀態**（SKILL §3）：測試碼一經定義「過」即鎖定；實作、驗收或判決當下均不得修改。測試定義有誤或 G1 修約後需重寫時，附紅燈證據與定義錯誤理由，顯式回測試狀態重新定義。實作問題只回實作狀態，測試不動。

**寫了就要是真的（假測試判返工）**——測試不是流程道具，MUST NOT 寫假測試。**假測試判準**（命中任一即假）：
- **無斷言**：測試碼沒有真實斷言（assert 等於沒寫、斷言永遠為真、只印 log 不求值）。
- **測實作細節非行為**：斷言綁死實作內部（呼叫次數、私有狀態、實現順序），行為變了測試照過、行為錯了三不知。
- **mock 過度**：mock 掉整個被測對象，測的是 mock 自己不是真實行為。
- **形式化湊數**：為滿足「每功能必測」而寫、與 G1 驗收項無對應、刪掉也不影響任何驗收。
- **結構冒充需求**：只斷言檔案、字串、節點、schema 或內部排列正確，沒有操作並觀察 G1 使用者結果。
- **紅燈放水**：先看實作再寫測試讓它必過，測試失去先行意義。

秘書判決時**檢查測試真實性**：測試對應哪個 G1 AC-ID、斷言是否真實求值。判假即返工。若現有證據不足以可靠判斷測試真實性，依 SKILL §3 必須取得一次外部子代理唯讀技術意見，主對話複核後自行判決，不得請老闆判斷測試設計；只有 `USER_OBSERVABLE=NO` 的工作可建議 direct，且不能取代 G1 驗收。

**與開發／驗收階段的時序制約**（SKILL §3）：測試階段寫的測試針對實作階段的實作碼；測試階段定義的「過」要對齊驗收階段依 G1 驗收的項。三者形成閉環——測試階段定義「過」、實作階段寫被測實作、驗收階段跑測試驗收「完成」。**測試先行**：測試階段先寫測試（此時紅燈，實作尚未存在），實作階段才依測試階段定義的「過」實作讓測試轉綠——這是執行層的核心紀律，測試階段是落地流程的第一棒。

**不可 commit**：測試階段完成測試碼後，測試碼留在工作區，待同功能實作完成時由秘書一併 commit 存檔（獨佔，建立待驗對象——該功能的測試碼＋實作碼同 commit；commit＝存檔先於驗收）。測試階段 MUST NOT 自行 `git add`／`git commit`。

**預設直接修正**：只限不改變使用者可觀察行為並填 `tmp/direct-change.md`；任何承接 G1 AC-ID 的工作都不得用 direct 繞過測試與驗收。
