# 治理詞彙

詞義有歧義、編修規則或恢復工作時使用。本表是治理概念的定義來源，具體操作引用各方法；產品自身術語留在產品的正式文件。

| 概念 | 定義及易混淆邊界 |
|---|---|
| 直接實作／main 模式 | 沿已授權分支工作、不建立活動 slug 的模式；分支名稱可以不是 main。 |
| slug | 承載同一工作流程與里程碑的具名工作識別；main 交接的 task 名稱不會建立 slug。 |
| 里程碑 | 同一 slug 中可交付並接受使用者判定的一組結果，以 ms 識別。 |
| 時點 1／2／3 | 三個使用者決策時點：時點 1 在 research→plan（審 G1），時點 2 在 quality→build（審 G2），時點 3 在 verify 出口（審驗收結果）；皆為獨立審查加使用者判定。 |
| 責任段 | requirement 至 verify 的目前工作責任（六段圓環）；技術回查不代表需求已改變。 |
| 行為片段 | 一條能從入口到可觀察結果的小工作單位；通常位於同一里程碑內。 |
| AC-ID | 一項可驗收需求的穩定識別，用來對應計畫與證據。 |
| 契約定義區 | G1／G2 中 `## 回指記錄` 之前的定義，分別於時點 1／時點 2 核准後以 hash 封存。 |
| 回指記錄 | 正式定義對應到操作、來源及結果的證據區；不藉更新證據改寫定義。回指為三角循環（G1→G3→G2→G1）：G2 回指 G1、G3 回指 G2、G1 回指 G3（時點 3 審查後閉環）。 |
| 獨立審查 | 由獨立檢閱者取得、有來源及範圍的意見；主代理核對後負責整合。 |
| 產品訪談 | 每個對話開始及開發中需求對齊時，與使用者確認目標、範圍、限制與授權、驗收並寫入本對話紀錄的一輪；對齊需求與授權，不取代時點判定，也不決定技術選擇。新意圖先經訪談對齊，再回 requirement 重入流程。 |
| 使用者判定 | 使用者對需求、授權或正式出口的決定；CLI 旗標僅承接已存在的事實。 |
| 先行研究 | 時點審查與使用者判定期間的非同步準備：唯讀查證、tmp 筆記與隔離原型，並記下判定時的比對基準；不推進、不改受審來源、不提交，結果不構成判定。 |
| 受驗提交 | 時點 3 審查所對應的工作分支末端提交；收尾已留痕時取其工作提交。審查後再提交須重新審查。 |
| 提交印章 | 綁定 repo、訊息與時效的機械提交檢查結果；不等於產品已驗收或可發布。 |
| 行為證據 | 特定輸入、操作及環境下可觀察的實際結果；測試綠燈只涵蓋其斷言。 |
| 交接快照 | 保存時的工作說明及定位事實，用來核對接續；不替代原授權、正式來源或產品備份。 |

術語與使用情境矛盾時，先核對正式來源及實作，依已授權目標釐清再更新相關引用。泛用程式概念不必加入本表。
