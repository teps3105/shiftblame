# 獨立檢閱

審計者對受審 repo 唯讀；問題重現限於隔離暫存工作區。任務帶入必要範圍、材料及驗證限制，避免完整複製不相關的標準清單。

時點 1 檢查 G1（需求與研究）是否忠於使用者、邊界與驗收是否具體且有據；時點 2 檢查 G2（計畫與品質安排）可執行、可驗收且與 G1 對應；時點 3 檢查真實結果、證據適用性、漏驗及未處理的重要缺陷。其他技術檢閱依風險或證據缺口使用。

審查簡報固定比較基準、受審提交及實際差異範圍，附需求與證據來源；進行中的工作也包含 staged、未 staged 及相關未追蹤內容。記錄未能讀取或未執行的範圍，避免只看 HEAD 而漏掉工作樹。判定前的先行研究筆記不放入簡報，審查只針對受審內容。

## 先行研究

時點審查與使用者判定期間可非同步先行研究，縮短等待：以唯讀查證、外部查證、.shiftblame/tmp/ 筆記及隔離原型處理之後確定會用到的問題。不推進責任段、不改受審定義區或受驗來源、不提交，也不延後判定；審查結果與待判定內容照常即時交給使用者。

筆記開頭記下 sb state 印出的比對基準：時點 1 為 G1 定義區 hash，時點 2 為 G2 定義區 hash，時點 3 為受驗提交（工作分支末端）。判定後先核對基準與判定結果——未變且未改需求時沿用，有變更只重查受影響部分。發現會改變需求或驗收時告知使用者；判定前的研究結果不提供給審查者，以免影響獨立審查。

## 分軸

實作與驗收檢閱分開回答兩個問題：

- **需求符合度**：逐項對照 G1 或直接實作的已授權需求，找出缺漏、部分完成、錯誤行為、越界及證據不適用。引用需求與支持判定的實際來源。
- **工程品質**：檢查變更造成的可靠性、維護性與專案規範問題；文件變更另以「離開當前對話的讀者」身分核對 docs/ 與 README——不依賴治理語彙或對話脈絡、無未定義即用的詞。區分有明文依據的違規與設計建議，工具已檢查的格式事項（如 sb docs 的結構檢查）沿用結果。

兩軸分別報告，任一軸通過都不替另一軸背書；靜態 diff 不能替代真實驗收。小變更可由同一獨立審計者分欄完成；大範圍、爭議或高風險時可分派獨立上下文，使用相同基準再由主代理整合。分軸不新增使用者核准時點，也不讓一般直接實作強制進入 slug。

每項發現附檔案位置、實測或可核對來源，說明觸發條件、影響及最小修復。區分必修與建議，實測重現與靜態推論分別標示；發現品質以證據、影響及可修復性判定。

主代理核對發現，修復必修項並對修復做必要複審。已驗證且未受影響部分沿用。只有關鍵結論仍有爭議、證據衝突或高風險盲點時另取獨立意見。

報告存於 .shiftblame/tmp/，保留審計原文及必要證據。供 sb adversarial 使用的報告末段含「對抗判定：通過」或「對抗判定：不通過」及「審查模型：實際模型」。此格式供 CLI 解析；報告內容須來自實際獨立審查。需要的獨立能力不可用時說明缺口，先完成其餘可獨立推進的工作。
