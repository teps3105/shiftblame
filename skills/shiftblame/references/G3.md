# G3——實作與驗收（build／verify 段）

build 段依已授權結果與 G2（計畫與品質）實作，在 G3 建立實作紀錄並回指已封存的 G2 定義區 hash（三角回指的 G3 → G2 邊）；verify 段逐項對照 G1 驗收——在實際需要的環境建立前提、執行操作並觀察結果。

## 實作與整合

優先重用既有能力。讀取相關呼叫與消費者，修正共同根因，保護無關使用者變更。以可診斷、可回復的一組改動推進，依影響執行必要檢查。可獨立分工時使用隔離工作區，整合者核對變更與測試；平行推進的片段與背景任務以檔案邊界互斥——每份檔案同時只有一個實作者。外部應用由其適用技能承接來源保存與實機驗證。

依 G2 的片段安排推進：無依賴的片段即續行，不以完成順序阻塞彼此。預期耗時的建置、測試與驗證以背景任務或子代理執行，等待期間續行其他片段，結果到齊再整合；沒有可續行工作時結束回合回報狀態，完成通知到再接續。採測試先行時依 G2 的品質安排取得失敗到通過的回饋。原症狀未消失、根因不明或連續修補無進展時，依 [DEBUG](DEBUG.md) 改用可反駁假設及定向取證。

發現計畫、品質安排或技術前提錯誤時回對應責任段（quality／plan／research）修正並續行；只有需求／授權改變才先經訪談回 requirement 修約。與實作同批更新受影響文件，保持描述一致。完成功能或一致的修正批後，精準 staged，經 `sb commitmsg` 提交。

## 驗收

進入 verify 前保持受驗工作樹乾淨；受驗來源保持穩定，驗收所需資料、可丟棄快取及輸出可在明確範圍準備。沿用與交付內容、依賴及環境一致的有效證據，重驗受影響或失效部分。記錄 SATISFIED、UNSATISFIED 或 UNVERIFIED，附能支持判定的操作及觀察來源：測試綠燈只代表其斷言範圍，畫面／渲染、交互、外部系統等需求使用對應證據；需要人工操作的項目安排實機驗證，未執行則如實標示。各項證據相互獨立時可平行取證——長測試與實機驗證以背景任務並行，等待期間核對已完成項，全數到齊才檢閱與終審。發現來源問題先回 build 修正，再重驗受影響部分。

## 時點 3

必修項修復並驗證後，取得時點 3 的獨立驗收檢閱（依 [AUDIT](AUDIT.md)），主代理核對其證據與範圍。揭露實際完成、殘餘與未驗項，交使用者終審；終審的確認記入訪談紀錄新的一輪（觸發寫「交付前」）。使用者 pass 後，`sb next requirement --new-ms --adversarial --boss-ok` 或 `sb end --adversarial --boss-ok` 承接授權；時點 3 審查完成後 G1 回指 G3 閉環，正式出口以使用者決策為準。審查與終審期間可先行研究，受驗來源保持不變。
