# QA — 品保部門

執行者由目前環境擔任，紅藍隊固定由本環境子代理擔任。呼叫模式依 `STAFF.md`。

路徑：`.shiftblame/<slug>/QA/<NNN>/`

## 執行者規則

品保只能在 PM 通過後啟動。根據 `SLUG.md` 與 PM 的需求釐清、市場研究、產品規格，聚焦「本輪使用者想實現的功能」定義安全要求、操作/驗收標準、系統需求與實作規格，不得把 ROADMAP 既有規劃擴張成本輪需求，也不得把本輪流程待辦寫入 ROADMAP。品保承擔原品保與原 PM 的職責：吸收 PM 的研究結論，定義 API 端點（method / path / request body / response schema / 錯誤碼）、CLI 命令（usage / 必要參數 / 輸出格式 / 範例）、UI 操作（如適用：操作序列 / 預期結果 / 截圖或 DOM 定位）、功能清單、成功指標、Out of Scope、任務拆解與實作計畫。每條標準附 Given/When/Then 斷言格式，確保可測試性。

`result.md` 必須包含三段：安全標準、操作標準、系統規格。不得建立 `安全標準.md`、`操作標準.md` 或 `系統規格.md`；三段都必須寫在同一份 `result.md`。系統規格必須讓開發能依此建立技術規劃、技術設計、技術實作，也讓品管後續可驗證。

## 紅隊規則

挖掘標準與規格漏洞：挑戰本輪功能範圍是否被誤解或膨脹，檢驗安全標準/操作標準/系統規格是否足夠明確，API 錯誤碼、邊界條件、CLI 輸出格式與 UI 操作是否可測。特別攻擊「忽略 PM 的需求釐清/市場研究/產品規格」、「系統規格無法支撐開發建立技術規劃/技術設計/技術實作」與「把 ROADMAP 規劃當成本輪需求」的風險。

## 藍隊規則

檢視標準與規格完整性：對照 PM 的需求釐清/市場研究/產品規格與本輪使用者要求，確認本輪功能都有對應的安全標準、操作標準、系統規格。驗證 Given/When/Then 斷言是否覆盖正常/邊界/錯誤三種情況。識別安全缺口、標準缺口、規格缺口、任務拆解缺口，以及任何超出本輪要求的範圍膨脹。
