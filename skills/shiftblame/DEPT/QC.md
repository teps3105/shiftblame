# QC — 品管部門

> 適用模式：L2 + L3 + L4

## 職責

- 三方 CLI 獨立驗證穩健性、邊緣案例、紅藍隊攻擊
- 禁止重複 DEV 自動化綠燈內容，不重複管理者 E2E 已覆蓋路徑
- 穩健性攻擊：空值、極端值、特殊字元、並行操作、時序競爭
- 邊緣案例挖掘：非常態輸入、異常流程、邊界條件
- 紅隊視角攻擊 + 藍隊視角防禦掃描 + 紅藍對照
- Web SPA 透過前端介面操作（chrome-devtools-mcp），不僅打 API

## 執行模型

三方驗證（equal_consensus）。三方 CLI 平行派工，各自獨立執行驗證。

**角色：**
- claude：穩健性攻擊 + 邊緣案例挖掘
- codex：紅隊攻擊（攻擊者視角重現失敗案例）
- gemini：藍隊防禦掃描 + 紅藍對照

**流程：**
1. 管理者讀取上游（DEV）conclusion.md + 管理者 E2E 驗證結果
2. 管理者發布 task.md，指派三方各自驗證職責
3. 三方平行執行，各自寫入 review.md
4. 管理者彙整三方 review.md，寫入 conclusion.md
5. 判定：
   - 通過（PASS）→ 推進秘書收尾
   - 不通過（FAIL）→ 退回 DEV 開新 NNN 修正

**不通過退回 DEV 規則：**
- 不在 QC 部門內開修正循環
- conclusion.md 記載失敗根因與具體退回項目
- 退回 DEV 後，DEV 依退回項目開新 NNN 修正
- 修正完成後，管理者必須再次執行 E2E 實際驗證，通過後才可重新進入 QC
- 同一 slug 下 QC 退回 DEV 最多 5 次，超過向上退回至 PRD

**CLI 介入：** 三方 CLI 各自寫入 review.md，管理者彙整寫 conclusion.md。

## 產出規格

路徑：`.shiftblame/<slug>/QC/`
- `claude/review.md` — claude 寫入（穩健性 + 邊緣案例）
- `codex/review.md` — codex 寫入（紅隊攻擊）
- `gemini/review.md` — gemini 寫入（藍隊防禦 + 紅藍對照）
- `conclusion.md` — 管理者寫入（驗證結論）

### review.md 必備內容

**claude（穩健性 + 邊緣案例）：**
1. 穩健性攻擊結果（逐條）
2. 邊緣案例清單與測試結果
3. 對照 QA 斷言逐條攻擊結果
4. 發現的問題清單（BUG、邏輯斷裂、數量）
5. 操作佐證（截圖路徑、console logs、步驟紀錄）

**codex（紅隊攻擊）：**
1. 攻擊路徑清單與結果（逐條）
2. 成功重現的失敗案例
3. 安全問題清單
4. 操作佐證

**gemini（藍隊防禦 + 紅藍對照）：**
1. 防禦掃描結果（逐條）
2. 紅藍對照表（攻擊項 vs 防禦驗證）
3. 防禦缺口分析
4. 操作佐證

### conclusion.md 必備內容

1. 三方驗證結果摘要
2. 問題總覽（BUG、邊緣案例、邏輯斷裂、安全問題數量）
3. 紅藍對照結論
4. 驗收結論（PASS 或 FAIL）
5. 驗收後部署指引（PASS 時必填）
6. 失敗根因分析與退回建議（FAIL 時必填）

## 運作規則

**R1 真實操作驗證**
Web SPA 或有 UI 的應用，必須透過前端介面驗證（chrome-devtools-mcp），嚴禁僅以 API 替代。

**R2 紅藍對照**
gemini 的 review.md 必須包含紅隊（codex 攻擊）與藍隊（gemini 防禦）的對照表，缺一不可。

**R3 邊緣案例挖掘**
claude 主動穩健性攻擊：空值、極端值、特殊字元、並行操作、時序競爭。不僅驗證 Happy Path。

**R4 對照 QA 斷言逐條攻擊**
禁止重複自動化綠燈。QA 定義「應該怎樣」，QC 驗證「各種意外下是否依然如此」。

**R5 不重複管理者 E2E**
管理者已在 DEV→QC 閘門完成 E2E 實際驗證。QC 不重複走 Happy Path，聚焦穩健性、邊緣案例、紅藍隊。

**R6 產出必含操作佐證**
無證據的 PASS 視同失效。

**R7 驗收結論與指引**
PASS → 部署指引。FAIL → 根因分析 + 退回建議（退回 DEV）。

**R8 README.md / REPO.md 品質檢閱**
所有模式驗證範圍包含：
- README.md：版本號與框架設定一致、架構描述與實作一致、格式正確
- `.shiftblame/REPO.md`：技術棧與實作一致、待辦事項準確、各區段完整

這兩個檔案不在開發階段修改（秘書收尾時維護），QC 只檢閱品質，發現問題由秘書裁定。

**R9 桌面驗證**
QC 驗證標準：三方各自至少一個邊緣案例或攻擊路徑實際跑通。最低證據：完整測試執行輸出 + 操作步驟紀錄。

**R10 QC 退回後管理者重新 E2E**
QC 不通過退回 DEV，DEV 修正完成後，管理者必須再次執行 E2E 實際驗證。通過後才可重新進入 QC。不可跳過此閘門。

## 認知模型

**QC 補 DEV 與管理者盲區**：DEV 證明「程式碼如其所寫」，管理者 E2E 證明「核心路徑如用戶所預期」，QC 證明「各種意外下是否依然如此」。
**證據是唯一基礎**：無證據的 PASS 視同失效。
**三方獨立驗證**：三方 CLI 各自獨立執行，不互相抄襲結果。管理者彙整判定。
**不通過即退回**：QC 不通過直接退回 DEV 開新 task，不在 QC 內修正循環。
