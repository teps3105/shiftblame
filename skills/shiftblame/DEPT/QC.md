# QC — 驗收上線部門

執行者由目前環境擔任，紅藍隊固定由本環境子代理擔任。呼叫模式依 `STAFF.md`。

路徑：`.shiftblame/<slug>/QC/<NNN>/`

## 執行者規則

驗收上線在工程收尾後啟動，工具選擇依實際環境決定（CLI / API / chrome-devtools-mcp 等）。

### 工作結論（寫入 task.md，狀態 EXECUTED）

執行端到端驗證，確認三方至少各有一個邊緣案例或攻擊路徑實際跑通。驗收上線內部包含三個階段：邏輯驗證（LOGIC REVIEW，含清理檢查確認無殘留）、部署（DEPLOYED，從功能分支部署）、端到端驗證（E2E，驗證部署結果）。三個階段可在一次驗收上線任務或多次驗收上線任務中完成（取決於是否退回）。驗收上線內部階段失敗一律退回產品開發新 NNN（驗收上線不修改程式碼）。每個階段的具體通過標準由驗收上線執行者在驗收計畫中定義。將驗證結論寫入 task.md（狀態 EXECUTED）。

驗收上線退回觸發條款：不得自行修改程式碼、設定檔或任何實作產物。

### 結果產出（寫入 result.md，紅藍回饋後）

依紅藍回饋，將驗收計畫、驗收報告、驗收結論整理為 result.md，包含三段：驗收計畫、驗收報告、驗收結論。不得建立「驗收計畫.md」、「驗收報告.md」或「驗收結論.md」；內容必須彙整驗收計畫、實測證據、完成紀錄與 PASS/FAIL 判定。

## 紅隊規則

以攻擊者視角重現失敗案例：挖掘安全漏洞、構造異常輸入、重現崩潰場景。分析系統在壓力下的行為，識別被忽略的失敗模式。提供攻擊成功的第一手證據。

## 藍隊規則

掃描防禦缺口：對照紅隊攻擊項，驗證防禦機制是否有效。產出紅藍對照表，明確列出攻擊路徑與對應的防禦驗證結果。分析殘餘風險，提出改進建議。確保無證據的 PASS 無效。
