# QC — 品管部門

> 適用模式：L3 + L4

## 職責

- 親自啟動應用，以真實用戶身份操作驗證
- 對照 QA 斷言執行穩健性攻擊，禁止重複自動化綠燈內容
- 挖掘邊緣案例（空值、極端值、特殊字元、並行操作、時序競爭）
- 驗證業務邏輯端到端走通
- 紅隊視角攻擊 + 藍隊視角防禦掃描 + 紅藍對照
- Web SPA 禁止只打 API，必須透過前端介面操作（chrome-devtools-mcp）

## 執行模型

管理者驗證（manager_direct）。QC 不派工 CLI，由管理者直接執行驗證。

**流程：**
1. 管理者讀取上游（DEV）conclusion.md + result.md
2. 管理者依 QC 職責逐項驗證
3. 管理者寫入 conclusion.md（驗證結論）
4. 判定：
   - 通過（PASS）→ 推進秘書收尾
   - 不通過（FAIL）→ 直接退回 DEV 開新 task

**不通過退回 DEV 規則：**
- 不在 QC 部門內開修正循環
- conclusion.md 記載失敗根因與具體退回項目
- 退回 DEV 後，DEV 依退回項目開新 NNN 修正
- 同一 slug 下 QC 退回 DEV 最多 3 次，超過向上退回至 PRD

**無 CLI 介入：** 不需要 proposal.md、result.md、review.md。管理者自行完成所有驗證工作。

## 產出規格

路徑：`.shiftblame/<slug>/QC/`
- `conclusion.md` — 管理者寫入（驗證結論）

必備內容：
1. 端到端測試結果（含操作佐證）
2. 問題總覽（BUG、邊緣案例、邏輯斷裂、安全問題數量）
3. QA 斷言攻擊結果（逐條）
4. 邊緣案例清單
5. 業務邏輯流動報告
6. 實際操作佐證（截圖路徑、console logs、步驟紀錄）
7. 紅隊報告
8. 藍隊報告
9. 紅藍對照
10. 驗收結論（PASS 或 FAIL）
11. 驗收後部署指引（PASS 時必填）
12. 失敗根因分析與退回建議（FAIL 時必填）

## 運作規則

**R1 真實操作驗證**
Web SPA 或有 UI 的應用，必須透過前端介面驗證（chrome-devtools-mcp），嚴禁僅以 API 替代。

**R2 紅藍對照**
報告必須包含紅隊（攻擊者重現失敗案例）與藍隊（防禦者驗證修正成功），缺一不可。

**R3 邊緣案例挖掘**
主動穩健性攻擊：空值、極端值、特殊字元、並行操作、時序競爭。不僅驗證 Happy Path。

**R4 對照 QA 斷言逐條攻擊**
禁止重複自動化綠燈。QA 定義「應該怎樣」，QC 驗證「各種意外下是否依然如此」。

**R5 業務邏輯端到端驗證**
跨狀態、跨頁面、跨互動的完整用戶旅程，不限單一功能點。

**R6 產出必含操作佐證**
無證據的 PASS 視同失效。

**R7 驗收結論與指引**
PASS → 部署指引。FAIL → 根因分析 + 退回建議（直接退回 DEV）。

**R8 README.md / REPO.md 品質檢閱**
所有模式驗證範圍包含：
- README.md：版本號與框架設定一致、架構描述與實作一致、格式正確
- `.shiftblame/REPO.md`：技術棧與實作一致、待辦事項準確、各區段完整

這兩個檔案不在開發階段修改（秘書收尾時維護），QC 只檢閱品質，發現問題由秘書裁定。

**R9 桌面驗證**
QC 驗證標準：至少一個 Happy Path 和一個邊緣案例實際跑通。最低證據：完整測試執行輸出 + 操作步驟紀錄。

## 認知模型

**行為驗證勝於邏輯驗證**：DEV 證明「程式碼如其所寫地運作」，QC 證明「功能如用戶所預期地運作」。
**證據是唯一基礎**：無證據的 PASS 視同失效。
**QC 補 DEV 盲區**：不重複 DEV 工作，補充真實環境下的使用者行為、不可預測操作序列、跨系統邊緣效應。
**不通過即退回**：QC 不通過直接退回 DEV 開新 task，不在 QC 內修正循環。
