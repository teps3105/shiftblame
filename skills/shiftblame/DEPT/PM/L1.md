# PM — 執行者宣告規則

PM 是功能開發管線的第一個部門。必須在品質保證啟動前完成閘門。

PM 是前端設計的唯一權威。PM 產出的「前端設計與視覺規格」為前端所有設計決策的最終來源，DEV 不得自行決定前端設計（版面、元件、互動流程、視覺效果），只能依 PM 規格實作前端接線與資源管理。

## 前端設計產物暫存規則

前端設計的視覺產出（線框圖、互動原型、視覺稿、設計稿等）一律存放在 `.shiftblame/tmp/` 或 Open-design 環境的專案中，不進入版本控制。除非老闆明確要求納入版本控制，否則這些產物只作為開發中的參考材料。PM result.md 中的文字形式設計規格（色值、間距、元件清單等）為正式產物，必須完整寫入 result.md。

PM 執行者在產出 result.md 時，依老闆之 Open-design 環境操作，使用 MCP 工具或 HTTP API 進行前端設計與視覺驗證，讓老闆在專案中查看設計。這些設計工作在 PM 階段完成，下游 QA 據此建立驗證標準與 GWT 測試案例，DEV 據此實作前端接線。

每一輪執行前必須先在 task.md「## 宣告」段落寫入本輪計畫（本輪目標、預期產出），經管理者向老闆確認同意後才能開始執行。管理者確認時必須說明「現在是 L1 階段（宣告）」。每一輪都可以完整執行（研究調查與前端設計等），由老闆在宣告確認時決定範圍。PASS 後即可推進到下游或本部門新執行切片。

根據 `SLUG.md` 與 task.md，釐清本輪使用者真正想實現的功能、現有 repo/REPO.md/ROADMAP.md 的相關背景、本輪範圍與非本輪事項，並調查建立標準前需要知道的市場研究、通用方法、設計模式、CVE 或版本差異。同時依老闆之 Open-design 環境操作，產出前端設計與視覺規格。ROADMAP 只能列為收尾後的穩定背景或後續候選，不得自動納入本輪；本輪流程待辦與開發中判斷只寫入 `SLUG.md`。

PM 可參照 `.shiftblame/PRD/` 中的產品需求文件作為需求來源（若存在）。PRD 為非強制參照。

任何輪次不得更動已 PASSED 的前輪計畫範圍（功能範圍、架構決策、技術選型等）。若在執行中發現需要更動計畫，須由管理者判定：功能範圍增減或架構決策變更屬計畫更動（觸發回溯或進路線圖），實作方式、邊界處理、錯誤處理等不改變功能範圍的調整屬執行細節（不觸發）。

PM result.md 以目標導向產出：聚焦「本輪要達成什麼、品質標準是什麼、怎麼驗證完成」。RAPID 模式下 PM 吸收 QA 職責（品質定義、測試標準與驗收條件），一併寫入 result.md。
