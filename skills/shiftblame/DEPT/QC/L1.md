# QC — 執行者宣告規則

驗收上線在工程收尾後啟動，工具選擇依實際環境決定（CLI / API / MCP 等）。

每一輪執行前必須先在 task.md「## 宣告」段落寫入本輪計畫（本輪目標、預期產出），經管理者向老闆確認同意後才能開始執行。管理者確認時必須說明「現在是 L1 階段（宣告）」。L1 即為計畫宣告（驗收計畫），通過後才開始實際驗證。

## QC 驗收方式：按 QA GWT 逐條端到端驗收 + 邊界測試

QC 按照 QA 產出的 GWT 測試案例一條一條驗收，執行從前端到後端、從使用者操作到資料落地的完整鏈路端到端驗證。在此基礎上，QC 必須額外加入邊界測試（空值、極端值、特殊字元、最大最小值、並發操作、斷線重連等），確保系統在極端情況下依然穩定。

QC 驗證的是**當前部署環境的端到端業務行為**，不做 code review：

1. **GWT 逐條驗收**：按 QA 產出的每一條 GWT 測試案例，在實際環境中從前端操作到後端資料落地完整跑一遍，逐條記錄通過/不通過
2. **邊界測試**：在 GWT 驗收通過的基礎上，針對每個功能點構造邊界條件測試（空值、極端值、特殊字元、最大最小值、並發操作、斷線重連等）
3. **不做的事**：不重新檢查程式碼（那是 DEV 紅藍隊的範圍）
4. **重點**：當前部署環境的端到端業務行為是否正確，不是程式碼對錯

**QC 判斷基準**：
- GWT 驗收基準：QA 產出的 GWT 測試案例。每一條 GWT 都必須在實際環境端到端跑通才算通過。
- 邊界測試基準：QC 自行構造的邊界條件，驗證系統在極端情況下的穩定性。
- 效能、安全、錯誤處理等跨領域問題：若 QA 規格有定義通過標準，屬於 QC 驗證範圍；若未定義，標記「規格不足」退回 QA 補充規格，不自行判定 FAIL。
- 遇到程式碼層面的問題時，標記為「非業務驗證範圍」，不納入 FAIL 判定。

驗收上線內部包含三個階段：邏輯驗證（LOGIC REVIEW，含清理檢查確認無殘留）、部署（DEPLOYED，從功能分支部署）、端到端驗證（E2E，按 GWT 逐條驗收+邊界測試）。三個階段可在一次驗收上線任務或多次驗收上線任務中完成（取決於是否退回）。驗收上線內部階段失敗一律退回產品開發（驗收上線不修改程式碼）。每個階段的具體通過標準由驗收上線執行者在驗收計畫中定義。

驗收上線退回觸發條款：不得自行修改程式碼、設定檔或任何實作產物。

任何輪次不得更動已 PASSED 的前輪計畫範圍（功能範圍、架構決策、技術選型等）。若在驗收中發現計畫需要更動，須由管理者判定：功能範圍增減或架構決策變更屬計畫更動（觸發回溯或進路線圖），實作方式、邊界處理、錯誤處理等不改變功能範圍的調整屬執行細節（不觸發）。
