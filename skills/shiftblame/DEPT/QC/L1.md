# QC — 執行者工作結論規則

驗收上線在工程收尾後啟動，工具選擇依實際環境決定（CLI / API / chrome-devtools-mcp 等）。

`QC/001` 是初步、不清楚且未經完整攻防的驗收前計畫輪，僅能確認驗收範圍、驗收計畫與風險，不得直接開始測試或驗收。驗收上線至少必須完成 `QC/002` 循環並通過 Result Check 與 BossConfirm，才可作為上線或收尾依據。

QC 驗證的是**當前部署環境的業務行為**，不做 code review：

1. **需求對比**：逐項對比 QA 與 PM 定義的所有使用者需求、業務邏輯規劃，確認是否正確實現
2. **功能驗證**：DEV 宣稱已完成的功能，在當前部署環境實際操作，確認真的完成
3. **不做的事**：不重新檢查程式碼（那是 DEV 紅藍隊的範圍）
4. **重點**：當前部署環境的業務行為是否正確，不是程式碼對錯

**QC 判斷基準**：
- 驗證對象是 QA task.md 定義的規格，不是 DEV result.md 的技術描述。規格定義的通過標準為準。
- 效能、安全、錯誤處理等跨領域問題：若 QA 規格有定義通過標準，屬於 QC 驗證範圍；若未定義，標記「規格不足」退回 QA 補充規格，不自行判定 FAIL。
- 遇到程式碼層面的問題時，標記為「非業務驗證範圍」，不納入 FAIL 判定。

驗收上線內部包含三個階段：邏輯驗證（LOGIC REVIEW，含清理檢查確認無殘留）、部署（DEPLOYED，從功能分支部署）、端到端驗證（E2E，驗證部署結果）。三個階段可在一次驗收上線任務或多次驗收上線任務中完成（取決於是否退回）。驗收上線內部階段失敗一律退回產品開發新 NNN（驗收上線不修改程式碼）。每個階段的具體通過標準由驗收上線執行者在驗收計畫中定義。將驗證結論寫入 task.md（狀態 EXECUTED）。

驗收上線退回觸發條款：不得自行修改程式碼、設定檔或任何實作產物。

執行部門 002+ 不得更動 001 定義的計畫範圍。若在驗收中發現計畫需要更動，須由管理者判定並處理（回溯或進路線圖）。
