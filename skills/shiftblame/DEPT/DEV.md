# DEV — 產品開發部門

執行者由目前環境擔任，紅藍隊固定由本環境子代理擔任。呼叫模式依 `STAFF.md`。

路徑：`.shiftblame/<slug>/DEV/<NNN>/`

## 執行者規則

DEV 開始前，管理者必須先詢問老闆想先達成品質保證結果裡哪個可見功能；若尚未取得選擇，不得開始實作。DEV task.md 的目標必須用繁體中文描述本回合要實際做出的作品效果，不得只寫技術項目。

### 工作結論（寫入 task.md，狀態 EXECUTED）

依老闆選定的可見功能實作，內部可參考品質保證的安全標準、操作標準、系統規格，但對老闆回報時只說作品變化與可操作結果。先建立技術規劃、技術設計的前置內容，明確定義本回合可見功能、測試情境、驗證方式與預期證據，再依此開始修改程式碼。每完成一個可觀看片段，實際啟動作品並提供 URL、指令、截圖或操作證據；老闆可在 DEV 中多次要求觀看變化、追加小調整或指定下一個想看到的效果。這些 `BossPreview` 回合不需要紅藍隊。README.md 的更新由產品開發執行者視需要執行，使其反映本輪功能的最終現況。README.md 是工程產品開發文件，修改屬於產品開發部門。實作時保留必要工程品質：先定義可驗證行為，再完成程式碼與測試；完成前執行語法檢查、測試或等效驗證。驗證結果回報給老闆時，使用「可以新增並看見卡片」「按下儲存後資料還在」這類功能語言，不用測試框架或技術術語包裝。commit 訊息格式約束：

- 格式：`<type>: <繁體中文標題>`（標題不超過 72 字元）
- body 以條列說明變更要點，每項一行
- type 清單：feat（新功能）、fix（修正）、docs（文件）、style（格式）、refactor（重構）、test（測試）、chore（雜務）
- 標題與 body 全程繁體中文。type 前綴使用慣例英文字
- 一個 NNN 對應一個 commit，不得在同一 NNN 中多次 commit

開發必須在呼叫紅隊攻擊前 commit 目前所有變更到功能分支（見操作標準 10）。紅隊攻擊的對象是 task.md 中的工作結論（不是 result.md），紅隊同時驗證功能分支上的目前狀態。commit 在 `feat/<slug>` 功能分支上。功能分支在第一次進入產品開發時由管理者建立（見操作標準 15）。將工作結論寫入 task.md（狀態 EXECUTED）。開發中待調整事項、退回脈絡與跨輪筆記寫入 `.shiftblame/<slug>/SLUG.md`，不得寫入 ROADMAP。

### 結果產出（寫入 result.md，紅藍回饋後）

依紅藍回饋，將技術規劃、技術設計、技術實作整理為 result.md。技術規劃和設計是工作過程的一部分，先於程式碼實作；result.md 是紅藍後才寫的定稿。result.md 必須包含三段：技術規劃、技術設計、技術實作。不得建立「技術規劃.md」、「技術設計.md」或「技術實作.md」。

## 紅隊規則

驗證老闆選定的可見功能是否真的做出來：檢查使用者能否按預期操作、看到結果、遇到錯誤時理解發生什麼。攻擊邊界情境（空內容、極端值、特殊字元、快速連點、刷新或重開）。紅隊攻擊的對象是 task.md 中的工作結論（不是 result.md），紅隊同時驗證功能分支上的目前狀態。技術缺陷可記錄，但紅隊結論必須先用作品語言說明哪個使用情境會失敗。

## 藍隊規則

確認本回合功能完整性：對照老闆選定的品質保證功能與 DEV task.md 的可見功能，確認作品是否能被操作、觀看與驗證，並確認技術規劃/技術設計/技術實作已先於實作建立且足以支撐驗收上線產出驗收計畫/驗收報告/驗收結論。整理紅隊指出的使用情境，逐項判定已修正、可接受或必須退回。藍隊報告必須包含給老闆看的中文摘要：目前能看到什麼、怎麼試、還有哪些不符合期待。
