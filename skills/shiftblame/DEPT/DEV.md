# DEV — 開發部門

執行者由目前環境擔任，紅藍隊固定由本環境子代理擔任。呼叫模式依 `STAFF.md`。

路徑：`.shiftblame/<slug>/DEV/<NNN>/`

## 執行者規則

DEV 開始前，管理者必須先詢問老闆想先達成品保結果裡哪個可見功能；若尚未取得選擇，不得開始實作。DEV task.md 的目標必須用繁體中文描述本回合要實際做出的作品效果，不得只寫技術項目。

依老闆選定的可見功能實作，內部可參考品保的安全標準、操作標準、系統規格，但對老闆回報時只說作品變化與可操作結果。`result.md` 必須包含三段：技術規劃、技術設計、技術實作。不得建立 `技術規劃.md`、`技術設計.md` 或 `技術實作.md`。開發必須先在 `result.md` 建立技術規劃、技術設計、技術實作的前置內容，明確定義本回合可見功能、測試情境、驗收方式與預期證據，才能開始修改程式碼；後續實作結果與驗證證據也持續記錄在同一份 `result.md`。每完成一個可觀看片段，實際啟動作品並提供 URL、指令、截圖或操作證據；老闆可在 DEV 中多次要求觀看變化、追加小調整或指定下一個想看到的效果。這些 `BossPreview` 回合不需要紅藍隊；正式實作與驗證證據寫入 `result.md`，開發中待調整事項、退回脈絡與跨輪筆記寫入 `.shiftblame/<slug>/SLUG.md`，不得寫入 ROADMAP。

實作時保留必要工程品質：先定義可驗證行為，再完成程式碼與測試；完成前執行語法檢查、測試或等效驗證。驗證結果回報給老闆時，使用「可以新增並看見卡片」「按下儲存後資料還在」這類功能語言，不用測試框架或技術術語包裝。

commit 訊息格式約束：

- 格式：`<type>: <繁體中文標題>`（標題不超過 72 字元）
- body 以條列說明變更要點，每項一行
- type 清單：feat（新功能）、fix（修正）、docs（文件）、style（格式）、refactor（重構）、test（測試）、chore（雜務）
- 全程繁體中文，不得使用英文描述
- 一個 NNN 對應一個 commit，不得在同一 NNN 中多次 commit

開發必須在呼叫紅隊攻擊前 commit 目前所有變更到功能分支（見操作標準 10）。紅隊攻擊的對象是 task.md 中的工作結論（不是 result.md），紅隊同時驗證功能分支上的目前狀態。commit 在 `feat/<slug>` 功能分支上。功能分支在第一次進入開發時由管理者建立（見操作標準 15）。

## 紅隊規則

驗證老闆選定的可見功能是否真的做出來：檢查使用者能否按預期操作、看到結果、遇到錯誤時理解發生什麼。攻擊邊界情境（空內容、極端值、特殊字元、快速連點、刷新或重開）。紅隊攻擊的對象是 task.md 中的工作結論（不是 result.md），紅隊同時驗證功能分支上的目前狀態。技術缺陷可記錄，但紅隊結論必須先用作品語言說明哪個使用情境會失敗。

## 藍隊規則

確認本回合功能完整性：對照老闆選定的品保功能與 DEV task.md 的可見功能，確認作品是否能被操作、觀看與驗證，並確認技術規劃/技術設計/技術實作已先於實作建立且足以支撐品管產出驗收計畫/驗收報告/驗收結論。整理紅隊指出的使用情境，逐項判定已修正、可接受或必須退回。藍隊報告必須包含給老闆看的中文摘要：目前能看到什麼、怎麼試、還有哪些不符合期待。
