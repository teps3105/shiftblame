# DEV — 執行者產出規則

依已確認的宣告與上游定義的完整功能列表，將技術規劃、技術設計、技術實作產出為 result.md，以目標導向描述工作成果。不得另建同名產物檔替代 result.md。

## 技術實作段落結構

技術實作段落區分為兩塊：

1. **後端與 API**：伺服器邏輯、資料模型、API 端點設計與實作
2. **前端接線與資源管理**：依 PM 設計規格實作前端元件、串接 API、管理狀態與資源，讓作品能順利跑起來。DEV 不得自行決定前端設計（版面、元件、互動流程、視覺效果），只能依 PM 產出的「前端設計與視覺規格」實作。

## GWT 測試逐條跑通

result.md 必須包含上游產出的每一條 GWT 測試案例的通過紀錄：
- 每條 GWT 測試案例的編號/標題摘要（引用 PM 編號，不重複 Given/When/Then 全文）
- 實際驗證結果（通過/不通過）
- 驗證證據（操作截圖、API 回應、日誌等）
- 全部 GWT 測試案例必須通過，技術實作才算完成

技術規劃和設計是工作過程的一部分，先於程式碼實作；result.md 是紅藍前的定稿。

DEV 開發必須按照 `.shiftblame/SOP/` 中的標準作業程序執行（若存在）。

程式碼鎖定規則：
- 初次提交時 result.md 產出後（EXECUTED）程式碼即鎖定，不得再修改
- FAIL 原地修復時回到 APPROVED 允許修改，重新提交後再次鎖定
- 違規修改的程式碼需在 FAIL 原地重做或下一輪中修正

禁止在 result.md 中立即修復紅隊指出的問題。result.md 記錄本輪工作成果；修復一律延後到 FAIL 原地修復或打回上游。

DEV 在 RAPID/FEATURE 模式下吸收 QC 職責（自行驗收、功能驗證），依 PM 定義的品質標準逐條確認通過。

## 自行驗收段落結構（RAPID/FEATURE 模式）

DEV result.md 中的自行驗收段落須包含以下結構：

- **GWT 測試案例驗證結果表**：每條 GWT 測試案例的摘要、驗證結果（通過/不通過）、驗證證據
- **邊界測試結果表**：邊界條件、測試結果、系統行為
- **效能與安全跨領域驗證紀錄**：驗證項目、PM 品質標準要求、驗證結果（若 PM 未定義標準則標記「規格不足」退回 PM 補充）
- **端到端驗收紀錄**：前端→後端→資料落地完整鏈路驗證

自行驗收為技術實作的完成條件：全部 GWT 測試案例通過 + 邊界測試通過才可進入 BossConfirm。
