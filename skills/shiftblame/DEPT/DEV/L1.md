# DEV — 執行者工作結論規則

DEV 開始前，管理者必須先詢問老闆想先達成品質保證結果裡哪個可見功能；若尚未取得選擇，不得開始實作。DEV task.md 的目標必須用繁體中文描述本回合要實際做出的作品效果，不得只寫技術項目。

`DEV/001` 是初步、不清楚且未經完整攻防的實作前計畫輪，僅能確認影響範圍、技術規劃與風險，不得修改程式碼、正式文件、設定、部署或 git 狀態。產品開發至少必須完成 `DEV/002` 循環並通過 Result Check 與 BossConfirm，才可作為下游正式輸入。

依老闆選定的可見功能實作，內部可參考品質保證的安全標準、操作標準、系統規格，但對老闆回報時只說作品變化與可操作結果。先建立技術規劃、技術設計的前置內容，明確定義本回合可見功能、測試情境、驗證方式與預期證據，再依此開始修改程式碼。每完成一個可觀看片段，實際啟動作品並提供 URL、指令、截圖或操作證據；老闆可在 DEV 中多次要求觀看變化、追加小調整或指定下一個想看到的效果。這些 `BossPreview` 回合不經過閘門審查。README.md 的更新由產品開發執行者視需要執行，使其反映本輪功能的最終現況。README.md 是工程產品開發文件，修改屬於產品開發部門。實作時保留必要工程品質：先定義可驗證行為，再完成程式碼與測試；完成前執行語法檢查、測試或等效驗證。驗證結果回報給老闆時，使用「可以新增並看見卡片」「按下儲存後資料還在」這類功能語言，不用測試框架或技術術語包裝。commit 訊息格式約束：

- 格式：`<type>: <繁體中文標題>`（標題不超過 72 字元）
- body 以條列說明變更要點，每項一行
- type 清單：feat（新功能）、fix（修正）、docs（文件）、style（格式）、refactor（重構）、test（測試）、chore（雜務）
- 標題與 body 全程繁體中文。type 前綴使用慣例英文字
- 一個 NNN 對應一個 commit，不得在同一 NNN 中多次 commit

所有變更必須 commit 到 `feat/<slug>` 功能分支上。在將工作結論寫入 task.md 之前，所有程式碼變更應已 commit。功能分支在第一次進入產品開發時由管理者建立。將工作結論寫入 task.md（狀態 EXECUTED）。開發中待調整事項、退回脈絡與跨輪筆記寫入 `.shiftblame/<slug>/SLUG.md`，不得寫入 ROADMAP。
