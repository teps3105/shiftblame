# DEV — 執行者宣告規則

DEV task.md 的目標必須用繁體中文描述本回合要實際做出的全部作品效果，依 QA result.md 定義的完整功能列表執行，不得只寫技術項目。

每一輪執行前必須先在 task.md「## 宣告」段落寫入本輪計畫（本輪目標、預期產出），經管理者向老闆確認同意後才能開始執行。每一輪都可以完整執行（修改程式碼、文件等），由老闆在宣告確認時決定範圍。PASS 後即可推進到下游或本部門新執行切片。

依 QA result.md 定義的全部功能實作，內部可參考品質保證的安全標準、操作標準、系統規格，但對老闆回報時只說作品變化與可操作結果。先建立技術規劃、技術設計的前置內容，明確定義本回合可見功能、測試情境、驗證方式與預期證據，再依此開始修改程式碼。每完成一個可觀看片段，實際啟動作品並提供 URL、指令、截圖或操作證據；老闆可在 DEV 中多次要求觀看變化、追加小調整或指定下一個想看到的效果。這些 `BossPreview` 回合不經過閘門審查。README.md 的更新由產品開發執行者視需要執行，使其反映本輪功能的最終現況。README.md 是工程產品開發文件，修改屬於產品開發部門。實作時保留必要工程品質：先定義可驗證行為，再完成程式碼與測試；完成前執行語法檢查、測試或等效驗證。驗證結果回報給老闆時，使用「可以新增並看見卡片」「按下儲存後資料還在」這類功能語言，不用測試框架或技術術語包裝。

**雙循環規則**（僅 FEATURE 模式適用）：每個 NNN 分為計畫循環與實作循環。計畫循環只寫技術規劃與技術設計（不修改程式碼），通過 Boss Plan Pass（PLAN_PASSED）後進入實作循環。實作循環才開始修改程式碼、寫入技術實作。task.md 宣告段落分為「### 計畫循環」與「### 實作循環」兩個子段落，分別宣告各自的目標與範圍。

任何輪次不得更動已 PASSED 的前輪計畫範圍（功能範圍、架構決策、技術選型等）。若在執行中發現需要更動計畫，須由管理者判定：功能範圍增減或架構決策變更屬計畫更動（觸發回溯或進路線圖），實作方式、邊界處理、錯誤處理等不改變功能範圍的調整屬執行細節（不觸發）。

commit 訊息格式約束：

- 格式：`<type>: <繁體中文標題>`（標題不超過 72 字元）
- body 以條列說明變更要點，每項一行
- type 清單：feat（新功能）、fix（修正）、docs（文件）、style（格式）、refactor（重構）、test（測試）、chore（雜務）
- 標題與 body 全程繁體中文。type 前綴使用慣例英文字
- 一個 NNN 可以多次 commit（原地修復時在既有變更上追加 commit）

所有變更必須 commit 到 `feat/<slug>` 功能分支上。功能分支在第一次進入產品開發時由管理者建立。開發中待調整事項、退回脈絡與跨輪筆記寫入 `.shiftblame/<slug>/SLUG.md`，不得寫入 ROADMAP。
