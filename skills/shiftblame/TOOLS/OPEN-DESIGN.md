# OPEN DESIGN 工具包

本文件整理 Open Design 的基礎定位、資源判讀方式、最小可用操作順序，以及研究結論如何回寫到 shiftblame 的 PM `result.md`。目標是讓下一位 Agent 在 PM 階段需要做前端設計時，不必再從零研究 Open Design 是什麼、先看哪裡、怎麼把成果交接下去。

## Open Design 是什麼

Open Design 是一套 AI 設計工作環境，也能透過 MCP 資源讓 Agent 讀取設計相關內容。對 shiftblame 來說，它不是拿來產生程式碼，而是拿來幫 PM 階段做三件事：

- 整理畫面方向與視覺規格
- 讀取可重用的設計技能與設計語言
- 把設計成果留在專案裡給老闆查看，並讓下游 DEV 能接手

## 它在 shiftblame 裡負責什麼

- PM：用來整理需求對應的畫面、元件、互動與視覺方向
- PM：定義品質標準與設計驗證標準（已整合至 PM result.md，承接原 QA 職責）
- DEV：依規格實作與進行自行驗收（承接原 QC 職責）

所以 Open Design 的主要輸出不是程式碼，而是：

- 畫面結構
- 互動流程
- 元件規格
- 視覺語言
- 可供老闆直接查看的設計內容

## 常見資源怎麼讀

### `od://focus/active`

先看目前有沒有活躍專案或正在編輯的設計內容。

- `active: false`
  代表目前沒有開啟中的設計專案。這是正常狀態，不代表工具壞掉，只表示現在沒有可直接接續的設計上下文。
- `active: true`
  代表已有活躍專案，可以優先從目前專案內容往下工作。

### `od://skills/<name>/SKILL.md`

當你已經知道自己要做哪一類設計產物時讀它。

適合的情境：

- 要做線框或版面規劃
- 要整理元件規格
- 要產出某種固定格式的設計交付物

### `od://design-systems/<slug>/DESIGN.md`

當你要決定整體視覺語言、品牌方向、色彩或排版調性時讀它。

適合的情境：

- 老闆希望作品有明確風格
- 需要統一色彩、字型、元件語言
- PM 需要先決定視覺調性，再往下寫規格

## 最小可用操作順序

下一位 Agent 第一次接手時，照這個順序做就好：

1. 開啟 Open Design 環境。
2. 先讀 `od://focus/active`。
3. 如果沒有活躍專案，先把需求拆成要補的畫面、互動或風格，再決定要讀 skill 還是 design system。
4. 如果有活躍專案，先理解現有設計內容，再補缺的規格。
5. 需要方法時讀對應 skill；需要整體視覺語言時讀 design system。
6. 把最後可交接的設計規格寫回 PM `result.md`，不要只把答案留在設計工具裡。

## 什麼時候讀什麼

- 想知道「這種設計產物通常怎麼做」：先讀 skill
- 想知道「整體風格要長成什麼樣子」：先讀 design system
- 想知道「現在專案裡有沒有可接著做的內容」：先讀 `od://focus/active`

如果同時要做功能規劃和視覺規劃，通常順序會是：

1. 先確認有沒有活躍專案
2. 再看需不需要補 skill
3. 最後才決定是否需要 design system 來收斂整體風格

## 研究結論怎麼寫回 PM `result.md`

Open Design 幫你整理出來的內容，最後要變成 PM `result.md` 裡的「前端設計與視覺規格」。至少要回寫這些資訊：

- 這次畫面要讓使用者看到什麼
- 主要區塊怎麼組成
- 使用者怎麼操作
- 重要元件有哪些
- 視覺方向是什麼
- 哪些內容留在 Open Design 裡供老闆直接查看

簡單說：

- `result.md` 負責留下可交接的設計規格與決策
- Open Design 專案負責承載實際可查看的設計內容

## 建議回寫格式

PM 在整理「前端設計與視覺規格」時，可以優先寫：

- 畫面目標
- 版面區塊
- 元件清單
- 互動流程
- 視覺語言
- 老闆去哪裡看設計稿

如果某些資訊還沒定案，不要先寫進 ROADMAP，應留在 `.shiftblame/<slug>/SLUG.md`。

## 本輪對 PM L1 / L2 的檢查結論

本輪已檢查 `skills/shiftblame/DEPT/PM/L1.md` 與 `skills/shiftblame/DEPT/PM/L2.md`。

結論：**本輪不需要修改。**

原因：

- PM L1 已經清楚說明 PM 要依老闆的 Open-design 環境操作，使用 MCP 工具或 HTTP API 進行前端設計與視覺驗證。
- PM L2 已經清楚定義「前端設計與視覺規格」要怎麼寫回 `result.md`，也說明設計成果要留在專案中讓老闆查看。

所以這份工具包這一輪的任務，是補足「Agent 第一次接手時的使用說明」，不是去改動 PM 規則本身。

## 使用原則

- 先讀活躍專案狀態，再決定下一步
- 不把研究結論只留在工具裡
- 可交接的規格一定要寫回 PM `result.md`
- 開發中的暫時判斷、退回原因、未定案想法寫進 `SLUG.md`
- 不把開發中的設計待辦直接寫進 `ROADMAP.md`

## 一句話總結

Open Design 是 shiftblame 在 PM 階段的設計工作台；它幫 Agent 判讀目前設計上下文、補設計方法與視覺語言，最後再把可交接的設計規格寫回流程文件。
