# GATE — 閘門與收尾

## 閘門原則

1. **回饋即意圖**：老闆每次說話即觸發意圖揭露，管理者必須先揭露理解到的意圖，確認後才執行
2. **SOP 約束**：SOP 為各專案執行準則，建立與修改皆需意圖揭露
3. **先提案再質疑**：G1/G2 雙軌平行，各走正→反→收斂流程
4. **迭代收斂**：管理者以最後收斂為基線增量增加
5. **雙軌平行**：G1 計畫視角 ‖ G2 技術視角，同時進行，各自收斂
6. **固定雙子代理**：永遠只開兩個子代理（G1 + G2），不得增開多個 G1/G2 或多視角子代理
7. **變更前先體驗**：修正/優化類變更前，管理者必須與老闆共同完整體驗產品，記錄問題後再進入管線
8. **Slug 前置硬閘門**：任何實作前必須先完成 slug 文件夾建立 + G1/G2 子代理回收 + 管理者收斂寫入 G1.md/G2.md
9. **雙軌隔離**：G1/G2 分開運作、分開產出、分開收斂，管理者合併為實作基線

## 狀態序

Slug：IN_PROGRESS → PASSED

每個 NNN：CONVERGED → PASSED（commit）或 FAILED（開新 NNN）

FAIL 以收斂為基線增量增加（正→反→收斂重新跑）。

## NNN 生命週期

每個 NNN 僅產出 `G1.md` 與 `G2.md`，禁止新增 slug 鏈外文件（白名單見 SKILL.md「`.shiftblame/` 內部佈局」）。

**範圍聚焦**：每個 NNN 處理單一可驗證問題（可寫成驗收條件、可被閘門 PASS/FAIL 判定者）；不同問題拆成獨立 NNN，不混在同一 NNN。

**體驗閘門**（修正/優化類變更）：管理者與老闆共同完整體驗產品，記錄使用者體驗、缺陷、BUG 等問題。問題寫入當輪 slug 的反方/收斂或 SOP 已知問題區。新功能開發類無此閘門。

**START**：載入三層租約（SOP｜SLUG §7｜SKILL+GATE+MANAGE+ROLE/G1+G2）→揭露目標→**暫停等老闆確認**。

**正方（雙軌平行）**：G1 正方提出計畫方案 ‖ G2 正方提出技術方案。固定兩個子代理，各自承擔 G1/G2 視角。

**反方（雙軌平行）**：G1 反方質疑計畫方案 ‖ G2 反方質疑技術方案。同一子代理切換為反方身份。

**收斂**：管理者分別收斂 G1 和 G2，產出兩份各自結論。反方 H/M/L 標註，不做決策。收斂結論與實作內容附於當輪 `G1.md`/`G2.md` 末尾，不另開新文件。收斂後揭露實作意圖（將做什麼變更）→**暫停等老闆確認**→確認後才正式實作。

**閘門**：呈現雙軌收斂結論→老闆 PASS/FAIL。

- PASS → 按兩份收斂結論實作 → commit
- FAIL → 以收斂為基線增量增加 → 開新 NNN

## 收尾

1. 最終 NNN PASS 後實作完成
2. 管理者品質確認
3. 老闆 PASSED
4. 管理者提交文件更新
5. `git checkout main && git merge --no-ff feat/<slug>`→推送→清理（每個 slug 恰好一個 merge commit）
6. 歸檔：將 `.shiftblame/<slug>/` 移至 `.shiftblame/archive/<slug>/`（archive 為可清空暫存，老闆可隨時清理），並更新 GRAPH.md 與 REPO.md 的歸檔紀錄（持久紀錄，欄位見各檔模板）

**回歸規則**：改善建議→SOP 未完成項目；BUG→SOP 已知問題區；目標→SOP 當前目標區。
