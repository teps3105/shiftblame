# GATE — 閘門與收尾

## 閘門原則

1. **回饋即意圖**：老闆每次說話即觸發意圖揭露，管理者必須先揭露理解到的意圖，確認後才執行
2. **老闆不是技術裁判**：老闆提供大局、需求、優先序、風險接受與 PASS/FAIL；agent 以證據、反證、取捨與替代方案提出可反駁建議
3. **證據閘門**：正方、反方與收斂須標示主張依據、查證狀態、未知項、風險/反證與替代方案；不確定技術主張若未查證，不得作為推進或 PASS 建議的依據
4. **SOP 約束**：SOP 為各專案執行準則，建立與修改皆需意圖揭露
5. **先提案再質疑**：G1/G2 雙軌平行，各走正→反→收斂流程
6. **迭代收斂**：管理者以最後收斂為基線增量增加
7. **雙軌平行**：G1 外部研究規劃視角 ‖ G2 內部技術實作視角，同時進行，各自收斂（側重非硬切，兩軌相輔相成、可各自查證）
8. **固定雙子代理**：永遠只開兩個子代理（G1 + G2），不得增開多個 G1/G2 或多視角子代理。反方獨立複審的 codex 整合見原則 12，不改變雙軌結構
9. **變更前先體驗**：修正/優化類變更前，管理者必須與老闆共同完整體驗產品，記錄問題後再進入管線
10. **Slug 前置硬閘門**：任何實作前必須先完成 slug 文件夾建立 + G1/G2 子代理回收 + 管理者收斂寫入 G1.md/G2.md
11. **雙軌隔離**：G1/G2 分開運作、分開產出、分開收斂，管理者合併為實作基線
12. **反方獨立複審與成果驗收的外部擔任（codex 選用）**：codex 啟用與雙層細則見 SKILL 核心原則「選用外部角色整合」

## 狀態序

**Slug**：IN_PROGRESS → PASSED（PASS 唯一存在於 slug 層級，由老闆拍板 slug 結束）

**每個 NNN**：START → 正方 → 反方 → 收斂 → 實作 → commit →（老闆指示推進）下一個 NNN

**NNN 層級無 gate / 無 PASS / 無 FAIL 機制**。一個 NNN 走完整輪（正→反→收斂→實作）即推進；推進時機由老闆隨時指示，agent 不得自行判定可推進、不得因 NNN 走完就自動 commit 不請示。例外：老闆明確指示「撤銷／退回」時不提交。commit 是本地存檔動作（可逆、不外送）；push 才是對外動作，仍需老闆指示。

Slug 內的迭代以收斂為基線增量增加：下一個 NNN 以上一 NNN 收斂為基線。整條 slug 所有 NNN 的 commit 疊在同一 `feat/<slug>` 分支，不為每個 NNN 開新分支。

**節奏紀律（與推進互補）**：「功能告一段落、先解決其他」≠「功能全部完善」。開發期間每個 NNN 只做**當下該做的那一塊**，做完即推進切換到別的迫切問題（橫向切換，不是收尾）；**嚴禁每輪急著收斂／急著完善／急著給完成戳記**。完善（功能從頭到尾打磨到完成）只限 slug **最後一個 NNN**——前提是所有問題已浮現、無未知殘留；在那之前永遠預設「還有沒做的」，不提前收斂。

## NNN 生命週期

每個 NNN 僅產出 `G1.md` 與 `G2.md`，禁止新增 slug 鏈外文件（白名單見 SKILL.md「`.shiftblame/` 內部佈局」）。

**範圍聚焦**：每個 NNN 處理單一可驗證問題（可寫成驗收條件、可驗收的單一問題）；不同問題拆成獨立 NNN，不混在同一 NNN。

**證據鏈最低條件**：凡涉及技術判斷、架構/套件/外部 API、效能/安全/成本、repo 無先例、與老闆技術直覺衝突或 agent 不確定者，須列出證據來源、查證狀態、未知項、風險/反證與替代方案。低風險且 repo 內已有明確先例者，可引用專案現況作為證據，不強制外查。

**體驗閘門**（修正/優化類變更）：管理者與老闆共同完整體驗產品，記錄使用者體驗、缺陷、BUG 等問題。問題寫入當輪 slug 的反方/收斂或 SOP 已知問題區。新功能開發類無此閘門。

**START**：載入三層租約（SOP｜SLUG §7｜SKILL+GATE+MANAGE+ROLE/G1+G2）→揭露目標→**暫停等老闆確認**。

**正方（雙軌平行）**：G1 正方提出計畫方案 ‖ G2 正方提出技術方案。固定兩個子代理，各自承擔 G1/G2 視角。正方須說明方案依據，不把老闆的非技術描述直接轉成技術結論。

**反方（雙軌平行）**：G1 反方質疑計畫方案 ‖ G2 反方質疑技術方案。同一子代理切換為反方身份做初步質疑（保留內部對抗）。反方須檢查是否迎合老闆技術直覺、是否缺少證據鏈、是否隱藏反證或替代方案。反方獨立複審的 codex 啟用與雙層細則見閘門原則 12。

**收斂**：管理者分別收斂 G1 和 G2，產出兩份各自結論。反方 H/M/L 標註，不做決策。收斂結論與實作內容附於當輪 `G1.md`/`G2.md` 末尾，不另開新文件。收斂須交代證據鏈與取捨：主張依據、查證狀態、未知項、風險/反證、替代方案，以及為何建議推進。收斂後揭露實作意圖（將做什麼變更、依據為何）→**暫停等老闆確認**→確認後才正式實作。

**NNN 推進（commit 與驗收解耦）**：NNN 走完正→反→收斂、實作完成後即 commit（本地存檔，可逆）；commit 不綁驗收。NNN 層驗收可選（管理者初判／老闆覆核，機制見 SKILL 核心原則「選用外部角色整合」）。commit 後由老闆指示推進到下一個 NNN（或退回）。此層級無 PASS/FAIL 判定。

**Slug 閘門（slug 結束才適用）**：整條 slug 所有 NNN 完成、老闆拍板 slug 結束時 → 老闆 PASS → 走收尾流程。PASS 是 slug 層級的唯一閘門判定，由老闆決定，agent 不得自行宣告。

## 收尾

1. 老闆有意拍板 slug 結束時，先觸發 **slug 末強制驗收**（兜底，見 SKILL 核心原則「選用外部角色整合」）：整條 slug 成果交 codex 獨立驗收；codex 判退修→不得 PASS，rework 後重驗
2. slug 末驗收通過後，老闆拍板 slug 結束（PASS）進入收尾
3. 管理者品質確認
4. 老闆 PASSED
5. 管理者更新 REPO.md、ROADMAP.md、SOP.md、GRAPH.md 與相關 PRD/PID
6. Obsidian 連接收尾：確認 `.shiftblame/` 整棵樹可作 vault root 可視；驗證四文件、`PRD/`、`PID/` 內所有 wiki links 解析到現有 Markdown；`archive/` 與開發中 slug 可視但不列入連接完整性
7. `git checkout main && git merge --no-ff feat/<slug>`→推送→清理（每個 slug 恰好一個 merge commit）
8. 歸檔：將 `.shiftblame/<slug>/` 移至 `.shiftblame/archive/<slug>/`（archive 為可清空暫存，老闆可隨時清理），並更新 GRAPH.md 與 REPO.md 的歸檔紀錄（持久紀錄，欄位見各檔模板）
9. 反面教訓提煉：若本 slug 有「方向性錯誤被否決撤回」的教訓，提煉為方向性紀律（不保留單案 slug 名與具體系統內容），記入專案 SOP 的反面教訓區或對應原則旁。單案完整過程隨 slug 歸入 `archive/`。判準：教訓是否「可脫離單案、通用於未來」——是則提煉，否則只歸檔

**回歸規則**：改善建議→SOP 未完成項目；BUG→SOP 已知問題區；目標→SOP 當前目標區。

## 視覺驗收原則（UI／玩家-facing／入口／可旋轉 3D 場景類變更）

1. **可視化驗證不可省略**：UI／玩家-facing／入口類問題不能只靠 headless CLI，須含可視驗證證據
2. **前端測試預設瀏覽器工具**：前端 UI／互動／視覺驗證預設用瀏覽器工具（可視截圖、pixel metric、互動探查、視覺近似度評估），不得只用 headless CLI 斷言 UI 行為。視覺類變更須有瀏覽器可視證據
3. **可旋轉 3D／場景類多視角**：涉及可旋轉 3D 場景、相機軌道或縮放層級的視覺變更，驗證須涵蓋多視角截圖比對（預設、拉近、拉遠、轉動等），不得只驗單一視角
4. **最終裁判是老闆的眼睛**：自動化圖像識別只能當「有無回歸」的粗篩，不得單獨據以 PASS；與老闆直覺衝突時預設相信老闆。最終 PASS 須老闆親眼看過
