# SBM-GATE — 閘門、`<nnn>` 生命週期、複審、收尾

## 1. 範圍

本規範定義框架之閘門原則、狀態序、`<nnn>` 生命週期、G3 執行規劃階段、複審機制與收尾程序。本規範為 SBM-SKILL §9（管線）之子規範。規範詞彙依 SBM-SKILL §3.1（RFC 2119 / RFC 8174）。

## 3. 閘門原則

### 3.1 回饋即意圖

見 SBM-SKILL §5.1。

### 3.2 老闆角色邊界

老闆提供大局／需求／優先序／風險接受／PASS-FAIL。agent MUST 以證據提可反駁建議；技術裁判由 agent 承擔。

### 3.3 證據閘門

正方／反方／收斂 MUST 標主張依據、查證狀態、未知項、風險反證與替代方案。未查證者 MUST NOT 作推進或 PASS 依據，MUST 改走查證路由（SBM-SKILL §5.4）。

### 3.4 先提案再質疑

見 SBM-SKILL §5.6。

### 3.5 迭代收斂

見 SBM-SKILL §5.7。

### 3.6 正反收斂軌分軌

G1 外部研究規劃視角 ‖ G2 內部技術實作視角，正反收斂分軌產出各自收斂，相輔相成不分先後。

### 3.7 固定雙軌（正反收斂）

正反收斂 MUST 只走 G1+G2 雙軌。正方主 session 身份切換、反方子代理獨立。執行者歸屬實作軌（見 SBM-SKILL §5.13）。G3 為共識後執行規劃層（非正反收斂軌），見 §6。

### 3.8 變更前先體驗

見 SBM-SKILL §5.8。

### 3.9 Slug 前置硬閘門

實作前 MUST 先完成：

1. slug 文件夾建立
2. 反方子代理回收
3. 管理者收斂寫入 G1.md/G2.md

啟動序列含文件衛生檢測（SOP/ROADMAP 存在性 + 措辭 grep，見 SBM-SKILL §8.1 步驟 1）。不符即 MUST 進入修正路由（先修正再開 slug）。

### 3.10 正反收斂軌隔離

G1/G2 正反收斂分軌產出（正方身份切換、反方獨立上下文）。管理者 MUST 合併為實作基線。G3 為非正反收斂軌，不適用此隔離原則。

## 4. 狀態序

### 4.1 Slug 狀態

`IN_PROGRESS → PASSED`

PASS 唯 slug 層級，由老闆拍板 slug 結束。

### 4.2 `<nnn>` 狀態

`START → 正方 → 反方 → 收斂 → G3 執行規劃層（產 <plan>）→ 執行者逐項實作（每項 <task> 自驗通過即 commit）→ <complete> 達成 →（老闆指示推進）下一個 <nnn>`

`<nnn>` 層級無 gate／無 PASS／無 FAIL。推進時機 MUST 由老闆隨時指示。執行者/管理者推進前 MUST 請示老闆。`<nnn>` 走完時 MUST 進入等待老闆指示狀態。

commit 為本地存檔（可逆）。push 為對外動作，MUST 經老闆指示。

### 4.3 節奏紀律

「功能告一段落」≠「功能全部完善」。每個 `<nnn>` MUST 只做當下該做的那一塊，做完即推進切換。每輪聚焦當下範圍完成；完善保留至 slug 最後一個 `<nnn>`（前提：問題已浮現、無未知殘留）。

執行者達成 `<complete>` 為實作完成，非 PASS。PASS 唯老闆拍板 `<slug>` 結束。

## 5. `<nnn>` 生命週期

### 5.1 產出範圍

每個 `<nnn>` 產出限於 `G1.md` + `G2.md` + `G3.md`。額外文件 MUST 歸入 slug 鏈或 MUST 記入技術債。

範圍 MUST 聚焦單一可驗證問題；不同問題 MUST 拆獨立 `<nnn>`。

### 5.2 各階段

| 階段 | 動作 |
|------|------|
| **START** | 載入三層租約（SOP｜SLUG §6｜SKILL+GATE+ROLE/+TEMPLATES/）→ 揭露目標 → **暫停等老闆確認** |
| **正方（雙軌分軌）** | 主 session 擔任 G1 提計畫方案 ‖ G2 提技術方案（身份切換，分軌產出）。MUST 說明依據；老闆非技術描述 MUST 先轉譯為技術規格再作結論 |
| **反方（雙軌分軌）** | 子代理擔任 G1 質疑計畫 ‖ G2 質疑技術（獨立上下文對抗） |
| **收斂** | 管理者分別收斂 G1／G2，產出兩份結論（G1 產 `<task>`／G2 產 `<complete>`），附於當輪 G1.md/G2.md 末尾。收斂 MUST 交代證據鏈與取捨。收斂後揭露實作意圖 → **暫停等老闆確認** → 確認後管理者合併為一致基線 → **G3 執行規劃層**（見 §6，產 `<plan>`）→ 派發執行者實作 |

## 6. G3 執行規劃階段

G1+G2 收斂基線後，管理者進入 G3 執行規劃階段，產出 `<plan>`（實作策略 + 行動序列 + 驗收流程 + 明確化 `<complete>`）。G3 為共識後執行規劃層（非正反收斂軌，見 SBM-SKILL §5.13）。本節為 G3 複雜度判定 + Minor/Major 變更模型的**單一權威定義處**；G3.md 模板僅放格式骨架並指標引用本節。

### 6.1 複雜度判定準則

合併基線後、派發執行者前，管理者 MUST 依三維度判定複雜度（**待校準建議值，首次引入無歷史樣本**）：

| 維度 | 複雜門檻 |
|------|----------|
| `<task>` 序列長度 | ≥ 4 |
| 跨檔數 | ≥ 4 |
| 強序列依賴對 | ≥ 2 |

### 6.2 判定結果與切段規則

- 滿足任一 → 複雜 → 序列派發多個執行者（依賴鏈斷點/檔案邊界切段，一個完成才開下一個，非並行）
- 皆未達 → 單一執行者逐項
- 獨立檔 `<task>`：MAY 任意切
- 一致性 `<task>`（跨檔同步）：MUST 保持於同一執行者實例

管理者 MAY 依 SBM-SKILL §5.18① 調整，MUST 記錄理由。明確化 `<complete>` 格式見 SBM-TM-G2 §5.3。

### 6.3 Minor/Major 變更模型

執行中變更分兩類：

**Minor（當前 `<nnn>` 內）**：實作順序調整 / 驗證方式調整 / 細節方案替換。流程：執行者發現問題 → 更新 `<plan>` → commit 訊息記錄變更（`change(<slug>): <摘要>`）→ 繼續當前 `<nnn>`。

**Major（觸發新 `<nnn>`）**：任務目標改變 / 完成標準改變 / 架構方向改變。流程：提出變更 → 重新 G1/G2 正反收斂 → 產生新版 `<plan>` → 新 `<nnn>`。

**中間地帶判定**：

| 情境 | 分類 |
|------|------|
| 跨檔但不改目標（如同步更新條文用語） | Minor |
| 完成標準細節調整（如 V3 判準 ≥3 改 ≥4） | Minor |
| 實作順序調整導致依賴鏈重組 | Major |

### 6.4 明確化 `<complete>` 位置

明確化 `<complete>` 段於 G3 階段產出，**附於 G3.md §2.1③**（當輪具體清單）；**格式權威定義保留於 SBM-TM-G2 §5.3**（四類驗證類型 / `T[N]` / `V[N][.M]` / `S#` 規則不搬移）。

## 7. 複審機制（外部審查）

### 7.1 觸發點

| 觸發點 | 機制 |
|--------|------|
| ① G1/G2 收斂段寫入後 | 老闆-gated、預設關閉（收斂後揭露審核升級鏈選項） |
| ② `<nnn>` 所有序列（`<task>`）執行完畢後 | post-執行者硬審核（MUST 做）。執行者達成 `<complete>` 後 MUST 做獨立審核。同時承擔 G3 無反方之殘留風險（G3 不走正反收斂，見 SBM-SKILL §5.13） |
| ③ `<slug>` 分支全域 | 老闆-gated、預設關閉 |

### 7.2 觸發點② 審核路由

管理者 MUST 揭露升級鏈選項 → 老闆選擇擔任者（見 TOOLS/AUDIT/）。

- 老闆選外部 → 依選擇調度
- 老闆未選外部 → read-only 子代理 MUST 獨立 code review，審 e2e 證據／未驗項
- 管理者自審 → MUST 改走獨立審核路由（SBM-SKILL §5.14）

### 7.3 流程

- **①③**：管理者狀態揭露 → 交付老闆 → 老闆選擇是否複審（①含升級鏈選項）
- **②**：管理者依擔任者選擇調度獨立審核 → 回收 code review/e2e 結果 → 狀態揭露（自驗／獨立 review／e2e／未驗項）→ 交付老闆

未跑 e2e 即 MUST 標「未驗」。擔任者與工具細則見 TOOLS/。

## 8. 收尾

老闆拍板 slug 結束（PASS）方 MUST 走收尾：

| 步驟 | 動作 |
|------|------|
| ① | 管理者品質確認 |
| ② | 老闆 PASSED |
| ③ | 更新 SOP/ROADMAP（MUST 寫當下事實；日誌式／教訓式措辭 MUST 改寫為當下結構性事實，見 SBM-SKILL §5.5） |
| ④ | `git checkout main && git merge --no-ff feat/<slug>` → 推送 → 清理（每 slug 恰一個 merge commit） |
| ⑤ | 歸檔 `.shiftblame/<slug>/` 至 `archive/` |
