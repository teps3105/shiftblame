# sb-do — 核對完稿，自動放行進入開發

> **自動階段觸發**：sb-think 已確認的工作完成定義層一次推進後，由主對話直接執行。位置：G1→G2→G3 各一次定稿、§10 核對 → 放行進入開發；放行是工作狀態邊界，不另向老闆確認。

定義層一次推進完成後自動執行。G1 承接 sb-think 已確認的語義，G2／G3 向前對齊；主對話核對完稿後直接放行，不把 skill 觸發或 CLI 推進當成新決策。

先 `load skill: shiftblame`，主對話秘書執行：

## 流程

0. **秘書核對 §10 一致性**（主對話）：讀取當前 `<ms>` 的 G1／G2／G3，親自核對兩兩雙向一致（三對六向）——這是一次核對（一次定律，SKILL §1.1），非環形重跑入口。核對結論 MUST 落記錄 `<repo>/.shiftblame/tmp/alignment-check.md`（三對各自結論）。
0.5. **過狀態機閘門並封存 G1**：`sb next release`（SKILL §1.8）——除 G3 失敗模式、實作步驟與 §10 記錄外，腳本查核 G1 每項 AC-ID 的 BEHAVIOR 契約欄位，以及 G3 是否以相同 ID 逐項承接；通過時封存完整 G1 與 SHA-256。不得帶 `--boss-ok` 或再次詢問。
1. **放行判定**：
   - **三對六向全成立** → 放行。SKILL §3 臨時檢閱條件未觸發者不要求配套；已觸發者須有主對話複核後的結論或「未驗」揭露。SLUG §4 節點從 `三面向制衡（G1→G2→G3）` 推進到 `開發`。
   - **任一向缺漏** → **拒絕放行**，提示具體缺漏（如「G2 §1 技術分析未回指 G1 需求 R3」），責任面向一次補正後重核（不打轉，不環形重跑三面向制衡）。
   - 觸發臨時檢閱條件但未取得結論 → 對應項標「未驗」，放行時向老闆揭露後由老闆決定；不阻擋放行。
2. **放行後進入開發**：主對話依 G3 逐功能切換測試→實作→commit 存檔→驗收→判決狀態，完整走完才開下一功能。測試狀態依 G1 定義「過」並鎖定；實作狀態依 G2 寫碼且不得改鎖定測試；實作完成由秘書依 `sb-commit` 存檔；驗收狀態照 G3 對該 commit 跑自動化檢查並逐項收集 G1 使用者行為證據。判決含測試真實性、鎖定與行為證據核對，不通過返工後疊加新存檔再驗。未觸發 §1.4 重流程且確實 `USER_OBSERVABLE=NO` 的微修才可 direct。

   **direct 限制優先**：只有 `USER_OBSERVABLE=NO` 且 `tmp/direct-change.md` 填實理由者可直接修正；任何 G1 AC-ID 或使用者可觀察行為不得套用 direct，收斂仍須具備全部 AC 的 SATISFIED／BEHAVIOR 證據。

## 邊界

- 本 prompt 是**放行 gate**，不產出新文件、不改需求；只核對既有 G1~G3 一致性並推進節點。
- 一致性核對以 §10 為唯一判準；不得以「看起來一致」繞過逐項核對。
- 放行後進入開發；G1 成為封存契約。開發中只有 CONFORMS 的技術細節可單調細化 G2／G3；UNDERSPECIFIED／CONFLICTS 必須停止，以 `tmp/amendment.md` 記錄差異並經老闆確認後 `sb amend --boss-ok` 修約（§1.4.1）。
