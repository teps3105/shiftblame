# sb-do — 確認完稿，放行進入開發

當老闆要放行開發時執行（由 sb-think 分發）。用於定義層一次推進完成、老闆確認完稿後，放行進入開發。

先 `load skill: shiftblame`，主對話秘書執行：

## 流程

0. **秘書核對 §10 一致性**（主對話）：讀取當前 `<ms>` 的 G1／G2／G3，親自核對兩兩雙向一致（三對六向）——這是一次核對（一次定律，SKILL §1.1），非環形重跑入口。
1. **放行判定**：
   - **三對六向全成立** → 放行（觸發獨立研究條件者——複雜／高風險／無先例／與老闆直覺衝突／老闆指定，SKILL §3——須已由秘書代派子代理複核、結論存 `<repo>/.shiftblame/tmp/`；未觸發條件者不要求配套）。SLUG §4 節點從 `三面向制衡（G1→G2→G3）` 推進到 `開發`。
   - **任一向缺漏** → **拒絕放行**，提示具體缺漏（如「G2 §1 技術分析未回指 G1 需求 R3」），責任面向一次補正後重核（不打轉，不環形重跑三面向制衡）。
   - 觸發獨立研究條件但未取得結論 → 對應項標「未驗」，放行時向老闆揭露後由老闆決定；不阻擋放行。
2. **放行後進入開發**：主對話秘書依 G3 實作計畫採多循環螺旋開發（§1.4），推進**執行層時序**執行觸發重流程條件的功能（commit 單位）；**每個 ms 就是一個里程碑**（G3 §1.5 定義本 ms 功能範圍）。**預設直接修正**：功能未觸發 §1.4 重流程條件（① 行為改變 ② 介面改變 ③ 多檔協同 ④ 跨層級 ⑤ 老闆指定）時，秘書直接執行並 commit，不走執行層時序。觸發時走執行層落地時序：測試階段（子代理）依 G1 寫測試定義「過」→ 實作階段（**主對話**，依 G2）寫實作碼＋實機驗證 → 驗收階段（子代理）照 G3 跑 CI 測試、驗收「完成」→ 秘書讀 `<repo>/.shiftblame/tmp/` 三份產出後**判決合格才 commit（獨佔）**；判決含**測試真實性檢查**（無真實斷言的假測試判返工回測試階段）與**測試鎖定核對**（鎖定測試碼被測試階段以外改過即判返工回測試階段重新定義，SKILL §3——任何角色不得為綠燈逕改測試）。**測試先行**：先寫測試（紅燈）再實作，與定義層「驗收先於實作」對齊。本 ms 所有功能 commit 完成後觸發收斂。**commit 與所有判決（合格/返工）由秘書獨佔**；執行層中測試/驗收性質子代理可在授權範圍內寫 repo（測試寫測試碼、驗收寫測試環境配套並跑 CI 測試）但皆不可 commit，**實作階段（G2 落地）由主對話親為**（§3 承載歸屬）；定義層中審計/規劃性質子代理對 repo 唯讀，**研究階段（G2）由主對話親為**。

## 邊界

- 本 prompt 是**放行 gate**，不產出新文件、不改需求；只核對既有 G1~G3 一致性並推進節點。
- 一致性核對以 §10 為唯一判準；不得以「看起來一致」繞過逐項核對。
